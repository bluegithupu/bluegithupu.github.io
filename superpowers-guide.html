核心理念

TDD 测试驱动开发

先写测试，先看失败。测试写在代码之前才能证明它真正测试了正确的东西。

系统化方法优先

临时方案会累积技术债。系统化的方法确保每个问题都得到彻底的解决。

降低复杂度

小而bounded的单元更容易推理和测试。避免过度设计。

证据优先于声称

「完成」「修复」「通过」这些词必须建立在实际运行验证命令的基础上。

技能库详解

🤝 协作流程 9 个技能

brainstorming 头脑风暴

任何创意工作（功能、组件、行为修改）之前必须激活的技能。 提供硬性关卡，确保设计得到用户批准后再开始实现。

流程：探索上下文 → 澄清问题 → 提出方案 → 展示设计 → 写设计文档

硬性规则：未经用户批准的设计，不得开始任何编码工作

writing-plans 编写计划

将复杂任务分解为可执行计划。每个任务 2-5 分钟，包含具体文件和命令。 使用 TDD 流程：失败测试 → 最小代码 → 通过测试。

核心原则：每个步骤必须有实际代码和命令，不允许占位符

executing-plans 执行计划

按照预写的计划进行实现。三步流程：加载审核 → 执行任务 → 完成开发。 遇到阻塞立即停止并寻求帮助。

关键要求：严格遵循计划步骤，不跳过验证，遇到障碍立即求助

subagent-driven-development 子智能体驱动开发

每个任务分发独立的fresh子智能体，双阶段审查（规范合规性 → 代码质量）。 一次只运行一个子智能体避免冲突。

子智能体状态：DONE / DONE_WITH_CONCERNS / NEEDS_CONTEXT / BLOCKED

模型选择：机械任务用廉价模型，架构设计用最强模型

using-git-worktrees 使用 Git 工作树

创建隔离的开发空间。首先检测现有隔离状态，优先使用平台原生工具， Git 作为最后的备选方案。

安全规则：验证项目目录已gitignore后再创建工作树

finishing-a-development-branch 完成开发分支

开发完成后的验证和清理工作。验证测试 → 检测环境 → 展示选项 → 执行选择 → 清理工作空间（仅在适当时机）。

选项1和4才会清理工作树，永远不删除用户需要的工作空间

requesting-code-review 请求代码审查

「及早审查，频繁审查」原则。任务后强制审查，主要功能后强制审查， 合并前强制审查。

严重程度：Critical立即修复 → Important前进前修复 → Minor记录后续处理

反馈处理：审查者发现问题 → 实现者修复 → 再次审查

receiving-code-review 接收代码审查反馈

以技术严谨性而非情绪化表演来接收反馈。验证后再实现，有疑问就提问， 建议错误时用技术推理反驳。

核心态度：外部反馈是建议而非命令，验证后再实施

dispatching-parallel-agents 并行分发智能体

多个独立问题可以同时调查时使用。将不同问题分发给不同子智能体并行处理， 大幅节省时间。

前提条件：问题必须独立、可并行执行、自包含

价值所在：三 个独立问题可在一个问题的时间内解决

🧪 测试驱动 1 个技能

test-driven-development 测试驱动开发

TDD 铁律：没有失败的测试就不能写生产代码。 RED（写失败测试）→ GREEN（写最小代码通过）→ REFACTOR（重构）

为什么顺序重要：代码后写的测试会立即通过，什么也证明不了。

好测试：最小化（只测一件事）、清晰的名字、使用真实代码而非mock

🔧 调试与验证 2 个技能

systematic-debugging 系统化调试

找到根本原因后再尝试修复。四阶段：根因调查 → 模式分析 → 假设验证 → 实施修复。

铁律：未经根因调查，禁止提出修复方案

警告信号：尝试3次以上修复失败？质疑架构而非症状

verification-before-completion 完成前验证

在声明工作「完成」「修复」「通过」之前，必须实际运行验证命令并检查输出。 测试通过≠代码编译，智能体报告成功≠更改正确。

铁律：运行命令，读取输出，然后才报告结果。无例外，无捷径。

⚙️ 元技能 2 个技能

using-superpowers 使用技能框架

关于如何有效使用其他技能的元框架。核心原则：任何响应前先检查技能， 即便只有1%的可能性也要激活。

优先级：用户指令 > 技能 > 系统默认

流程技能（头脑风暴、调试）优先于实现技能

writing-skills 编写技能

用 TDD 的方法编写技能文档。RED（无技能时运行，文档化理性化）→ GREEN（编写最小技能）→ REFACTOR（添加反制措施）。

铁律：「没有失败的测试就没有技能」

技能结构：技能名/SKILL.md + 支持文件（仅在需要时）

技能调用关系

📍 触发入口

  • 用户发起创意任务 → brainstorming 自动触发
  • 用户发起实现任务 → writing-plans 自动触发
  • 任何响应前 → using-superpowers 检查

🔗 串联关系

  • brainstorming → writing-plans → executing-plans
  • executing-plans → subagent-driven-development
  • subagent-driven-development → requesting-code-review
  • requesting-code-review → receiving-code-review
  • executing-plans → finishing-a-development-branch

🔧 支撑技能

  • systematic-debugging → 任何调试场景
  • verification-before-completion → 任何完成声明前
  • using-git-worktrees → 执行计划前创建隔离环境
  • dispatching-parallel-agents → 多个独立问题时

⚙️ 元框架

  • using-superpowers → 管理所有技能使用规则
  • writing-skills → 定义如何编写新技能
  • 所有技能 → 遵循 TDD 理念
