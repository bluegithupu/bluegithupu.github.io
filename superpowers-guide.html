技能优先级
触发规则

using-superpowers 是整个技能体系的入口点。它在每个对话开始时触发，决定哪些技能适用于当前任务。

核心原则：如果你认为某个技能有 1% 的可能性适用于你正在做的事情，你必须调用该技能。这不是可选的，不可协商，你也不能用合理化理由规避。

指令优先级：用户明确指令 > Superpowers 技能 > 默认系统提示词。当 CLAUDE.md 与技能冲突时，遵循用户的指令。

优先级技能类型示例说明
1（最高）流程技能brainstorming, systematic-debugging决定如何处理任务
2实施技能各种领域专用技能指导执行细节

💡 "让我构建 X" → 先 brainstorming，再实施技能。"修复这个 bug" → 先 debugging，再领域技能。

计划结构
无占位符原则

writing-plans 将设计文档转化为详细到"热情但缺乏品味、没有判断力、没有项目上下文、讨厌测试的初级工程师"都能遵循的实施计划。

计划保存位置： docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md

每个步骤粒度：一个动作（2-5 分钟）。含完整代码、精确文件路径、验证步骤。

概述
两阶段审查
子代理状态处理

subagent-driven-development 是整个体系的核心执行引擎。它在同一会话中逐任务派发全新的子代理，每个子代理完成后进行两阶段审查。

核心原则：每任务一个全新子代理 + 两阶段审查（规范符合性 → 代码质量）= 高质量、快速迭代。

连续执行：任务之间不要暂停与用户确认。除非遇到无法解决的阻塞、阻碍进度的歧义、或所有任务完成。"我应该继续吗？"的提示和进度摘要是在浪费用户时间。

每任务执行流程（两阶段审查）

①
派发实施子代理
使用 implementer-prompt.md 模板
②
子代理实施+自审
TDD 循环，提交，自检
③
规范符合性审查
派发 spec-reviewer 子代理
④
代码质量审查
派发 code-quality-reviewer 子代理
✅
标记任务完成
进入下一个任务

⚠️ 关键顺序：规范符合性审查（阶段③）必须在代码质量审查（阶段④）之前完成。不能跳过顺序或颠倒。

子代理返回的 4 种状态及处理方式

状态含义处理方式
DONE任务完成进入规范符合性审查
DONE_WITH_CONCERNS完成但标记了疑虑先阅读疑虑，再决定是否需要处理，然后进入审查
NEEDS_CONTEXT需要更多信息提供缺失上下文，重新派发同一个子代理
BLOCKED无法完成任务1. 提供更多信息重新派发；2. 换用更强模型；3. 将任务拆分为更小单元；4. 上报用户
概述
与 subagent 模式对比

executing-plans 在不支持子代理的平台上的替代执行方案。它加载计划、严格按步骤执行、在检查点暂停供人工审查。

使用场景：平台不支持子代理（如某些 CLI 环境）时，作为 subagent-driven-development 的替代方案。

注意：如果平台支持子代理，请使用 subagent-driven-development，质量会显著更高。

对比维度subagent-driven-developmentexecuting-plans
执行环境同一会话单独会话（含审查检查点）
子代理每任务派发全新子代理无子代理，主代理执行
审查机制两阶段自动审查批量执行 + 人机检查点
迭代速度快（任务间不暂停）较慢（检查点暂停）
适用平台支持子代理的平台（Claude Code 等）不支持子代理的平台

dispatching-parallel-agents 将独立任务并行派发给多个专用子代理。每个代理获得精确裁剪的指令和上下文，互相不干扰。

核心原则：每个独立问题域派发一个代理。让它们并发工作。

使用场景：3+ 测试文件以不同根因失败、多个子系统独立损坏、每个问题可以在不了解其他问题上下文的情况下理解。

好的代理提示词特征：① 聚焦（一个清晰的问题域）② 自包含（理解问题所需的全部上下文）③ 输出明确（代理应该返回什么）。

❌ 不要使用当：失败相关（修复一个可能修复其他）→ 先一起调查；需要完整上下文；探索性调试（还不知道哪里坏了）；共享状态（代理会互相干扰）。

红-绿-重构
铁律

test-driven-development 是整套体系的质量基石。先写测试，观察它失败，再写最少代码让它通过。

核心原则：如果你没有观察到测试失败，你就不知道它是否测试了正确的东西。

适用范围：新功能、Bug 修复、重构、行为变更。例外（需征得用户同意）：一次性原型、生成代码、配置文件。

在测试之前写了代码？删除它。从头开始。
❌ 常见合理化借口✅ 现实
"太简单了不需要测试"简单的代码也会坏。测试只需 30 秒。
"我会在之后测试"测试立即通过证明不了任何事。
"测试之后能达到同样目的"测试-之后 = "这做什么？" 测试-之前 = "应该做什么？"

"删除 X 小时工作是浪费"沉没成本谬误。保留无法验证的代码 = 技术债。

requesting-code-review 在问题级联前主动派发代码审查子代理来捕获问题。审查者获得精确裁剪的上下文进行评估 — 绝不继承你会话的历史。

核心原则：早审查，常审查。

强制审查时机：① subagent-driven-development 中每个任务后；② 完成主要功能后；③ 合并到 main 之前。

审查流程：获取 git SHAs → 派发代码审查子代理（使用 code-reviewer.md 模板）→ 根据反馈行动（Critical 立即修复，Important 继续前修复，Minor 稍后处理）。

概述
禁止响应
何时反驳

receiving-code-review 定义了接收代码审查反馈时的行为准则。需要技术严谨性，而非情绪化表现。

核心原则：先验证，再实施。先询问，再假设。技术正确性优先于社交舒适度。

响应模式：读取完整反馈 → 用自己的话理解需求 → 对照代码库实际情况验证 → 评估对本代码库技术是否正确 → 技术确认或理由充分反驳 → 一次实施一项，每项测试。

🚫 禁止的响应（CLAUDE.md 明确违规）

❌ "You're absolutely right!"（表演性同意）
❌ "Great point!" / "Excellent feedback!"（情绪化表现）
❌ "Let me implement that now"（未经验证）

✅ 重述技术需求
✅ 提出澄清问题
✅ 用技术推理反驳（如果错了）
✅ 直接开始工作（行动胜于言辞）

💡 如果你抓住自己即将写 "Thanks" → 删除它。陈述修复内容即可。为什么不要感谢？行动本身说明你听到了反馈。

门控函数
常见失败

verification-before-completion 要求在声明工作完成、修复完成或通过之前，必须先运行验证命令并确认输出。

核心原则：证据先于断言，永远。

铁律：如果在这条消息中没有运行验证命令，你不能声称它通过。

NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE
在声称任何状态或表达满意度之前 — 运行命令，读取输出，然后声称结果

门控函数（每次声明前必须执行）

1. IDENTIFY：什么命令能证明这个断言？
2. RUN：执行完整命令（新鲜、完整）
3. READ：完整输出，检查退出码，统计失败数
4. VERIFY：输出是否确认了断言？
  • 如果 NO：陈述实际状态（附证据）
  • 如果 YES：陈述断言（附证据）
5. ONLY THEN：做出断言
断言需要不充分
测试通过测试命令输出：0 失败上次运行、"应该通过"
Linter 干净Linter 输出：0 错误部分检查、外推
构建成功构建命令：exit 0Linter 通过、日志看起来不错
Bug 已修复测试原始症状：通过代码已更改，假设已修复
代理完成VCS diff 显示更改代理报告 "success"

四阶段
铁律

systematic-debugging 提供了一套系统化的四阶段调试方法，防止随机修复浪费时间并引入新 Bug。

核心原则：永远先在根因调查之后再尝试修复。症状修复是失败。

特别适用于：时间压力下（紧急情况让人想猜测）、"只是一个快速修复"看起来很明显、你已经尝试了多种修复、之前的修复没有工作、你不完全理解问题。

1
根因调查
读取错误、重现问题、检查最近更改、收集多组件系统中的证据
2
模式分析
找到工作示例、与参考对比、识别差异、理解依赖关系
3
假设与检验
形成单一假设、最小化测试、验证后再继续
4
实施
创建失败测试 → 实施单一修复 → 验证修复

⚠️ 如果 3+ 次修复都失败了 → 停止并质疑架构

模式表明架构问题：每次修复在不同地方揭示新的共享状态/耦合/问题；修复需要"大规模重构"来实施；每次修复在其他地方创造新症状。
这与失败假设不同 — 这是错误的架构。在尝试更多修复之前，先与你的用户伙伴讨论。

NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
如果你还没有完成阶段 1，你不能提出修复方案
🚩 危险信号（立即停止并返回阶段 1）
"快速修复一下，稍后调查"
"先试试改 X，看看是否工作"
"一次加多个更改，运行测试"（无法隔离有效更改）
"跳过测试，我会手动验证"
"我完全不理解但这可能行"
"再试一次修复"（已经尝试 2+ 次后）

TDD 映射
技能描述优化

writing-skills 是"元技能"——用于创建新技能的技能。它将 TDD（测试驱动开发）应用于流程文档：写压力测试场景（子代理）→ 观察失败（基线行为）→ 写技能文档 → 验证通过。

核心原则：如果你没有观察到代理在没有技能的情况下失败，你就不知道技能是否教会了正确的东西。

前置要求：必须先理解 test-driven-development 技能。此技能将 TDD 适应到文档创作。

Claude 搜索优化（CSO）—— 描述字段关键规则

⚠️ 关键：描述 = 何时使用，而非技能做什么

描述字段应该只描述触发条件。不要总结技能的工作流程。
为什么这很重要？测试发现，当描述总结工作流程时，Claude 可能遵循描述而不是读取完整的技能内容。
例如：描述说"代码审查 between tasks"导致 Claude 只做一次审查，尽管技能的流程图清楚地显示了两阶段审查。

"Use for TDD - write test first, watch it fail...""Use when implementing any feature or bugfix, before writing implementation code"
"Use when executing plans - dispatches subagent...""Use when executing implementation plans with independent tasks in the current session"

核心理念与哲学
🔴🟢🟣
测试驱动开发（TDD）
先写失败测试，观察它失败，再写最少代码让它通过。如果你没有观察到测试失败，你就不知道它是否测试了正确的东西。删除测试前写的代码，从头开始。
🧠
设计先于实施
任何创造性工作前，必须经过 brainstorming。探索需求，提出多个方案，呈现设计，获取审批。即使"简单"项目也不跳过。
🔍
证据先于断言
在声称工作完成前，必须先运行验证命令并确认输出。永远不在没有新鲜验证证据的情况下声称完成。
🎯
YAGNI
"You Aren't Gonna Need It"—— ruthless 地移除不必要功能。审查者建议"专业"功能时，先 grep 代码库确认是否实际被调用。
🏗️
隔离与清晰
将系统分解为更小的单元，每个都有清晰目的、通过定义良好的接口通信、可以独立理解和测试。
🤖
子代理驱动
每任务派发全新子代理，上下文无污染。两阶段审查（规范符合性 → 代码质量）确保高质量输出。
🔄
DRY / 小步 / 常提交
Don't Repeat Yourself。每步 2-5 分钟。频繁提交，每个提交对应一个完整、可验证的更改。
📊
技术严谨性优先
接收代码审查时，技术正确性优先于社交舒适度。验证后再实施，有理由地反驳，永远不表演性同意。
