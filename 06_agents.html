🧪 核心发现：AGENTS.md 的质量影响 ≈ 换一个模型
最好的 AGENTS.md 带来的质量提升，相当于从 Haiku 升级到 Opus；最坏的 AGENTS.md 让输出比没有文档还差。同一份文件可以对不同任务产生截然相反的效果（±30%）。
🔬 研究方法

评估方法

  • 使用 AuggieBench（内部评估套件）
  • 对比 Agent 输出与资深工程师审查的高质量 PR
  • 每个任务运行两次：有/无 AGENTS.md，比较得分

过滤标准

  • PR 必须限定在单个模块/应用内
  • 范围须是 AGENTS.md 信息可能有帮助的场景
  • 覆盖中层模块（~100 核心文件）效果最佳
✅ 7 个有效模式
1

渐进式披露 > 全面覆盖

把 AGENTS.md 当作技能文档——常见情况高级别描述，细节推到参考文件。最优配置：主文件 100–150 行 + 若干聚焦的参考文档。

+10–15% 全面改善
2

程序化工作流：从失败到完成

将任务描述为带编号的多步骤工作流。影响最显著的模式之一：让 Agent 从"无法完成"变为"首次尝试即正确解决方案"。

正确性 +25% · 完整性 +20%
3

决策表：在写代码前消除歧义

当代码库有 2-3 种合理方法时，强制提前做出选择。用决策表对比（如 React Query vs Zustand）。

best_practices +25%
4

真实代码样例提升代码复用

包含 3-10 行真实生产代码片断。Agent 会遵循模板而不是发明新模式。

code_reuse +20%
5

领域特定规则仍然重要

语言或组织特定的"陷阱"（如用 Decimal 而非 float 处理金融计算）。规则须具体且可执行。

减少截断/精度问题
6

每个"不要"都要配一个"要"

仅有警告的文档表现持续不佳。须同时给出反模式和正确替代方案。

避免过度探索
7

保持代码模块化——AGENTS.md 也是

表现最好的 Agent 文档描述的是相对隔离的子模块。超大、跨领域的根目录 AGENTS.md 表现较差。

最优：中层模块
⚠️ 最大失败模式：过度探索陷阱（Context Rot）
⚠️ 模式 1：过多的架构概述

现象：Agent 被拉去读取数十个文档文件，试图"更好地理解架构"。

后果：加载数万 token 不相关上下文，输出变差。

真实案例：一个两行配置修改任务，Agent 读了 12 个文档，加载约 80K token，搞混了哪个服务拥有该配置。completeness 下降 25%。

⚠️ 模式 2：过多的警告（缺乏对应的"要"）

现象：长"不要"段落缺乏对应的"要" → Agent 针对每个警告验证解决方案。

真实案例：AGENTS.md 含 30+ 条"不要"规则，简单 CRUD 端点任务，Agent 逐一检查每个警告是否相关。耗时翻倍，完整度降低 20%。

💡 核心结论
  1. 差距巨大：最好的 AGENTS.md = Haiku→Opus 的质量跃升；最坏的 = 不如没有文档
  2. 同一份文件可以产生相反效果：一项任务 +25%，另一项 -30%
  3. 最优大小：100-150 行 + 参考文件，优于全面覆盖
  4. 程序化工作流具有变革性：可让 Agent 从失败变为首次即正确完成
  5. 每个"不要"都配对一个"要"：仅有警告的文档持续表现不佳
  6. 过度探索是最大失败原因：过多架构概述和过多警告导致上下文腐烂
  7. 文档环境很重要：好的 AGENTS.md 无法克服糟糕的文档环境（如 500K 规格文档）
  8. AGENTS.md 是唯一可靠发现的文档位置
  9. 对于全新架构，不要用 AGENTS.md——使用规范驱动开发
