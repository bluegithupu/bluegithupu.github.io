🎯 核心问题：不是"选哪个工具"，而是"谁和我们走完这段转型路"
当你把 SDLC 改变为 AIDLC 时，它是可见的。但更难的改变是改变组织中每个人都如何思考他们的工作。
📊 四个转型阶段（当前分布）
STAGE 1

采纳 Agent

~70%

开发者在日常工作流中使用 AI 编码工具。POC 运行中，席位许可正在讨论。

STAGE 2

转向 AI 原生

~20%

Agent 有权自主构建、测试、部署和诊断 CI/CD 故障。

STAGE 3

扩展范围

~10%

Agent 拥有代码审查、较小任务端到端、事件响应。存在点自动化，但系统未完全集成。

STAGE 4

编排一切

<1%

Agent 监督的层级放大每一个人类行动。一个决策级联通过 Agent 层级。

🔄 AIDLC：AI 驱动生命周期的六个阶段

Augment 内部已经在多个阶段实现了 Agent 驱动。以下是每个阶段的详细情况：

1. 构思 （人类主导）
👤 产品负责人或工程师定义意图
较大功能：人类写规格 → Agent 辅助研究/上下文 → 人类通过迭代定稿。
较小任务：从 Slack/Linear/web 接收触发 → Agent 自主拥有范围。
2. 代码生成 （Agent 驱动）
🤖 Agent 写代码、创建 PR
核心思维转变："人类不应该写代码。"
较小任务：Agent 自主拥有完整 PR（代码、测试、文档），处理审查意见和冲突。
"PR 落地时已准备好合并，人类没有碰过一行。"
3. 代码审查 （共同拥有）
🤝 Agent 初审 + 人类最终审查
低风险变更：自动批准（无需人类）。
高风险变更：协作审查，Agent 揭示关键风险和架构决策。
📊 一家企业客户在 3 周内将开发者被代码审查阻塞的时间从 每周 30% 降至 10% 以下。
4. 验证 （Agent 驱动）
🤖 Agent 部署、测试、验证端到端
Agent 部署 PR 到预发环境，通过浏览器自动化演练功能，验证端到端工作。
门槛：不是"能编译吗"或"单元测试通过吗"，而是"它做了正确的事吗，端到端？"
5. 构建/测试失败 （知识复利）
🤖 Agent 自动修复简单情况 + 人类协作调查困难情况
每次会话（自主或协作）都会被提炼和持久化。
复利效应："下次发生类似故障时，Agent 无需人类参与即可处理。"
6. 事件响应 （最不成熟阶段）
🤖 协调的 Agent 团队 + 人类待命
代替凌晨 2 点呼叫人类工程师：分级员、调查员、PR 作者、Slack 协调员、SRE 组成的 Agent 团队工作事件。
人类角色："可用，但不驾驶。"
🧠 思维转变：不只是工作流改变
"当 Agent 写代码时，工程师失去了通过写代码培养的直觉。新的技能是通过规格和审查（而不是通过实现）来维护系统理解。"
— Augment Code 工程团队

❌ 旧思维

  • "我是一个写代码的人"
  • 原始编码能力是核心评价维度
  • 通过实现来建立系统理解
  • 工具评估基于功能特性对比

✅ 新思维

  • "我是一个定义意图并引导 Agent 走向正确结果的人"
  • 六大评价维度（原始编码能力不再是独立维度）
  • 通过规格和审查维护系统理解
  • 转型伙伴比工具特性更重要
🎯 AI 原生工程师的六大评价维度

原始编码能力不再是独立维度。组织现在从六个维度筛选：

🎨

产品品味

判断什么值得构建、用户体验是否正确的直觉

🏗️

架构判断

在系统层级做出正确权衡的能力

🤖

Agent 利用能力

高效引导 Agent 完成复杂任务

💬

沟通能力

清晰表达意图、提供有效反馈

🏆

主人翁精神

对结果负责，而不仅仅是对输出负责

⚡

学习速度

快速适应新工具、新模型、新范式

❌ 错误的问题 vs 正确的问题
❌ 错误的问题（VP 工程们每天都在问的）
"帮我对比这些 AI 编码工具的功能和定价……"
✅ 正确的问题（应该问的）
"不是'哪个工具'，而是'谁会和我们一起走完这段转型路'。"
🎯 核心结论
  1. 这不是工具变更——角色改变、技能改变、评估工程师的方式改变
  2. 没有通用剧本——必须根据每个组织的流程、内部工具和现有工作流定制
  3. 200 人 vs 2000 人工程组织——遇到的摩擦点不同
  4. 不能用无限 token 填补差距——工程始终不止是写代码
  5. 正确的对话——"不是哪个工具，而是谁和我们走完这段转型路"
