👥 Clients（客户端）

  • 通过 HTTP/gRPC 发送推理请求
  • 每个请求包含：Prompt、采样参数（temperature、max_tokens）
  • 支持流式输出（SSE/WebSocket）

🌐 API Server

  • 基于 ASGI（uvicorn + FastAPI）
  • 解析请求，构造 Sequence 对象，加入调度队列
  • 将输出 token 流式返回给客户端
  • 支持 OpenAI API 兼容接口

📋 Scheduler（调度器）

  • 每几毫秒"tick"一次，动态选择批次
  • 维护每个 Sequence 的 Block 表
  • 支持"抢占"：KV Cache 满时，挂起低优先级序列
  • 迭代级（iteration-level）调度，非请求级
  • 区分 Prefill 阶段（计算密集）和 Decode 阶段（内存密集）

🧱 Block Manager（PagedAttention）

  • 将 KV Cache 划分为固定大小的 Block（默认 16 tokens/block）
  • 维护逻辑块→物理块的映射表（Block Table）
  • CPU 侧管理分配，GPU 侧存储数据
  • 支持跨序列共享物理块（Prefix Caching）
  • Block 粒度分配，消除内存碎片

🎮 Model Runner（GPU 执行层）

  • 执行模型的 forward pass
  • FlashAttention 融合内核，直接消费 Block 索引的 KV 数据
  • 支持 Tensor Parallelism（多 GPU）
  • 输出 logits → 采样 → 生成下一个 token
  • 结果返回 Scheduler 更新序列状态

PagedAttention 分页注意力

传统系统按序列预分配连续内存，浪费 60-80%。PagedAttention 以 16-token 块为单位按需分配，实现近零浪费。

🎯 核心思想

将每个序列的 KV Cache 切成固定大小的"页"（Block），像操作系统的虚拟内存分页一样管理。 不需要为每个序列预留连续的大块内存，按需分配、按页离散。

⚖️ 传统方式 vs PagedAttention

❌ 传统（连续分配）

  • 每个序列预分配 max_tokens 个 token 空间
  • 实际生成往往远小于上限
  • 大量"已用但空着"的内存被浪费
  • 内存碎片导致无法容纳更多并发序列
  • 浪费率：60-80%

✓ PagedAttention

  • 按实际使用的 token 数分配 Block
  • 物理块按需分配，块内有多少用多少
  • Block 可来自任意空闲位置
  • 序列之间共享系统 Prompt 的块
  • 浪费率：<4%

🔑 调度器核心机制

🔁

迭代级调度

每生成一个 token（一次迭代）就重新调度，而非请求级。短序列和长序列可以同时往前推进。

⚡

Continuous Batching

完成输出的序列离开批次，新请求立即加入。GPU 利用率始终保持高位，不像静态批处理有空闲等待。

⛔

抢占机制

KV Cache 满时，调度器挂起优先级最低的序列，释放其 Block 给新序列使用。恢复后可继续。

✂️

Chunked Prefill

长 Prompt 的预填充（Prefill）被拆成多个 chunk，分散到多个调度周期，避免单次大 Prefill 阻塞 Decode。

Continuous Batching 连续批处理

传统静态批处理：等一批序列全部完成才处理下一批 → GPU 空闲。连续批处理：完成即退出，有空位就加入新序列。

Prefill（提示计算） Decode（逐 token 生成） Wait（等待加入批次）

📊 关键指标对比

指标 静态批处理 连续批处理 (vLLM)
GPU 利用率 低（等待最慢序列） 高（始终有任务）
首 token 延迟 高（必须等一批凑齐） 低（新请求立即加入）
吞吐量 受限于最慢序列 2-4× 提升
尾部延迟 高（长序列拖慢短序列） 低（迭代级抢占）

请求生命周期交互讲解

点击"下一步"逐步了解一个请求从进入 vLLM 到返回输出的完整过程。

① 接收请求
客户端发送 HTTP POST 请求到 vLLM API Server，请求体包含 prompt 和采样参数。
POST /v1/chat/completions
{
  "model": "meta-llama/Llama-3.1-8B-Instruct",
  "messages": [
    {"role": "system", "content": "你是helpful助手"},
    {"role": "user", "content": "解释什么是PagedAttention"}
  ],
  "max_tokens": 512,
  "temperature": 0.7
}
✓ API Server 解析请求，创建 Sequence 对象
② 入队调度
Scheduler 将新 Sequence 加入等待队列。每次"tick"（几毫秒）决定哪些序列参与下一批次。
Scheduler 队列
Seq#1 等待中 Seq#2 等待中 Seq#3（刚到达）
调度策略：优先调度已经完成 Prefill 的序列（Decode 阶段），新到的 Prefill 序列可以稍后加入。
③ Block 分配
Block Manager 为序列的 KV Cache 分配物理 Block。若内存不足，Scheduler 抢占低优先级序列的 Block。
物理 Block 池（示例）:
#0 Seq#1
#1 Seq#1
#2 Seq#2
#3 Seq#3 ← 新分配
#4 Seq#3 ← 新分配
#5 空闲
#6 空闲
Block Table[Seq#3]: [3, 4, _, _, _, ...] → 逻辑块0→#3, 逻辑块1→#4
④ GPU 执行
Model Runner 在 GPU 上执行 forward pass。FlashAttention 内核通过 Block Table 索引访问 KV Cache，完成一次迭代（生成一个 token）。
Prefill 阶段

计算整个 prompt 的注意力。计算密集，单次运行时间长。

Decode 阶段

逐 token 生成，每次 forward 只处理 1 个新 token。内存密集。

FlashAttention(K, V, block_table=[3,4,...]) → next_token logits → sampling → token
⑤ 输出返回
采样得到的 token 加入序列，Sequence 状态更新。完成时序列移至输出队列，API Server 通过 SSE 流式返回给客户端。
Stream Output (SSE)
data: {"choices":[{"delta":{"content":"P"},"finish_reason":null}]}
data: {"choices":[{"delta":{"content":"aged"},"finish_reason":null}]}
data: {"choices":[{"delta":{"content":"Attention"},"finish_reason":null}]}
...
data: {"choices":[{"delta":{"content":""},"finish_reason":"stop"}]}
✓ Sequence 状态: running → finished，释放所有 Block
