核心技术：PagedAttention

  • • 受 OS 虚拟内存分页启发
  • • KV Cache 非连续存储，按需分配
  • • 消除传统方案的内存碎片
  • • 支持长达 22B token 的上下文

核心技术：Continuous Batching

  • • 动态 batching，不等 batch 结束
  • • 推理完成即刻退出，释放显存
  • • 吞吐量比静态 batching 高 10+ 倍
  • • 配合 iteration-level scheduling

核心技术：Tensor Parallelism

  • • 模型权重横向切分到多 GPU
  • • AllReduce 汇总各 GPU 结果
  • • 支持任意数量的 GPU（1/2/4/8…）
  • • 与 PagedAttention 协同调度

⚡ Prefill 执行流程（Iteration by Iteration）
STEP 1

输入编码 — Embedding Lookup

将输入 token 序列 [The, cat, sat, on, the, mat] 转换为 embedding 向量

H₀ = Embed(token_ids)  // [seq_len, hidden_dim]
STEP 2

Q / K / V 投影

通过线性层生成 Query、Key、Value 向量，用于注意力计算

Q = H · W_q,  K = H · W_k,  V = H · W_v
STEP 3

PagedAttention 前向计算

所有 6 个 token 的注意力分数并行计算，共享 KV Cache 写入

Attn(Q, K, V) = softmax(Q · K^T / √d) · V
STEP 4

KV Cache 填充 — Batch Write

一次性将 6 个 token 的 K、V 块写入 HBM，比逐个写入效率高得多

KV_cache["block_0"] ← [K₁..K₆, V₁..V₆]  // contiguous

Prefill 阶段

Prefill 是首个前向传播，处理整个输入 prompt，建立 KV Cache。

特点：

  • ✅ 计算密集型，适合并行
  • ✅ 所有 KV 一次性写入 Cache
  • ✅ 首 token 延迟（Time to First Token, TTFT）
  • ⚠️ prompt 越长，Prefill 越慢

关键技术：

  • FlashAttention — IO-aware 注意力
  • KV Cache 预填充策略
  • Chunked Prefill — 长 prompt 拆分
🔄 Autoregressive Decoding 循环
STEP 1

Token Embedding

新 token 转换为 embedding 向量，加上位置编码（RoPE 等）

H₇ = Embed(token_id=342) + PosEnc(7)
STEP 2

PagedAttention — Q₇ vs [K₁..K₇]

Query 只有当前 token，但 Key/Value 读取全部历史缓存，通过 block_table 映射

Q₇ · [K₁..K₂..K₃..K₄..K₅..K₆..K₇]^T
STEP 3

KV Cache Append

新 token 的 K₇, V₇ 通过 Scheduler 分配物理块，写入 HBM

block_table[7] = free_block_id  // allocate on demand
STEP 4

采样下一个 Token

通过 SamplingParams（temperature/top_p）采样下一个 token

next_token ~ Categorical(softmax(logits / T))

Decode 阶段

Decode 是逐 token 自回归生成，每个 step 只处理 1 个 token。

特点：

  • ⚠️ Memory Bound（内存密集）
  • 📖 大量 KV Cache 读取，少量计算
  • 🔗 依赖链长 → 生成慢
  • ⏱️ Time Per Output Token (TPOT)

性能瓶颈：

  • KV Cache 带宽（HBM）
  • PagedAttention block table lookup
  • 内存复制开销

Static Batching 问题

  • • 等所有请求到达才开始处理
  • • 短 prompt 等长 prompt 完成
  • • GPU 大量空闲等待
  • • 吞吐量为 Continuous 的 1/10

Continuous Batching 优势

  • • Iteration-level 调度
  • • 完成即退出（EVICT）
  • • 新请求随时加入（APPEND）
  • • Preemption 保障公平

Iteration-level Scheduling

  • • 每个 decode iteration 检查队列
  • • 完成 → 释放 KV Cache 块
  • • 空间足够 → 接纳新请求
  • • 空间不足 → Preempt（抢占）

Continuous Batching

也称 Iteration-level Batching，是 vLLM 吞吐量的核心保障。

与 Static Batching 的区别：

  • Static: batch 固定到所有请求结束
  • Continuous: 每个 token step 重新调度

关键操作：

  • APPEND — 新请求加入批次
  • EVICT — 完成请求退出
  • PREEMPT — 内存不足时抢占
  • SWAP — CPU/GPU 间 KV Cache 交换

OS 虚拟内存分页

操作系统用页表将虚拟地址映射到物理地址，按需分配，Page Fault 时再加载。PagedAttention 借鉴了这一思想。

传统方案

连续 KV Cache（碎片化）

每个序列的 KV 必须放在连续内存区域。序列长度不同 → 预留过长 → 大量浪费（Internal Fragmentation）。

Seq A: [K₁ K₂ K₃ ... K₁₆] ← contiguous, pre-allocated 32 slots
PagedAttention

非连续块映射（block_table）

序列逻辑上连续（v0, v1, v2...），物理上分散在不同的 16-token 块中。按需分配，无内部碎片。

Seq A: v[0..3]→p2, v[4..7]→p5, v[8..11]→p8, v[12..15]→p12
效果

KV Cache 利用率大幅提升

传统方案：~30-40% 利用率。PagedAttention：~60-80%。相同显存可支持 2-4x 更多并发请求。

PagedAttention

由 University of Washington & Meta 提出（2023），是 vLLM 的核心技术。

解决的问题：

  • 传统方案：连续内存分配 → 碎片化
  • 内存预留过长，浪费严重
  • 长上下文支持受限

工作原理：

  • block_size=16 tokens/block
  • block_table 虚拟→物理映射
  • GPU kernel 直接通过 table 寻址
  • Copy-on-write 支持 fork

实测收益：

  • 吞吐量提升 ~24x vs HuggingFace
  • 支持 22B+ token 上下文
  • KV Cache 利用率 >60%
