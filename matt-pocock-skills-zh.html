面向真实工程师的技能（Skills For Real Engineers）

Matt 每天用来做真实工程（而不是"氛围编码"vibe coding）的 agent 技能。

开发真实应用很难。GSD、BMAD、Spec-Kit 这类方法试图通过"接管流程"来帮忙，但这样做会夺走你的控制权，并让流程中的 bug 难以解决。

这些技能被设计得小巧、易于改造、可组合。它们与任何模型都能配合。它们建立在数十年的工程经验之上。随便改造它们，把它们变成你自己的，尽情享受。

如果你想跟上这些技能的更新，以及我新建的技能，可以加入我的 newsletter（已有约 6 万名开发者）：

订阅 Newsletter

安装（30 秒上手）

两条路，两种理念。Claude Code 插件 把整套技能作为受管、只读的捆绑包安装，我发布更新时它会自动更新——你是"订阅"而不是"分叉"。skills.sh 把可编辑的技能文件复制进你的项目，这样你可以改造它们、让它们成为你的。二选一——两个都装会让每个技能出现两遍。

1. 获取技能

Claude Code 
claude plugins install mattpocock-skills
或者在会话内： 
/plugin install mattpocock-skills
它在 Claude Code 的官方应用市场中，所以无需预先添加任何东西，更新会自动送达。
Codex 和其他 agent 
npx skills@latest add mattpocock/skills
挑选你想要的技能，以及要安装到哪些编码 agent 上。**安装器会让你选择带走哪些技能——请确保 `setup-matt-pocock-skills` 是其中之一。** Codex 原生插件在路线图上——见 [`.agents/adr/0002-ship-as-a-claude-code-plugin.md`](./.agents/adr/0002-ship-as-a-claude-code-plugin.md)。
喜欢折腾的人 在任何 agent（包括 Claude Code）上使用同一个安装器： 
npx skills@latest add mattpocock/skills
它把技能作为普通文件写入你的仓库，归你所有、可编辑。不会有任何东西在你背后悄悄更新；想拉取我的最新改动时用 `npx skills update`。

2. 运行 /setup-matt-pocock-skills

在你的 agent 里，对每个仓库运行一次。它会：

  • 询问你想用哪个问题跟踪器（GitHub、Linear 或本地文件）
  • 询问你在分类工单时给工单打什么标签（/triage 使用标签）
  • 询问你想把新建的文档保存在哪里

3. 搞定——可以开工了

这些技能为什么存在

我构建这些技能，是为了修复我在 Claude Code、Codex 和其他编码 agent 身上看到的常见失败模式。

#1：agent 没做我想做的事

"没人确切知道自己想要什么"

David Thomas & Andrew Hunt，《程序员修炼之道》

问题。软件开发中最常见的失败模式是"错位"（misalignment）。你以为开发懂你的意思，然后你看到他们构建出来的东西——你意识到它完全没理解你。

在 AI 时代这完全一样。你和 agent 之间存在沟通鸿沟。解决办法是一场拷问式追问（grilling session）——让 agent 就你要构建的东西向你提出详尽的问题。

解决办法是使用：

  • /grill-me —— 用于非代码用途
  • /grill-with-docs —— 与 /grill-me 相同，但附加更多好东西（见下文）

这是我人气最高的技能。它们帮你在开工前与 agent 对齐，并深入思考你正在做的改动。每次你想做改动时都用它们。

#2：agent 太啰嗦

有了统一的语言（ubiquitous language），开发者之间的对话和对代码的表达都源自同一个领域模型。

Eric Evans，《领域驱动设计》

问题：项目开始时，开发者和软件的委托方（领域专家）通常讲着不同的语言。

我在自己的 agent 身上也感受到同样的张力。agent 通常被丢进一个项目，要求它边干边猜行话。于是它用 20 个词表达 1 个词就能说清的事。

解决办法是共享语言。它是一份帮助 agent 解码项目行话的文档。

例子 这是来自我的 `course-video-manager` 仓库的一个 [`CONTEXT.md`](https://github.com/mattpocock/course-video-manager/blob/076a5a7a182db0fe1e62971dd7a68bcadf010f1c/CONTEXT.md) 示例。哪个更好读？ - **之前**："当一门课程某个章节里的一节课被'实体化'（即在文件系统里获得一个位置）时，会出现一个问题" - **之后**："物化级联（materialization cascade）有问题" 这种简洁性会在一个个会话中不断回报你。

这已内置于 /grill-with-docs。它是一场拷问式追问，但同时帮你与 AI 建立共享语言，并把难以解释的决策记录在 ADR 中。

很难解释它有多强大。它可能是这个仓库里最酷的技巧。试试看。

Tip

共享语言除了减少啰嗦，还有许多其他好处：

  • 变量、函数和文件被一致地命名，使用共享语言
  • 因此，agent 更容易导航代码库
  • agent 在思考上花费更少的 token，因为它能使用更简洁的语言

#3：代码跑不通

"永远迈小步、迈谨慎的步。反馈的速率就是你的速度上限。永远不要接手一个太大的任务。"

David Thomas & Andrew Hunt，《程序员修炼之道》

问题：假设你和 agent 已经对齐了要构建什么。当 agent 仍然产出垃圾时怎么办？

是时候看看你的反馈回路了。如果 agent 没有关于它产出的代码实际如何运行的反馈，它就是在盲飞。

解决办法：你需要常规的一系列反馈回路：静态类型、浏览器访问和自动化测试。

对于自动化测试，红-绿-重构（red-green-refactor）循环至关重要。也就是 agent 先写一个失败的测试，再修复测试。这能让 agent 获得持续一致的反馈水平，产出好得多的代码。

我构建了一个 /tdd 技能，可以插入任何项目。它鼓励红-绿-重构，并给 agent 大量关于什么算好测试、什么算坏测试的指导。

对于调试，我还构建了一个 /diagnosing-bugs 技能，把最佳调试实践包裹进一个纪律严明的循环，逐阶段设门禁。

#4：我们建了一坨泥球

"每天都要投资于系统的设计。"

Kent Beck，《解析极限编程》

"最好的模块是深的。它们让大量功能可以通过一个简单接口被访问。"

John Ousterhout，《软件设计哲学》

问题：大多数用 agent 构建的应用既复杂又难以变更。因为 agent 能极大加速编码，它们也加速了软件熵。代码库以前所未有的速度变得更复杂。

解决办法是一种对 AI 驱动开发的全新态度：关心代码的设计。

这被内置进这些技能的每一层：

  • /to-spec 在创建规格说明前，就你要触碰哪些模块向你提问

而关键的 /improve-codebase-architecture 会普查一个代码库、找出"加深"（deepening）的机会，并把候选清单交到你手上。我建议每几天在你的代码库上跑一次。它是一场普查，不是救援：在真正老旧的代码库上它会找到真正的候选，但它不会替你把泥球解开。

总结

软件工程的基本功比以往任何时候都重要。这些技能是我把这些基本功浓缩成可复现实践的最大努力，帮你交付你职业生涯中最好的应用。好好享用。

这些技能沿着一条轴区分——谁能调用它们。用户触发（User-invoked）的技能只有在你输入它们时才可触达（例如 /grill-me）；它们的职责是编排。模型触发（Model-invoked）的技能可以由你调用，也可以在任务匹配时由 agent 自动取用；它们承载可复用的纪律。一个用户触发的技能可以调用模型触发的技能，但绝不调用另一个用户触发的技能。

  • triage —— 让 issue 穿过一串分类角色的状态机。

  • setup-matt-pocock-skills —— 为工程技能配置本仓库（问题跟踪器、分类标签、领域文档布局）。在使用其他工程技能前，对每个仓库运行一次。
  • to-spec —— 把当前对话变成一份规格说明并发布到问题跟踪器。没有采访——只是综合你已经讨论过的内容。
  • to-tickets —— 把任何计划、规格说明或对话拆成一串"曳光弹"工单，每张声明其阻塞边——以文本形式写进本地文件，或作为真实跟踪器上的原生阻塞链接。
  • implement —— 构建规格说明或一叠工单所描述的工作，在预先商定的接缝处驱动 /tdd，并在提交前用 /code-review 收尾。
  • wayfinder —— 把一大块工作——超过单个 agent 会话能容纳的量——规划成问题跟踪器上的一张共享决策工单地图——逐个解决，直到通往目的地的道路清晰。

模型触发

  • prototype —— 构建一次性原型回答设计问题——对状态/逻辑问题用一个可分享的单一 HTML 文件，或从一条路由切换多个截然不同的 UI 变体。
  • diagnosing-bugs —— 针对疑难 bug 和性能回退的纪律化诊断循环：构建一个对这个 bug 变红的反馈回路 → 最小化 → 提出假设 → 插桩 → 修复 → 回归测试。
  • research —— 针对高可信一手来源调查一个问题，并把发现作为带引用的 Markdown 文件存进仓库，作为后台 agent 运行。
  • tdd —— 带红-绿-重构循环的测试驱动开发。一次一个垂直切片地构建功能或修复 bug。
  • domain-modeling —— 主动构建并锐化项目的领域模型——对照术语表质疑术语，用边界场景压测，并就地更新 CONTEXT.md 和 ADR。
  • codebase-design —— 设计深模块的共享纪律与词汇：小接口背后藏大量行为，置于干净的接缝处，并能透过该接口测试。
  • code-review —— 对自某个固定点以来的差异做双轴评审：标准（是否遵循仓库编码标准，外加 Fowler 坏味道基线？）和规格（是否忠实实现了来源 issue/规格？），以并行子 agent 运行，互不污染。
  • resolving-merge-conflicts —— 逐块处理进行中的 git 合并或变基冲突，按意图解决并追溯双方的一手来源，然后完成该操作——绝不 --abort。
  • wizard —— 生成一个交互式 bash 向导，引导人类完成只有他们能执行的步骤：供应基础设施、设置凭据或 CI 密钥、走一遍陌生的第三方面板，或执行一次性的迁移或切换。

词汇（Language）

问题跟踪器（Issue tracker）： 承载仓库 issue 的工具——GitHub Issues、Linear、本地 .scratch/ markdown 约定等。to-tickets、to-spec、triage 等技能读写它。 避免：backlog 管理器、backlog 后端、issue 宿主

Issue： 问题跟踪器内部一个被跟踪的独立工作单元——由 to-tickets 产出的一个 bug、任务、规格说明或切片。 避免：ticket（仅在引用外部系统确实称它们为 ticket 时使用，或用于决策工单——见下文）

决策工单（Decision ticket）： 一个 wayfinder 单元——wayfinder:map 的一个子 Issue，承载一个问题，其解决方式是一个决策，而不是一段待执行的构建切片。decision 这个限定词让它与实现工单区分开来；wayfinder 引入这个词，之后就用 "ticket"。

分类角色（Triage role）： 分类期间贴到 Issue 上的规范状态机标签（例如 needs-triage、ready-for-afk）。每个角色都通过 docs/agents/triage-labels.md 映射到问题跟踪器里的一个真实标签字符串。

关系（Relationships）

  • 一个问题跟踪器持有许多 Issue
  • 一个 Issue 同时携带一个分类角色
  • 一个决策工单是一个 Issue（wayfinder:map 的一个子项）

标记的歧义（Flagged ambiguities）

  • "backlog" 之前被用来同时指代承载 issue 的工具和其中的工作量主体——已解决：工具是问题跟踪器；"backlog" 不再作为领域术语使用。
  • "backlog backend"/"backlog manager"——已解决：合并进问题跟踪器。

name: ask-matt
description: Ask which skill or flow fits your situation. A router over the skills in this repo.
disable-model-invocation: true

Ask Matt（询问 Matt）

你记不住每一个技能，所以开口问。

一个流程（flow）是一条穿行于各技能之间的路径。大多数路径沿着一条主流程运行，两条接入坡道（on-ramp）汇入其中。其余的都是独立技能，或是在底层运行的词汇层。

主流程：想法 → 交付（idea → ship）

大多数工作走过的路线。你有一个想法，并希望把它构建出来。

  1. /grill-with-docs —— 通过访谈打磨想法。每当你在工作目录（working directory）中工作时，从这里开始：它是有状态的，会把学到的东西保留在 CONTEXT.md 和 ADR 中。（没有工作目录？用 /grill-me —— 见「独立技能」。两者运行的是同一个 /grilling 原语；grill-with-docs 会留下书面痕迹，因此在有仓库可留下痕迹时，它是两者中更好的那个。）
  2. 分支 —— 你能否在对话中解决每一个问题？ 如果某个问题需要可运行的答案（状态、业务逻辑、必须亲眼看过的 UI），就绕道原型，双向都用 /handoff 搭桥（原型生活在自己独立的目录里，这正是 /handoff 的用途 —— 见「阶段边界」）： - /handoff 交接出去，然后针对那个文件打开一个新的会话， - /prototype 用一次性代码回答问题， - 把学到的内容 /handoff 交接回来，并在原始想法线程中引用它。
  3. 分支 —— 这是需要多个会话的构建吗？ - 是 → /to-spec（把线程转化为规格说明），然后 /to-tickets 把它拆分成曳光弹工单，每张工单都声明其阻塞边界（blocking edges）。在本地跟踪器上，每个工单是 .scratch/<feature>/issues/ 下的一个文件，按「阻塞者优先」手工推进；在真实跟踪器上，边界变成原生阻塞链接，因此任何阻塞者已完成（blockers are done）的工单都可以被拾取 —— 逐张工单启动 /implement，每张之间用 /clear 清空上下文。每张工单都是自包含的，所以上一张的上下文可以丢弃。 - 否 → 就在当前上下文窗口中执行 /implement。

无论哪种方式，/implement 都会在内部驱动 /tdd 来构建每个 issue —— 一次一个红-绿切片 —— 然后在提交前用 /code-review 收尾：对 diff 做双轴审查（Standards 标准 + Spec 规格）。当你只是想测试先行地构建一个具体行为、而无需完整规格时，单独使用 /tdd；每当你想针对某个固定点（fixed point）审查分支或 PR 时，单独使用 /code-review。

上下文卫生（Context hygiene）

把第 1–3 步保持在一个连续不间断的上下文窗口中 —— 在 /to-tickets 完成之前不要压缩（compact）或清空 —— 这样拷问、规格和工单都建立在同一套思考之上。之后每个 /implement 都从工单出发、以全新状态开始。

这一点的上限是智能区（smart zone）：模型仍能清晰推理的窗口（在最新模型上约 150k token）。如果会话在 /to-tickets 之前逼近它，不要在降级状态下硬撑 —— 在最近的阶段边界处 /compact（压缩），然后继续（见「阶段边界」）。

接入坡道（On-ramps）

一种产生工作的起始情境，随后并入主流程。

  • Bug 和请求堆积 → /triage。它让 issue 在分类/分诊角色间流转，并产出 agent-ready（可直接交给 agent）的 issue，后续由 /implement 拾取。

分类/分诊只用于非你创建的 issue —— bug 报告、外部发来的功能请求、任何原始到达的内容。/to-tickets 产出的工单已经是 agent-ready 的，所以不要对它们做分类/分诊。

  • 有什么东西坏了 → /diagnosing-bugs。用于棘手的那类：第一眼看不透的 bug、间歇性 flake（偶发失败）、在两个已知良好状态之间悄悄溜进来的回归。在拥有紧致反馈回路（tight feedback loop）之前它拒绝空想 —— 一条已经能在这个 bug 上变红的命令 —— 然后用回归测试来修复。如果真正的结论是没有好的接缝能把 bug 锁住，它的事后复盘会交给 /improve-codebase-architecture。

  • 一块巨大而迷雾重重的工作 —— 绿地项目或超大的功能构建，单个会话装不下 → /wayfinder，这里最具认知负荷的流程。当从当下到目的地之间的路还不可见时，它在问题跟踪器上绘制一张共享地图（shared map），由决策工单（decision tickets）组成，并一次一个地解决它们 —— 产出的是决策，而非交付物 —— 直到迷雾被推后、道路清晰。/grill-with-docs 打磨的是你能在单个会话里握住的想法，而 wayfinder 面向的是你握不住的想法 —— 它更慢、更稠密，所以只把它留到这种场景，永远不要用于范围明确的特性。

当地图清晰后，它交接，而非构建：在 /to-spec 处并入主流程，后者把地图上相互关联的决策坍缩成可构建的计划，然后照常走 /to-tickets 和 /implement。把地图直接循环进 /implement 会跳过这次坍缩、丢掉相互关联的细节 —— 只有当工作确实很小的时候才直接去 /implement。

代码库健康（Codebase health）

不是功能开发 —— 是维护。

  • /improve-codebase-architecture —— 每当你有空就运行它，让代码库保持对 agent 友好、便于在其中操作。它浮现加深机会（deepening opportunities）；挑中一个_就产生了一个想法_，你可以把它带到主流程的 /grill-with-docs。它是发现候选者的勘察；/codebase-design（下面）是你设计选中者的工作台。

底层的词汇（Vocabulary underneath）

两个模型触发的参考技能，运行在其他技能之下 —— 各自是其词汇的唯一事实来源。当问题是词语而非流程时，直接使用它们；或者让上面的技能把它们拉进来。

  • /domain-modeling —— 打磨项目的领域语言：挑战一个模糊的术语，消解一个过载的词（"account" 承担了三份工作），把一个难以逆转的决策记录为 ADR。这是 /grill-with-docs 所驱动的主动修炼，用来让 CONTEXT.md 保持为一份干净的词汇表。
  • /codebase-design —— 深模块词汇（module 模块、interface 接口、depth 深度、seam 接缝、adapter 适配器、leverage 杠杆效应、locality 局部性），用于设计模块的形态：在干净的接缝处、小接口背后承载大量行为。/tdd 和 /improve-codebase-architecture 都讲这套语言。

阶段边界（Phase boundaries）

阶段（phase）是会话内的一块工作 —— 拷问、实现、QA。在两个阶段的边界处你有五个选项，在其中做出选择是整个地图中最模糊的决策：

  • Continue（继续） —— 原地不动。不费任何代价，不丢任何东西。
  • /clear —— 清空窗口，当这里的内容对下一步无关紧要时。
  • /handoff —— 写一个可移植的 markdown 文件。用途狭窄：只用于新工具链（harness）、新目录、同事，或在阶段中途派生一个旁支任务。它买到的是可移植性（portability）。
  • Subagent（子代理） —— 把一个范围紧凑的任务发送到它自己的窗口，并取回一份报告。
  • /compact —— 压缩这份上下文，并用它播种一个新会话。默认选项，位于决策树的底部，而不是最先够到的那个。

阅读 PHASE-BOUNDARIES.md 了解有序的决策树 —— 五个问题、每个分支背后的推理，以及为什么一手来源（primary source）的成本让 Continue（继续） 成为第一个需要排除的选项。要在边界处做决策；阶段中途，要么继续，要么把剩余部分拆给子代理。

独立技能（Standalone）

完全脱离主流程。

  • /grill-me —— 与 /grill-with-docs 相同的无情访谈，但无状态（stateless）：它本地不保存任何东西，也不构建 CONTEXT.md。当你不在工作目录中工作时使用它 —— 打磨一个计划、一个设计、一段写作，任何其下没有仓库的东西。如果你在工作目录中，改用 /grill-with-docs：它运行同样的访谈并留下书面痕迹，因此严格来说是更好的那个。
  • /grilling —— 访谈原语本身：轮次、前沿（frontier）、事实是 agent 的活而决策是你的。/grill-me 和 /grill-with-docs 是两个具名的入口，/triage、/wayfinder 和 /improve-codebase-architecture 都在内部运行它。只有当你想在没有任何包装的情况下获得访谈时，才直接使用它。
  • /resolving-merge-conflicts —— 逐块处理进行中的 merge 或 rebase 冲突，按意图解决 —— 追溯到每一侧的一手来源，而不是挑选代码行 —— 然后完成操作。它永远不会运行 --abort。独立且不在任何流程上：当你已经身在冲突中时使用它。
  • /prototype —— 一个小型、一次性的程序，回答一个设计问题：这个状态模型感觉对吗，或者这个 UI 应该长什么样。「一次性」是对代码编写方式的一种约束，而不是销毁它的承诺：答案会折进真实代码，原型本身则作为一手来源保存在 main 之外的一个 prototype/<name> 分支上，并由实现 issue 指向它。它是主流程第 2 步的绕道，但任何时候当设计问题难以在纸面上敲定时，都可以使用它。
  • /research —— 把阅读苦力委托给后台 agent：它针对一手来源调查一个问题，然后在仓库中留下一份带引用的 Markdown 文件。在它阅读时你可以继续工作。它产出的文件是可以在 /grill-with-docs 处带进主流程的东西 —— 研究滋养思考，而不是取代思考。
  • /to-questionnaire —— 当阻碍你的东西不在你脑中、也不在代码库里，而在别人那里时，它会为那个人写一份问卷来填写。它是 /grill-me 的镜像：它不是就主题访谈你，而是就发送访谈你 —— 发给谁、你需要拿回什么 —— 并把问题对准空白处。拿回来的内容是 /grill-with-docs 或 /to-spec 的素材。
  • /wizard —— 用于只有人类能完成的步骤：供应基础设施、设置凭据或 CI secrets、点击穿过一个陌生的第三方仪表盘、运行一次性的迁移或切换。它生成一个交互式 bash 脚本，打开每个 URL、捕获每个值、并把它们写入 .env 和 GitHub secrets —— 于是该流程不再需要你每次向 agent 重新解释。模型触发，所以 agent 一遇到只有你能通过的墙就会去够它。如果 agent 能自己做，它就该自己做；这是给真正有人在回路的场景。
  • /wait-what —— 针对一条没有落地的消息的纠正手段。在对话中途、任何其他技能内部使用它，agent 会用你缺失的上下文、用 CONTEXT.md 的词汇、以朴素的英文重新表述它刚说的话。它是在事后起效；/grill-with-docs 是事前的解药，因为早期商定的共享语言才是让行话根本不出现的原因。
  • /teach —— 在多个会话中学习一个概念，把当前目录用作有状态的工作空间。
  • /writing-for-agents —— 供编写 agent 消费的文档时参考：技能、AGENTS.md、被指向的文档。

阶段边界（Phase boundaries）

阶段（phase）是会话内的一块工作 —— 拷问、实现、QA。这个定义是刻意模糊的：一个阶段在你心想 "好了，这部分做完了" 时结束。

阶段边界（phase boundary）是两个阶段之间的空隙，也是这个决策唯一该出现的地方。阶段中途没有任何决策要做 —— 要么继续，要么把剩余工作拆给子代理。在阶段中途压缩会让 agent 丢掉思路。

五个选项

选项 作用
Continue（继续） 留在当前会话。完全没有上下文切换。
/clear 清空上下文窗口，从零开始。
/handoff 写一个可移植的 markdown 文件，并在任何地方用它播种会话。
Subagent（子代理） 把任务发送到它自己的上下文窗口，并取回一份报告。
/compact 压缩这份上下文，并用摘要播种一个新会话。

决策树（The tree）

在边界处自上而下地思考。第一个是胜出。

1. 你能在本次会话中继续吗？ 有两件事让答案为「是」：下一阶段需要把这一阶段当作一手来源，或者你还有足够的智能区（约 150k token）容纳下一阶段。拷问 → 实现是标准的「是」：实现想要逐字逐句的推理过程，而不是它的摘要。Continue 不费代价、也不丢东西，所以先排除它。

2. 这份上下文对接下来要做的事无关紧要吗？ 本次会话里的一切 —— 探索、决策、死胡同 —— 都可以丢弃吗？如果是，就 /clear。这是整个棋盘上最便宜的走法：不花时间，并还给你整个窗口。/clear 也不是终局 —— 旧会话仍然可恢复。

搞错这一步的代价是单向的。清掉一份相关的上下文，你就失去了你所构建之物背后的为什么，无论把 diff 回读多少遍都要不回来。

3. 你需要交接吗？ /handoff 用途狭窄。只在以下情况需要它：

  • 换到一个新工具链（harness）（Claude → Codex），
  • 移到一个新目录或新仓库，
  • 把工作交给一位同事，
  • 或在不脱轨的前提下，派生一个在阶段中途发现的旁支任务。

这份清单就是全部条款。/handoff 买到的是可移植性 —— 一份会移动的文件。如果没有任何东西在移动，你就不需要它。

4. 这个任务能在离开键盘（AFK）时完成吗？ 它的范围足够紧凑，可以在你离开键盘、无需引导的情况下运行吗？如果是，就把它发送给子代理，让本次会话保持原样。自动化审查是标准场景：agent 读 diff 并报告，期间不需要你。

5. 否则，/compact。 上下文相关、同一工具链、同一目录，且你需要保持在回路中 —— 决策树最终落在这里，而且经常落在这里。给它一条指令（/compact we're going to QA this area），让摘要保留下一阶段需要的东西。

/compact 是默认选项，不是最先够到的那个。它位于底部，因为它前面的四个问题都更便宜或更精确。从它入手的人的失败模式是：新会话对摘要压平的那个决策，自信地给出了错误的判断。

一手来源与二手来源（Primary and secondary sources）

除 Continue 外的每一步都会把一手来源变成二手来源 —— 把真实发生的会话替换成对它的摘要。这笔交易永远是同一副形状：

来源 信息 噪声 可活动空间
一手来源（Continue） 完整 很多 很小
二手来源（/compact、/handoff） 有损 较少 很大

这就是为什么问题 1 排在最前。只有当留下的代价大于节省的代价时，你才付出那点有损性。

这些都是判断力问题

这些问题不是客观的 —— 每个都含有个人的品味，同一个边界在不同日子里可能走向两个方向。价值在于按顺序提出它们，并且是在边界处提出，而不是在工作中途。

Triage（分类/分诊）

让项目问题跟踪器上的 issue 通过一个小型状态机流转，状态机由分类/分诊角色组成。

如果本仓库把外部 pull request 当作请求面（request surface）（见 issue-tracker 配置），分类/分诊也覆盖它们：PR 就是附带代码的 issue —— 同样的角色、同样的状态、同样的机器，只有少数标注为"针对 PR"的差异点。根据跟踪器配置，把裸 #42 解析为 issue 或 PR。

在分类/分诊期间，凡是发布到问题跟踪器的评论或 issue，必须以下列免责声明开头：

> *This was generated by AI during triage.*

参考文档

  • AGENT-BRIEF.md —— 如何撰写经久耐用的 agent brief（agent 简报）
  • OUT-OF-SCOPE.md —— .out-of-scope/ 知识库如何运作

角色

两个类别角色：

  • bug —— 有什么东西坏了
  • enhancement —— 新功能或改进

五个状态角色：

  • needs-triage —— 维护者需要评估
  • needs-info —— 等待报告者提供更多信息
  • ready-for-agent —— 规格齐全，可供离线（AFK）agent 直接使用
  • ready-for-human —— 需要人类实现
  • wontfix —— 不会处理

对于 PR，同样的状态对照附带代码来解读：ready-for-agent 意味着已附上 brief，agent 应在 diff 上采取下一步行动；ready-for-human 意味着可以交给人类合并了。

每个经过分类/分诊的 issue 都应恰好携带一个类别角色和一个状态角色。如果状态角色冲突，先标记出来，并在做任何其他事情之前询问维护者。

这些是规范角色名 —— 问题跟踪器中实际使用的标签字符串可能不同。映射应该已经提供给你了。如果没有，告诉用户运行 /setup-matt-pocock-skills。

状态转换：未打标签的 issue 通常先进入 needs-triage；从那里移动到 needs-info、ready-for-agent、ready-for-human 或 wontfix。报告者回复后，needs-info 回到 needs-triage。维护者随时可以推翻 —— 标记看起来不寻常的转换，并在继续之前先询问。

调用方式

维护者调用 /triage 并用自然语言描述他们的需求。解读请求并执行。示例：

  • "把需要我关注的东西都给我看看"
  • "我们看看 #42"（issue 或 PR）
  • "把 #42 移到 ready-for-agent"
  • "有哪些是 agent 可以拾取的？"

展示需要关注的内容

查询问题跟踪器，并按旧的在前排列，展示三个桶：

  1. 未打标签（Unlabeled） —— 从未分类/分诊过。
  2. needs-triage —— 评估进行中。
  3. needs-info 且自上次分类/分诊备注以来有报告者活动 —— 需要重新评估。

当 PR 在范围内时，把这些桶里的外部 PR 也包含进来，并在每行打上 [PR] 或 [issue] 标签。发现动作只浮现外部 PR（跟踪器配置定义谁算外部）—— 协作者进行中的 PR 不是分类/分诊的工作。这个过滤只用于发现；被明确点名的 PR 无论作者是谁，总是会做分类/分诊。

展示每个条目的数量和一行的摘要。让维护者来挑。

分类/分诊一个具体的 issue 或 PR

  1. 收集上下文。 阅读完整的 issue 或 PR（正文、评论、标签、作者、日期；对于 PR 还要读 diff）。解析任何先前的分类/分诊备注，以免重新问已解决的问题。使用项目的领域词汇表探索代码库，并尊重该区域内的 ADR。对照代码库运行两项检查：(a) 冗余 —— 按领域概念（而不只是请求的字面措辞）搜索已有实现，并报告你在哪里找过。如果找到，它就是一个已实现（already-implemented）的 wontfix（第 5 步）。(b) 先前被拒 —— 阅读 .out-of-scope/*.md，浮现任何与此请求相似的条目。

  2. 给出建议。 把你的类别与状态建议及理由告诉维护者，加上与请求相关的一段简明代码库概述 —— 包括它是否已经实现。等待指示。

  3. 核实主张。 在进行任何拷问之前，检查该主张是否站得住脚。对于 bug，按报告者的复现步骤复现它。对于 PR，确认 diff 确实做了它声称的事 —— checkout 它，运行相关测试或命令。报告发生了什么：已确认（附代码路径）、失败、或细节不足（一个强烈的 needs-info 信号）。已确认的核实能产出强得多的 agent brief。

  4. 拷问（如有必要）。 如果请求需要补充展开，调用两次 Skill 工具，分别用于 "grilling"（拷问）和 "domain-modeling"（领域建模）—— 一轮轮问题地把它拷问成型，在决策落定时即时打磨领域术语并更新 CONTEXT.md/ADR。

  5. 应用结果： - ready-for-agent —— 发布一条 agent brief 评论（AGENT-BRIEF.md）。 - ready-for-human —— 与 agent brief 相同的结构，但注明为什么不能委派（判断力事项、外部访问、设计决策、人工测试）。 - needs-info —— 发布分类/分诊备注（模板见下）。 - wontfix —— 关闭，评论内容取决于原因：

    • 已实现（Already implemented） —— 该改动已存在于代码库中。指出它所在的位置；不要写入 .out-of-scope/（那个知识库是为被拒的请求准备的，不是已构建的）。
    • 被拒（bug） —— 礼貌解释，然后关闭。
    • 被拒（enhancement） —— 写入 .out-of-scope/，从一条评论链接它，然后关闭（OUT-OF-SCOPE.md）。
    • needs-triage —— 应用该角色。如果有部分进展，可选地发一条评论。

快速状态覆盖

如果维护者说"把 #42 移到 ready-for-agent"，相信他们并直接应用该角色。确认你将要做什么（角色变更、评论、关闭），然后执行。跳过拷问。如果要在没有拷问会话的情况下移到 ready-for-agent，询问他们是否想写一份 agent brief。

撰写 Agent Brief（agent 简报）

agent brief 是当 issue 或 PR 移到 ready-for-agent 时，发布在 GitHub issue 或 PR 上的一条结构化评论。它是离线（AFK）agent 将据此工作的权威规格说明。原始正文和讨论只是上下文 —— agent brief 才是契约。

brief 说明agent 应该做什么，这会延伸覆盖两个表面：对于 issue，那是从零构建这个改动；对于 PR，那是在现有 diff 上还剩下什么要做 —— 完成它、补上缺口、回应评审意见。两种情形原则相同；下面 PR 的示例展示了差异。

原则

经久耐用优于精准

issue 可能在 ready-for-agent 上待上几天或几周。在此期间代码库会变化。写 brief 时要让它即使文件被重命名、移动或重构后依然有用。

  • 要做：描述接口、类型和行为契约
  • 要做：点名 agent 应该寻找或修改的具体类型、函数签名或配置形态
  • 不要做：引用文件路径 —— 它们会过时
  • 不要做：引用行号
  • 不要做：假设当前的实现结构会保持不变

行为导向，而非过程导向

描述系统应该做什么，而不是如何实现。agent 会重新探索代码库，自己做实现决策。

  • 好："SkillConfig 类型应接受一个可选的 schedule 字段，类型为 CronExpression"
  • 坏："打开 src/types/skill.ts，在第 42 行加一个 schedule 字段"
  • 好："当用户不带任何参数运行 /triage 时，他们应该看到一份需要关注的 issue 摘要"
  • 坏："在主 handler 函数里加一个 switch 语句"

完整的验收标准

agent 需要知道何时算做完。每份 agent brief 都必须有具体、可测试的验收标准。每条标准都应能独立验证。

  • 好："运行 gh issue list --label needs-triage 应返回已经过初始分类的 issue"
  • 坏："分类/分诊应该正常工作"

明确的边界

说明什么不在范围内。这能防止 agent 过度打磨或对相邻功能做臆测。

模板

## Agent Brief

**Category:** bug / enhancement
**Summary:** one-line description of what needs to happen

**Current behavior:**
Describe what happens now. For bugs, this is the broken behavior.
For enhancements, this is the status quo the feature builds on.

**Desired behavior:**
Describe what should happen after the agent's work is complete.
Be specific about edge cases and error conditions.

**Key interfaces:**
- `TypeName` — what needs to change and why
- `functionName()` return type — what it currently returns vs what it should return
- Config shape — any new configuration options needed

**Acceptance criteria:**
- [ ] Specific, testable criterion 1
- [ ] Specific, testable criterion 2
- [ ] Specific, testable criterion 3

**Out of scope:**
- Thing that should NOT be changed or addressed in this issue
- Adjacent feature that might seem related but is separate

## Agent Brief

**Category:** bug
**Summary:** Skill description truncation drops mid-word, producing broken output

**Current behavior:**
When a skill description exceeds 1024 characters, it is truncated at exactly
1024 characters regardless of word boundaries. This produces descriptions
that end mid-word (e.g. "Use when the user wants to confi").

**Desired behavior:**
Truncation should break at the last word boundary before 1024 characters
and append "..." to indicate truncation.

**Key interfaces:**
- The `SkillMetadata` type's `description` field — no type change needed,
  but the validation/processing logic that populates it needs to respect
  word boundaries
- Any function that reads SKILL.md frontmatter and extracts the description

**Acceptance criteria:**
- [ ] Descriptions under 1024 chars are unchanged
- [ ] Descriptions over 1024 chars are truncated at the last word boundary
      before 1024 chars
- [ ] Truncated descriptions end with "..."
- [ ] The total length including "..." does not exceed 1024 chars

**Out of scope:**
- Changing the 1024 char limit itself
- Multi-line description support

## Agent Brief

**Category:** enhancement
**Summary:** Add `.out-of-scope/` directory support for tracking rejected feature requests

**Current behavior:**
When a feature request is rejected, the issue is closed with a `wontfix` label
and a comment. There is no persistent record of the decision or reasoning.
Future similar requests require the maintainer to recall or search for the
prior discussion.

**Desired behavior:**
Rejected feature requests should be documented in `.out-of-scope/<concept>.md`
files that capture the decision, reasoning, and links to all issues that
requested the feature. When triaging new issues, these files should be
checked for matches.

**Key interfaces:**
- Markdown file format in `.out-of-scope/` — each file should have a
  `# Concept Name` heading, a `**Decision:**` line, a `**Reason:**` line,
  and a `**Prior requests:**` list with issue links
- The triage workflow should read all `.out-of-scope/*.md` files early
  and match incoming issues against them by concept similarity

**Acceptance criteria:**
- [ ] Closing a feature as wontfix creates/updates a file in `.out-of-scope/`
- [ ] The file includes the decision, reasoning, and link to the closed issue
- [ ] If a matching `.out-of-scope/` file already exists, the new issue is
      appended to its "Prior requests" list rather than creating a duplicate
- [ ] During triage, existing `.out-of-scope/` files are checked and surfaced
      when a new issue matches a prior rejection

**Out of scope:**
- Automated matching (human confirms the match)
- Reopening previously rejected features
- Bug reports (only enhancement rejections go to `.out-of-scope/`)

范围外知识库（Out-of-Scope Knowledge Base）

仓库中的 .out-of-scope/ 目录保存被拒功能请求的持久记录。它有两个用途：

  1. 机构记忆 —— 一个功能为什么被拒，这样当 issue 关闭时，理由不会丢失
  2. 去重 —— 当新 issue 与先前被拒的请求匹配时，技能可以浮现此前的决策，而不是重新辩论它

目录结构

.out-of-scope/
├── dark-mode.md
├── plugin-system.md
└── graphql-api.md

每个概念一个文件，而不是每个 issue 一个文件。请求同一件事的多个 issue 归并到同一个文件下。

文件格式

文件应该以轻松、可读的风格撰写 —— 更像一份简短的设计文档，而不是数据库条目。用段落、代码示例和范例让理由对第一次遇到它的人清晰且有用。

# Dark Mode

This project does not support dark mode or user-facing theming.

## Why this is out of scope

The rendering pipeline assumes a single color palette defined in
`ThemeConfig`. Supporting multiple themes would require:

- A theme context provider wrapping the entire component tree
- Per-component theme-aware style resolution
- A persistence layer for user theme preferences

This is a significant architectural change that doesn't align with the
project's focus on content authoring. Theming is a concern for downstream
consumers who embed or redistribute the output.

```ts
    // The current ThemeConfig interface is not designed for runtime switching:
    interface ThemeConfig {
      colors: ColorPalette; // single palette, resolved at build time
      fonts: FontStack;
    }
    ```

## Prior requests

- #42 — "Add dark mode support"
- #87 — "Night theme for accessibility"
- #134 — "Dark theme option"

文件命名

为概念使用一个简短、描述性的 kebab-case 名称：dark-mode.md、plugin-system.md、graphql-api.md。名称要足够可识别，让浏览目录的人不打开文件也能明白被拒的是什么。

撰写理由

理由应该有实质内容 —— 不是"我们不要这个"，而是为什么。好的理由会引用：

  • 项目范围或理念（"本项目聚焦于 X；主题化是下游关切"）
  • 技术约束（"支持这会需要 Y，这与我们的 Z 架构冲突"）
  • 战略决策（"我们选择用 A 而非 B，因为……"）

理由应该经久耐用。避免引用临时状况（"我们现在太忙了"）—— 那些不是真正的拒绝，而是推迟。

何时检查 .out-of-scope/

在分类/分诊期间（第 1 步：收集上下文），读取 .out-of-scope/ 中的所有文件。评估新 issue 时：

  • 检查该请求是否与某个现有的 out-of-scope 概念匹配
  • 匹配是按概念相似性，而不是关键词 —— "night theme" 匹配 dark-mode.md
  • 如果有匹配，浮现给维护者："这与 .out-of-scope/dark-mode.md 类似 —— 我们之前拒绝过这个，因为 [理由]。你还持同样的看法吗？"

维护者可以：

  • 确认 —— 新 issue 被追加到现有文件的"Prior requests"（先前请求）列表，然后关闭
  • 重新考虑 —— out-of-scope 文件被删除或更新，issue 走正常的分类/分诊流程
  • 不同意 —— 这些 issue 相关但不同，走正常分类/分诊流程

何时写入 .out-of-scope/

只有当enhancement（而非 bug）被 拒绝 为 wontfix 时。这同样适用于 enhancement 类 PR —— 被拒的 PR 也记录在这里，这样同样的请求不会作为全新代码再次出现。

当某个东西因为已经实现而被 wontfix 关闭时，不要写在这里。那是已构建的功能，不是被拒的；记录它会给去重检查投毒，制造虚假的拒绝。取而代之，关闭评论指出该功能已存在的位置。

流程：

  1. 维护者决定一个功能请求超出范围
  2. 检查是否已存在匹配的 .out-of-scope/ 文件
  3. 如果是：把新 issue 追加到"Prior requests"（先前请求）列表
  4. 如果否：用概念名、决策、理由和第一个先前请求创建新文件
  5. 在 issue 上发一条评论，解释决策并提及该 .out-of-scope/ 文件
  6. 用 wontfix 标签关闭 issue

更新或删除 out-of-scope 文件

如果维护者改变了对先前被拒概念的看法：

  • 删除该 .out-of-scope/ 文件
  • 技能不需要重开旧 issue —— 它们是历史记录
  • 触发重新考虑的新 issue 走正常分类/分诊流程

Improve Codebase Architecture（改进代码库架构）

浮现架构摩擦，并提出加深机会（deepening opportunities）—— 把浅模块改造成深模块的重构。目标是可测试性和 AI 可导航性。

这条命令_受_项目的领域模型_启发_，并建立在一套共享的设计词汇之上：

  • 调用 Skill 工具并传入 "codebase-design" 获取架构词汇（module 模块、interface 接口、depth 深度、seam 接缝、adapter 适配器、leverage 杠杆效应、locality 局部性）及其原则（删除测试、接口即测试面、"一个适配器是假想接缝，两个才是真接缝"）。在每条建议中严格使用这些术语 —— 不要漂移到 "component"、"service"、"API" 或 "boundary"。
  • CONTEXT.md 中的领域语言为好的接缝命名；docs/adr/ 中的 ADR 记录的是本命令不应重新辩论的决策。

流程

1. 探索

先定范围再扫描 —— YAGNI。 加深一个模块的收益在于让未来对它的修改更容易，所以要格外重视代码库中最近变动的部分。在查看之前先决定看哪里：

  • 如果用户指明了一个方向 —— 一个模块、一个子系统、一个痛点 —— 就采用它，并跳过下面的推断。
  • 否则，沿提交历史往回走一段距离（git log --oneline），找到代码库的热点 —— 反复出现的文件和区域 —— 让这些路径先吸引你的注意力。如果改动零散、没有清晰的热点，就把网撒大。

先阅读项目的领域词汇表（CONTEXT.md）和你要触碰区域内的任何 ADR。

然后生成一个子代理去走查代码库。不要遵循僵硬的启发式规则 —— 有机地探索，并记下你遭遇摩擦的地方：

  • 哪里理解一个概念需要在许多小模块之间来回跳？
  • 哪里模块是浅的 —— 接口几乎和实现一样复杂？
  • 哪里纯函数只是为了可测试性被抽出来，而真正的 bug 藏在它们被调用的方式里（没有局部性）？
  • 哪里紧耦合的模块在它们自己的接缝处泄漏？
  • 代码库的哪些部分未测试，或难以通过其当前接口测试？

对你怀疑是浅的东西应用删除测试（deletion test）：删除它会让复杂度集中，还是只是搬走它？"是，会集中"就是你要的信号。

2. 把候选者呈现为 HTML 报告

把一个自包含的 HTML 文件写入 OS 临时目录，这样不会在仓库里留下任何东西。从 $TMPDIR 解析临时目录，回退到 /tmp（Windows 上是 %TEMP%），并写入 <tmpdir>/architecture-review-<timestamp>.html，这样每次运行都得到一个新文件。为用户打开它 —— Linux 上 xdg-open <path>，macOS 上 open <path>，Windows 上 start <path> —— 并告诉他们绝对路径。

报告使用 CDN 的 Tailwind 做布局和样式，CDN 的 Mermaid 画图 —— 当图/流程/时序能可靠地传达结构时用它们。把 Mermaid 与手工 CSS/SVG 视觉混合使用 —— 当关系是图状时用 Mermaid（调用图、依赖、时序），当想要更编辑感的东西时用手工 div/SVG（质量图、横截面、折叠动画）。每个候选者都有一个前/后对比可视化。要视觉化。

为每个候选者渲染一张卡片，包含：

  • Files（文件） —— 涉及哪些文件/模块
  • Problem（问题） —— 当前架构为什么造成摩擦
  • Solution（方案） —— 会改变什么的平实英文描述
  • Benefits（收益） —— 用局部性和杠杆效应解释，以及测试会如何改进
  • Before / After diagram（前后对比图） —— 并排、手工绘制，说明浅与深
  • Recommendation strength（推荐强度） —— Strong（强）/ Worth exploring（值得探索）/ Speculative（推测性）之一，渲染为徽章

报告以 Top recommendation（首选推荐） 部分收尾：你会先处理哪个候选者，为什么。

领域用 CONTEXT.md 的词汇，架构用 /codebase-design 的词汇。 如果 CONTEXT.md 定义了 "Order"，就谈 "the Order intake module（Order 入口模块）" —— 不要说 "the FooBarHandler"，也不要说 "the Order service（Order 服务）"。

ADR 冲突：如果一个候选者与现有 ADR 矛盾，只有当摩擦真实到值得重开该 ADR 时才浮现它。在卡片中明确标注（例如一个警告框："contradicts ADR-0007 — but worth reopening because…"（与 ADR-0007 矛盾 —— 但值得重开，因为……））。不要列出 ADR 禁止的每一个理论重构。

完整的 HTML 骨架、图例模式和样式指导见 HTML-REPORT.md。

现在还不要提出接口。文件写好后，问用户："你想探索其中的哪一个？"

3. 拷问循环

用户选中一个候选者后，调用 Skill 工具并传入 "grilling"（拷问），与他们一起走决策树 —— 约束、依赖、加深后模块的形态、接缝后面是什么、哪些测试能存活。

副作用在决策结晶时即时发生 —— 调用 Skill 工具并传入 "domain-modeling"（领域建模），在推进过程中保持领域模型最新：

  • 把一个加深后的模块命名为 CONTEXT.md 中没有的概念？ 把这个术语加进 CONTEXT.md。如果文件不存在，惰性创建它。
  • 在对话中打磨一个模糊术语？ 就地更新 CONTEXT.md。
  • 用户带着一个有分量的理由拒绝了候选者？ 提议一份 ADR，措辞为："Want me to record this as an ADR so future architecture reviews don't re-suggest it?"（要不要我把它记录为 ADR，这样未来的架构评审就不会再推荐它？）只有当这个理由确实会被未来的探索者用来避免重复建议时，才提议 —— 跳过短暂的理由（"现在不值得"）和显而易见的理由。
  • 想为加深后的模块探索替代接口？ 调用 Skill 工具并传入 "codebase-design"，使用它的"设计两次"（design-it-twice）并行子代理模式。

页头

仓库名、日期和一个紧凑图例：实线框 = 模块，虚线 = 接缝，红箭头 = 泄漏，粗深色框 = 深模块。没有引言段 —— 直接进入候选者。

候选者卡片

图表承担主要分量。文字稀疏、平实，并毫不犹豫地使用词汇表术语（来自 /codebase-design 技能）。

每个候选者是一个 <article>：

  • Title（标题） —— 简短，点明这个加深（例如 "Collapse the Order intake pipeline"（折叠 Order 入口管线））。
  • Badge row（徽章行） —— 推荐强度（Strong = 祖母绿，Worth exploring = 琥珀色，Speculative = 石板灰），外加依赖类别的标签（in-process、local-substitutable、ports & adapters、mock）。
  • Files（文件） —— 等宽字体列表，font-mono text-sm。
  • Before / After diagram（前后对比图） —— 核心焦点。两列并排。模式见下。
  • Problem（问题） —— 一句话。哪里痛。
  • Solution（方案） —— 一句话。会改变什么。
  • Wins（收益） —— 要点，每条 ≤6 个词。例如 "Tests hit one interface"（测试命中一个接口）、"Pricing logic stops leaking"（定价逻辑不再泄漏）、"Delete 4 shallow wrappers"（删除 4 个浅包装）。
  • ADR callout（ADR 提示）（如适用）—— 琥珀色调盒子里的一行。

不要有解释段落。如果图表需要一段话来理解，就重画图表。

手工盒子与箭头（当 Mermaid 的布局跟你作对时）

模块用带边框和标签的 <div>。箭头用内联 SVG <line> 或 <path> 元素，绝对定位在一个相对容器上。当你想让"之后"图感觉像一个带粗边框的深模块、内部灰化时，用它 —— Mermaid 渲染不出那种重量感。

横截面（适合层叠的浅）

堆叠水平带（h-12 border-l-4）展示一个调用穿过的层。之前：6 层薄层，每层什么都不做。之后：1 条厚带，标注着合并后的职责。

质量图（适合"接口与实现一样宽"）

每个模块两个矩形 —— 一个表示接口表面积，一个表示实现。之前：接口矩形几乎与实现矩形一样高（浅）。之后：接口矩形短，实现矩形高（深）。

调用图折叠

之前：一棵函数调用树，渲染为嵌套盒子。之后：同一棵树折叠进一个盒子，现在内部化（now-internal）的调用在其中以淡化显示。

样式指导

  • 偏向编辑感，而不是企业仪表盘。慷慨的留白。标题可选衬线体（font-serif 搭配 stone/slate 效果很好）。
  • 克制用色：一个强调色（祖母绿或靛蓝）加红表示泄漏、琥珀表示警告。
  • 图表保持约 320px 高，让前后图舒服地并排、无需滚动。
  • 图内模块标签用 text-xs uppercase tracking-wider —— 它们应读起来像示意图，而不是 UI。
  • 唯一的脚本是 Tailwind CDN 和 Mermaid ESM 导入。报告其余部分都是静态的 —— 没有应用代码，除 Mermaid 自身的渲染外没有交互。

首选推荐部分

一张更大的卡片。候选者名、一句为什么、指向其卡片的锚链接。就这样。

语气

平实英文，简洁 —— 但架构名词和动词直接来自 /codebase-design 技能。简洁不是漂移的借口。

精确使用： module、interface、implementation、depth、deep、shallow、seam、adapter、leverage、locality。

永不替换为： component、service、unit（代替 module）· API、signature（代替 interface）· boundary（代替 seam）· layer、wrapper（当你想说的是 module 时）。

符合该风格的措辞：

  • "Order intake module is shallow — interface nearly matches the implementation."（Order 入口模块很浅 —— 接口几乎与实现相当。）
  • "Pricing leaks across the seam."（定价跨接缝泄漏。）
  • "Deepen: one interface, one place to test."（加深：一个接口，一处测试。）
  • "Two adapters justify the seam: HTTP in prod, in-memory in tests."（两个适配器为接缝正名：生产用 HTTP，测试用内存。）

Wins 要点用词汇表术语点出收益："locality: bugs concentrate in one module"（局部性：bug 集中在一个模块）、"leverage: one interface, N call sites"（杠杆效应：一个接口，N 个调用点）、"interface shrinks; implementation absorbs the wrappers"（接口收缩；实现吸收包装层）。不要写 "easier to maintain"（更易维护）或 "cleaner code"（更干净的代码）—— 这些术语不在词汇表里，配不上它们的位置。

不要含糊其辞、不要清嗓子、不要"it's worth noting that…"（值得一提的是……）。如果一句话能变成要点，就让它变成要点。如果一个要点能删掉，就删掉。如果一个术语不在 /codebase-design 词汇表里，在发明新词之前去拿一个在里面的。

流程

1. 探索

查看当前仓库，了解它的起始状态。读取已存在的任何东西；不要臆测：

  • git remote -v 和 .git/config —— 这是 GitHub 仓库吗？哪一个？

  • 仓库根部的 CONTEXT.md 和 CONTEXT-MAP.md
  • docs/adr/ 和任何 src/*/docs/adr/ 目录
  • docs/agents/ —— 本技能此前的输出是否已存在？
  • .scratch/ —— 表明本地 markdown issue 跟踪器约定已在使用的迹象

总结什么是已有的、什么是缺失的。然后按顺序处理各节 —— 一节、一个答案、再下一节。

本技能摄取当前对话上下文和代码库理解，产出一份规格说明。不要访谈用户 —— 只综合你已经知道的东西。

问题的解决方案，从用户视角出发。

一个长长的、编号的用户故事列表。每个用户故事应为如下格式：

  1. 作为<角色（actor）>，我想要<一个功能（feature）>，以便<收益（benefit）>

1. 作为手机银行客户，我想要看到我账户的余额，以便我能对我的支出做出更明智的决定

  • 将构建/修改的模块
  • 将被修改的模块的接口
  • 来自开发者的技术澄清
  • 架构决策
  • 模式变更
  • API 契约
  • 特定的交互

  • 哪些模块将被测试
  • 测试的先前范例（即代码库中相似类型的测试）

把任何计划、规格或对话拆解为一组曳光弹工单，每张工单都声明其阻塞边界——在本地是每个工单一个文件里的文字，在真实跟踪器上是原生阻塞链接。

以下内容来自 skills/engineering/to-tickets/SKILL.md：

name: to-tickets

disable-model-invocation: true

To Tickets（转为工单）

把一份计划、规格或对话拆解为一组工单（tickets）—— 曳光弹（tracer-bullet）垂直切片，每张声明阻塞它的工单。

问题跟踪器和分类/分诊标签词汇应该已经提供给你了。如果没有，告诉用户运行 /setup-matt-pocock-skills。

流程

1. 收集上下文

从对话上下文中已有的内容出发。如果用户传了一个引用（规格路径、issue 编号或 URL）作为参数，获取它并阅读其完整正文和评论。

2. 探索代码库（可选）

如果你还没探索代码库，做一次以理解代码的当前状态。工单标题和描述应使用项目的领域词汇表词汇，并尊重你触碰区域内的 ADR。

寻找预重构（prefactor）代码的机会，让实现更容易。"先把改动变容易，再做容易的改动。"

3. 起草垂直切片

把工作拆成曳光弹工单。

  • 每个切片都切出一条狭窄但完整的路径，穿过每一层（schema、API、UI、测试）—— 是垂直的，不是某一层的水平切片
  • 一个完成的切片能独立演示或验证
  • 每个切片的大小要能放进一个全新的上下文窗口
  • 任何预重构都应先做

给每张工单它的阻塞边界（blocking edges）—— 在它能开始之前必须完成的其它工单。没有阻塞者的工单可以立即开始。

宽泛重构是垂直切片的例外。 宽泛重构（wide refactor）是一种机械性的改动 —— 重命名一列、给一个共享符号改类型 —— 其爆炸半径（blast radius）横扫整个代码库，一次编辑就同时破坏成千上万个调用点，没有任何垂直切片能保持绿色。不要硬把它塞进曳光弹；把它编排为扩展–收缩（expand–contract）。先扩展：在旧形式旁边加上新形式，什么都不破坏。然后按爆炸半径分批量迁移调用点（按包、按目录），每批是它自己的工单，被扩展工单阻塞，批与批之间保持 CI 绿色，因为旧形式仍然存在。最后收缩：在所有调用者消失后删除旧形式，用一个被每个迁移批阻塞的工单。即使批次本身也无法单独保持绿色时，保留该序列，但让它们共享一个集成分支，所有批次都阻塞一个最终的"集成并验证"工单 —— 绿色只在那个工单上被承诺。

4. 询问用户

把提议的拆分呈现为编号列表。对每张工单展示：

  • Title（标题）：简短的描述性名称
  • Blocked by（阻塞者）：哪些其它工单（如有）必须先完成
  • What it delivers（它交付什么）：这张工单使其生效的端到端行为

问用户：

  • 粒度感觉对吗？（太粗 / 太细）
  • 阻塞边界正确吗 —— 每张工单是否只依赖真正门控它的工单？
  • 有没有工单该合并或进一步拆分？

迭代直到用户批准这个拆分。

5. 把工单发布到已配置的跟踪器

发布已批准的工单。如何发布取决于 /setup-matt-pocock-skills 配置的跟踪器 —— 工单本身无论哪种方式都一样，只有阻塞边界的形态不同：

  • 本地文件 → 在 .scratch/<feature-slug>/issues/<NN>-<slug>.md 下每张工单写一个文件，按依赖顺序从 01 开始编号（阻塞者在前）。每个文件的 "Blocked by" 列出它依赖的编号/标题。使用下面的每工单文件模板 —— 每张工单一个文件，绝不使用单个合并文件。
  • 真实问题跟踪器（GitHub、Linear 等） → 按依赖顺序（阻塞者在前）每张工单发布一个 issue，这样每张工单的阻塞边界可以引用真实标识符。平台有原生阻塞/子 issue 关系就用它；否则把每张工单的 "Blocked by" 设为阻塞它的 issue。应用 ready-for-agent 分类/分诊标签，除非另有指示 —— 这些工单生来就是 agent 可拾取的。

推进前沿（frontier）：任何阻塞者都完成的工单。对于纯粹的线性链，那就是从上到下。

不要关闭或修改任何父 issue。

wayfinder（指路者）

将一整个大块工作（超过单个 agent 会话所能容纳）规划为问题跟踪器上的一张共享决策工单地图，一次解决一张，直到通往目的地的路径清晰可见。

以下内容来自 skills/engineering/wayfinder/SKILL.md：

name: wayfinder
description: Plan a huge chunk of work — more than one agent session can hold — as a shared map of decision tickets on your issue tracker, and resolve them one at a time until the way to the destination is clear.
disable-model-invocation: true

一个模糊的想法来了 —— 大得超过单个 agent 会话，而且裹在迷雾里：从当下到目的地（destination）之间的路还不可见。寻路（wayfinding）就是找到那条路，而不是冲向目的地。本技能把这条路绘制为仓库问题跟踪器上的一张共享地图（shared map），然后一次一个地处理它的决策工单（decision tickets）—— 问题的解决是一个决策，而不是一段待执行的构建切片 —— 直到路线清晰。

目的地因事而异，而给它命名是绘图的第一个动作 —— 它塑造每一张工单。它可能是一份要交接并迭代的规格说明、一个要在规划开始前锁定的决策，或一个就地做出的改动，比如数据结构迁移。地图与领域无关 —— 工程工作、课程内容，凡契合此形态的都行。

规划，而非执行

wayfinder 默认是规划：每张工单解决一个决策，当地图上的路清晰时地图就完成了 —— 在有人去真正做那件事之前，再无任何待决定的东西。想做工作的冲动通常是信号，说明你已经到达地图的边缘，该交接了。一项工作可以在它的 Notes 中覆盖这一点 —— 把执行带进地图本身 —— 但除非如此，产出的是决策，而非交付物。

用名字引用

每张地图和工单都是一个 issue，所以它有一个名字 —— 它的标题。在人类阅读的一切里 —— 叙述、地图的 Decisions-so-far —— 用那个名字引用它，绝不只用裸 id、编号或 slug。一墙 #42, #43, #44 无法阅读；名字一眼可读。id 和 URL 不会消失 —— 名字包裹着它的链接 —— 但它们骑在名字_内部_，绝不取代它。

地图

地图是仓库问题跟踪器上的单个 issue，打了 wayfinder:map 标签 —— 规范的产物。它的工单是地图的子 issue。

地图是一个索引，不是仓库。它列出已做的决策，并指向承载其细节的工单；一个决策恰好存在于一个地方 —— 它的工单 —— 所以地图从不重述它，只概括它并链接它。

地图、它的子工单、阻塞和前沿查询物理上在哪里，是跟踪器特定的。 问题跟踪器应该已经提供给你了。如果没有，告诉用户运行 /setup-matt-pocock-skills。查阅跟踪器文档的"寻路操作"（Wayfinding operations）一节，了解_这个_仓库如何表达它们。如果没有提供跟踪器，默认用本地 markdown 跟踪器。

工单

每张工单都是地图的子 issue；跟踪器的 issue id 是它的身份。它的正文就是那个问题，大小适合一次 100K token 的 agent 会话：

## Question

<the decision or investigation this ticket resolves>

每张工单携带一个 wayfinder:<type> 标签 —— research、prototype、grilling、task 之一（见工单类型）。

一个会话通过把工单指派给主导地图的开发人员来认领它，先于任何工作，这样并发会话会跳过它。那个被指派者_就是_认领：一张打开、未指派的工单就是未认领的。

阻塞使用跟踪器的原生依赖关系 —— 这一点至关重要，因为它让前沿在跟踪器自己的 UI 里以_可视化_方式呈现，人类不用打开地图就能看到什么是可取的。只有缺少原生阻塞的跟踪器才回退到正文约定。当阻塞它的每张工单都关闭时，工单解除阻塞；前沿就是打开、未阻塞、未认领的子项 —— 已知世界的边缘。

答案不是正文的一部分 —— 它在解决时记录（见穿越地图）。解决工单时创建的资产从 issue 链接，而不是粘贴进去。

工单类型

每张工单要么是 HITL —— 人在回路（human in the loop），与一位为自己发声的人类_共同_工作 —— 要么是 AFK，由 agent 独自驱动。HITL 工单只能通过那种现场交流解决；agent 绝不代替人类的那一侧（一个回答自己问题的拷问 agent 已经破坏了这一点）。

  • Research（研究）（AFK）：阅读文档、第三方 API 或知识库等本地资源，浮现一个决策所等待的事实。由一个调用 Skill 工具并传入 "research" 的子代理解决。当需要当前工作目录之外的知识时使用。
  • Prototype（原型）（HITL）：通过做一个便宜、粗糙、具体的产物来供人回应，提高讨论的分辨率 —— 一个大纲、一个粗样、一个桩，或 UI/逻辑代码，通过调用 Skill 工具并传入 "prototype"。把原型链接为一项资产。当"它应该看起来什么样"或"它应该怎么表现"是关键问题时使用。
  • Grilling（拷问）（HITL）：对话。默认情形。总是调用两次 Skill 工具，分别用于 "grilling" 和 "domain-modeling"。
  • Task（任务）（HITL 或 AFK）：必须在能做出_决策_之前完成的体力工作 —— 无可决定、无可原型、无可研究，但讨论被它阻塞，直到做完。注册一个服务以便其 API 能被评判、供应访问权限、移动数据以便能看到它的形态。这是唯一一个_执行_而非决策的类型 —— 它靠解除一个决策的阻塞来赢得自己的位置，而不是靠交付目的地。agent 在能独自驱动的地方独自驱动（AFK）；否则它交给人类一份精确的清单（HITL）。当工作完成时解决；答案记录做了什么，以及后续工单依赖的任何结果事实（凭据位置、新 URL、行数）。

战争迷雾（Fog of war）

地图是_刻意_不完整的：不要绘制你还看不到的东西。在活跃工单之外是战争迷雾 —— 那些你看出要来、却还无法定下来的决策和调查的昏暗图景，因为它们悬在仍然开放的问题上。解决一张工单会清空它前方的迷雾，把现在可以具体化的东西升级为新的工单 —— 一次一张，直到通往目的地的路清晰、不再有工单。

地图的 Not yet specified（尚未明确）一节就是写下那个昏暗图景的地方：可疑的问题、以后要重访的区域。它是_朝向_目的地的未发现前沿 —— 这里的一切都在范围内，只是还不够锋利到能开票。视图允许多少就写得多松散或多完整；它兼作给协作者的路标，让他们读出这项工作的去向。

迷雾还是工单？ 检验标准是你现在能否精确陈述那个问题 —— _不是_你现在能否回答它。

  • 开票当问题已经锋利 —— 即使它被阻塞、你还不能对它行动。
  • 尚未明确当你还不能把它说得那么锋利。不要把迷雾预切成工单大小的块：它比工单粗，一片迷雾可能升级成几张工单，也可能一张都没有，一旦前沿到达它。

Not yet specified 排除已决定的东西（Decisions so far）、已是活跃工单的东西，以及范围外的东西（下一节）。

范围外（Out of scope）

迷雾只会朝_目的地_聚集。目的地固定了范围，所以超出它的工作就是范围外 —— 它不是迷雾，也不属于 Not yet specified。它在地图上有自己的一节 Out of scope：你有意识地排除了_这个_工作之外的工作。把它放在这里是范围，不是锋利度。

范围外的工作永远不会升级 —— 前沿在目的地停下 —— 所以只有当目的地被重新划定后它才会回归，而且是以一个全新工作的形式，不是恢复。

把某件事划为范围外是一个划定范围的动作，不是路线上的一个步骤。当一张已存在的工单结果落在目的地之外时 —— 绘图时错划进来，或由一次解决暴露 —— 就关闭它（一张关闭的工单明确地远离前沿），并在 Out of scope 一节留下一行：要点加它为什么在范围外，链接已关闭的工单。它不进入 Decisions so far，后者记录的是实际走过的路线 —— 一条范围边界不是上面的一个步骤。

调用方式

两种模式。无论哪种，一个会话绝不解决超过一张工单 —— 研究工单除外。

绘制地图

用户用一个模糊的想法调用。

  1. 为目的地命名。 调用两次 Skill 工具，分别用于 "grilling"（拷问）和 "domain-modeling"（领域建模），确定这张地图正在通向什么 —— 那份规格、那个决策或那个改动。目的地固定范围，所以先定它。
  2. 绘制前沿。 再次拷问，这次广度优先：横扫整个空间而不是在任何一条线上深挖，浮现开放的决策和现在可走的第一步。如果这没有浮现任何迷雾 —— 通往目的地的路已经清晰，整个旅程小得够一个会话 —— 你不需要地图。停下来，问用户想如何继续。
  3. 创建地图（标签 wayfinder:map）：Destination 和 Notes 填好，Decisions-so-far 为空，迷雾草拟进 Not yet specified。
  4. 创建你现在能明确的工单，作为地图的子 issue —— 然后用第二轮接线阻塞边界（issue 需要 id 才能相互引用）。接线把它们分类为前沿和被阻塞；一切你还不能明确的都留在迷雾里 —— Not yet specified 一节。
  5. 开火研究子代理。 对刚创建的每张 research 工单，起一个子代理调用 Skill 工具并传入 "research" 并行解决它，在一个一次性的 research/<name> 分支上捕获其发现，并带一个来自工单的上下文指针。
  6. 停下 —— 绘图是一个会话的工作；它手工解决不了任何东西。

穿越地图

用户用一张地图（URL 或编号）调用。一张工单是可选的 —— 没有的话，由你挑下一个决策，而不是用户。

  1. 加载地图 —— 低分辨率视图，不是每张工单的正文。
  2. 选择工单。如果用户点名了一张，就用它。否则按顺序取第一张前沿工单。认领它：在任何工作之前把它指派给自己。
  3. 解决它 —— 按需缩放：按需获取任何相关或已关闭工单的完整正文；为 ## Notes 块点名的任何技能调用 Skill 工具。拿不准时，调用两次 Skill 工具，分别用于 "grilling"（拷问）和 "domain-modeling"（领域建模）。
  4. 记录解决：把答案作为解决评论发布，关闭 issue，并向地图的 Decisions-so-far 追加一个上下文指针。
  5. 添加新浮现的工单（先创建再接线）；升级任何答案已使其可具体化的迷雾，从 Not yet specified 中清掉每个已升级的块，让它只作为新工单存在。如果答案揭示某张工单 —— 这张或另一张 —— 落在目的地之外，就把它划为范围外，而不是在路线上解决它。如果决策使地图的其他部分失效，更新或删除那些工单。

用户可能并行运行未阻塞的工单，所以要预期其他会话在并发编辑跟踪器。

工程 · 模型触发

Engineering（工程）—— 模型触发的技能

prototype（原型）

构建一个一次性原型（throwaway prototype）来回答设计问题：针对状态/逻辑用一个可分享的单一 HTML 文件，或针对 UI 生成几个可切换的变体。

name: prototype
description: Build a throwaway prototype to answer a design question. Use when the user wants to sanity-check whether a state model or logic feels right, or explore what a UI should look like.

Prototype（原型）

原型是用于回答某个问题的一次性代码（throwaway code）。问题决定了原型的形态。

Pick a branch（选择分支）

识别正在回答的是哪个问题——从用户的提示、周围的代码来判断，或如果用户就在旁边就直接询问：

  • "这个逻辑 / 状态模型感觉对吗？" → LOGIC.md。构建一个单一可分享的 HTML 文件——自由操作按钮（free-play buttons）加标签页式的引导演练（guided walkthroughs）——推动状态机遍历那些在纸面上难以推演的用例，而且非开发者也能上手操作。
  • "它应该长什么样？" → UI.md。在单一路由上生成几个截然不同的 UI 变体，可通过 URL 查询参数和一个浮动底部栏切换。

两个分支产出的产物截然不同——选错分支会浪费整个原型。如果问题确实模棱两可且联系不上用户，默认选择与周围代码更匹配的分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部写明这一假设。

Rules that apply to both（两个分支都适用的规则）

  1. 从第一天起就是一次性代码，并明确标注。 把原型代码放在它实际将被使用的位置附近（紧挨着它正在为其做原型的模块或页面），这样上下文一目了然——但命名要让随便一看的读者能看出它是原型而非生产代码。对一次性 UI 路由，遵循项目已有的路由约定，不要发明新的顶层结构。
  2. 零门槛运行。 UI 原型从项目任务运行器（task runner）中的一条命令启动——pnpm <name>、python <path>、bun <path> 等。逻辑演示是一个用户双击即可打开的单一 HTML 文件。无论哪种方式，启动时都不需要思考。
  3. 默认不做持久化。 状态保存在内存中。持久化恰恰是原型要_验证_的对象，而不是它应该依赖的东西。如果问题明确涉及数据库，就使用一个带清晰"PROTOTYPE — wipe me"（原型——请删除我）名称的临时数据库（scratch DB）或本地文件。
  4. 跳过打磨。 不写测试，不做超出"能让原型_跑起来_"范围的错误处理，不做抽象。目的是快速学到东西。
  5. 把状态展示出来。 每次操作之后（逻辑）或每次切换变体时（UI），打印或渲染完整的相关状态，让用户能看到什么变了。
  6. 完成后把成果归档。 把任何已验证的决策并入真实代码，然后把原型本身作为一手来源（primary source）归档：提交到一条一次性分支（throwaway branch）上，不要进 main，并在实现 issue 上留下指向该分支的上下文指针。同时把答案也归档——结论以及它所解决的问题——写入 issue 或一次提交。main 分支只保留已验证的决策。

附件文件：LOGIC.md

Logic Prototype（逻辑原型）

单个自包含的 HTML 文件——一个可分享的演示——让任何人通过点击按钮来驱动状态模型。当问题关乎业务逻辑、状态转换或数据形状时使用它——这类东西在纸面上看起来合理，只有当你用真实用例去推演它时才会感觉不对。

因为它只有一个文件、无需安装任何东西，你可以把它交给非开发者——设计师、产品经理、领域专家——让他们亲自感受这个模型。所以它要说他们的语言，而不是代码的语言。

When this is the right shape（何时这是正确的形态）

  • "我不确定这个状态机能不能处理 X 之后接 Y 的边界情况。"
  • "这个数据模型真的能让我表示……这种情况吗？"
  • "我想在动手写 API 之前先感受一下它应该长什么样。"
  • 任何"想按按钮、看状态变化"的场景。

如果问题是"它应该长什么样"——那就是错误的分支。用 UI.md。

Process（流程）

1. State the question（陈述问题）

在写代码之前，写下你要做原型的状态模型和问题。写一段话，放在演示的顶部（放在可见的介绍里，而不只是注释里）。一个答错了问题的逻辑原型是纯粹的浪费——把问题写明确，这样无论用户是现在看着你操作，还是之后不在场（AFK）时再回来看，它都可以被核查。

2. Isolate the logic in a portable module（把逻辑隔离在可移植的模块中）

把真正的逻辑——也就是正在回答问题的那部分——放进一个单独的 <script> 块里，写成一个小型、纯净的模块，以后可以整体提出来、放进真实代码库。它周围的页面是一次性的；这个模块不是。

正确的形态取决于问题：

  • 纯 reducer——(state, action) => state。当 action 是离散事件且状态是单一值时适用。
  • 状态机（state machine）——显式的状态与转换。当"现在哪些 action 是合法的"本身就是问题的一部分时适用。
  • 作用于普通数据类型的一小组纯函数。当没有隐含的当前状态、只有转换时适用。
  • 带清晰方法面（method surface）的类或模块——当逻辑确实持有持续的内部状态时。

选最贴合所问问题的形态，而不要选最容易接页面那种。保持纯净：不碰 DOM、不碰 document、没有按钮处理器伸进模块内部。页面调用它；没有任何东西反向流动。这正是让原型在自身寿命结束后依然有用的原因：一旦问题得到回答，经验证的 reducer / 状态机 / 函数集就能自己提升到真实模块中。

3. Build the shareable HTML file（构建可分享的 HTML 文件）

一个文件，纯 HTML/CSS/JS——无框架、无打包器、无服务器，所有内容内联，所以双击即可打开，也经得起被邮件传来传去。任何人都应该能通过打开它来运行它。

为非开发者而写。每个标签都用领域语言（domain language），而不是代码——按钮和状态读起来像业务，而不是像 reducer。用通俗的话解释正在发生什么。

用清晰的层级自上而下布局：

  1. 标题和一行说明——这个演示让你探索什么（第 1 步中的问题）。
  2. 当前状态——完整的相关状态，渲染成可读的面板（带标签的字段，而不是裸的 JSON 倾倒），每次点击后重新渲染，让变化可见。在有助于非开发者跟上时，指出刚刚发生了什么变化。
  3. 自由操作按钮——每个 action 一个按钮，随时可用，任何人都能以任意顺序戳模型。每次点击分派它的 action 并重新渲染状态。
  4. 引导演练——一组场景（scenario），每个标签页一个。每个标签页包含一段简短、通俗的场景描述——它搭建的情境以及要观察什么——下方是对应场景的按顺序排列的要按的按钮。每一步都是一个真实的按钮：点击它就执行该 action 并进入下一步。开始一个演练会重置到一个已知的初始状态，这样场景每次都按同样的方式运行。

选择那些能演示棘手用例的场景——快乐路径、一个刁钻的边界情况、一次对理应非法的操作的尝试——那些在纸面上难以推演的情况。

保持美观但有克制：干净的排版、充裕的间距、一个强调色。不要动画、不要噱头——没有任何与状态和按钮竞争注意力的东西。

4. Hand it over（交付）

把文件发给他们，或替他们打开。他们会在有空的时候点击演练和自由操作；有趣的时刻是当他们说"等等，这不应该可能"或"呃，我以为 X 会不一样"时——那些是_想法_里的 bug，而这正是全部的意义所在。如果他们想要新的 action 或新场景，就加进去。原型是会演化的。

5. Capture the answer and the prototype（归档答案与原型）

一旦原型回答了它的问，先归档答案，再按 SKILL 描述的方式归档原型。逻辑特化的映射：经验证的 reducer / 状态机 / 函数集提升进真实模块（决策，被吸收）；HTML 外壳随行到那条把原型作为一手来源保留的一次性分支——由于它是单个自包含文件，在那里的可重运行性（re-runnable）依然零门槛。

Anti-patterns（反模式）

  • 不要加测试。 需要测试的原型就不再是原型了。
  • 不要接真实数据库。 使用内存状态，除非问题专门关乎持久化。
  • 不要泛化。 不要"万一以后想支持 X 呢"。原型只回答一个问题。
  • 不要把逻辑和页面搅在一起。 如果纯净模块引用了 DOM、document 或按钮处理器，它就不再可移植了。让页面保持为包裹纯净模块的薄壳。
  • 不要用框架、打包器或服务器。 一个收件人双击的文件；React 应用或 dev server 会毁掉"可分享"。
  • 不要把 HTML 外壳发布到生产环境。 页面是为被人手动点击而优化的。它背后的逻辑模块才是值得保留的部分。

附件文件：UI.md

UI Prototype（UI 原型）

在单一路由上生成几个截然不同的 UI 变体，可通过浮动底部栏切换。用户在浏览器里来回切换变体，挑一个（或从每个里偷点东西），然后把其余扔掉。

如果问题关乎逻辑/状态而非外观——错误分支。用 LOGIC.md。

When this is the right shape（何时这是正确的形态）

  • "这个页面应该长什么样？"
  • "在拍板之前，我想看看这个仪表盘的几个选项。"
  • "给设置页面试一种不同的布局。"
  • 任何用户本来会花一天在脑子里从三个模糊的线框稿里挑一个的场合。

Two sub-shapes — strongly prefer sub-shape A（两种子形态——强烈优先子形态 A）

当 UI 原型贴着应用其余部分时（真实的 header、真实的 sidebar、真实的数据、真实的密度），它要容易评判得多。一条孤立的一次性路由是一个真空：每个变体在孤立状态里看起来都不错。只要有一个像样的现有页面能承载这些变体，就默认用子形态 A。只有当原型确实没有邻近的宿主时才用子形态 B。

Sub-shape A — adjustment to an existing page (preferred)（子形态 A——对现有页面的调整，首选）

路由已存在。变体在同一条路由上渲染，由 ?variant= URL 查询参数控制。现有的数据获取、参数和鉴权全部保留——只有渲染部分随变体切换。这是默认选择；除非有具体理由，否则选它。

如果原型针对的东西还没有页面、但天然应该住在某个页面里（仪表盘的新区块、设置屏幕的新卡片、现有流程中的新步骤）——那仍然是子形态 A。把变体挂载进宿主页面。

Sub-shape B — a new page (last resort)（子形态 B——新页面，最后手段）

只有当真被做原型的东西没有任何现有页面可以住进去时才用——例如一个全新的顶层界面，或一个无法嵌入任何合理位置的流程。

创建一条一次性路由，遵循项目已有的路由约定——不要发明新的顶层结构。命名要让人一眼看出是原型（例如在路径或文件名中包含 prototype 这个词）。用同样的 ?variant= 模式。

在承诺采用子形态 B 之前，做一次健全性检查：真的没有任何现有页面能承载它吗？一条空路由会掩盖那些有内容的路由才会暴露出来的设计问题。

两种子形态下的浮动底部栏完全相同。

Process（流程）

1. State the question and pick N（陈述问题并选定 N）

默认3 个变体。超过 5 个就不再是"截然不同"而开始变成噪音——以此封顶。

把计划写成一行的形式，放在原型的位置或文件顶部的注释里：

"Three variants of the settings page, switchable via ?variant=, on the existing /settings route." （"设置页面的三个变体，通过 ?variant= 切换，位于现有的 /settings 路由上。"）

无论用户是否在场反驳，这都成立。

2. Generate radically different variants（生成截然不同的变体）

起草每个变体。让每个都对照检查：

  • 页面的目的以及它能访问到的数据。
  • 项目的组件库/样式系统（TailwindCSS、shadcn、MUI、纯 CSS，随便什么）。
  • 清晰的导出组件名，例如 VariantA、VariantB、VariantC。

变体必须在结构上不同——布局不同、信息层级不同、主操作（primary affordance）不同，而不只是颜色不同。三个微调过的卡片网格不是 UI 原型，而是墙纸。如果两个草稿太相似，就用显式"不要用卡片网格"的指示重做其中一个。

3. Wire them together（把它们接起来）

在路由上创建一个切换组件（switcher component）：

// pseudo-code — adapt to the project's framework
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);

对于子形态 A（现有页面）：把所有现有数据获取保留在切换器之上；只有被渲染的子树随变体变化。

对于子形态 B（新页面）：位于 /prototype/<name> 下的一次性路由挂载同一个切换器。

4. Build the floating switcher（构建浮动切换器）

屏幕底部居中的一个小的固定定位条，包含三件东西：

  • 左箭头——循环到前一个变体（回绕）。
  • 变体标签——显示当前变体键，如果变体导出了名称，也显示那个名称。例如 B — Sidebar layout（B——侧边栏布局）。
  • 右箭头——循环到下一个（回绕）。

行为：

  • 点击箭头更新 URL 查询参数（用框架的路由器——Next 上用 router.replace、React Router 上用 navigate 等），这样变体可分享、刷新后依然稳定。
  • 键盘：← 和 → 方向键也可以循环。当 <input>、<textarea> 或 [contenteditable] 获得焦点时不要拦截方向键。
  • 视觉上与页面区分（例如高对比度的胶囊形、微妙的阴影），让人明显看出它不属于被评估的设计的一部分。
  • 在生产构建中隐藏——用 process.env.NODE_ENV !== 'production' 或等价检查门控，这样一次误合并原型也不会把这条栏发布给用户。

把切换器放进一个共享组件，让两种子形态都能复用。放在项目共享 UI 所在的位置。

5. Hand it over（交付）

展示出 URL（以及 ?variant= 键）。用户会在有空时来回切换。有趣的反馈通常是"我想要 B 的 header 配 C 的侧边栏"——那才是他们真正想要的设计。

6. Capture the answer and clean up（归档答案并清理）

一旦某个变体胜出，先归档答案——哪个变体以及为什么——再按 SKILL 描述的方式归档原型。把胜者并入真实代码，其余放到一次性分支，而不是 main：

  • 子形态 A——把胜者并入现有页面；把落败的变体和切换器从 main 移除。
  • 子形态 B——把胜出的变体提升为正式路由；把一次性路由和切换器从 main 移除。

完整的变体集合就是一手来源，所以它进入一次性分支而不是垃圾桶——留在 main 分支的变体组件和切换器会很快腐烂，并让下一个读者困惑。

Anti-patterns（反模式）

  • 变体之间只有颜色或文案不同。 那是微调，不是原型。真正的变体在结构上分歧。
  • 变体之间共享太多代码。 共享 <Header> 没问题；共享 <Layout> 就破坏了目的。每个变体都应该有自由抛弃布局的空间。
  • 把变体接上真实的写操作（mutation）。 只读原型没问题。如果某个变体需要变更数据，把它指向一个桩（stub）——问题是"它应该长什么样"，而不是"后端能不能工作"。
  • 直接把原型提升到生产环境。 变体代码是在原型的约束下写的（没有测试、错误处理极少）。并入时要正确地重写它。

diagnosing-bugs（问题诊断）

对疑难 bug 和性能回归的纪律化诊断回路：构建一个能在该 bug 上变红的反馈回路 → 最小化 → 提出假设 → 插桩 → 修复 → 回归测试。

name: diagnosing-bugs
description: Diagnosis loop for hard bugs and performance regressions. Use when the user says "diagnose"/"debug this", or reports something broken/throwing/failing/slow.

Diagnosing Bugs（问题诊断）

针对疑难 bug 的一套纪律。只有在有明确理由时才跳过阶段。

在探索代码库时，阅读 CONTEXT.md（如果存在）以获取相关模块的清晰心智模型，并检查你正在触碰的区域的 ADR。

Redact（脱敏）

这个技能要求你展示命令、输出和捕获的产物。先脱敏每一个秘密——在其位置写上 <REDACTED>。针对环境变量构建循环，让凭据留在环境中而不是留在你所展示的内容里。捕获的产物带有鉴权请求头：只引用那些携带信号的几行。

如果脱敏后的输出不足以诊断 bug，就说出来并询问用户。

Phase 1 — Build a feedback loop（阶段 1——构建反馈回路）

这才是这个技能的核心。 其他一切都是机械性的。如果你对这个 bug 有一条紧的通过/失败信号——一条能在_这个_ bug 上变红的信号——你就能找到根因；二分、假设检验和插桩都只是消费它。如果你没有，再多地盯着代码也救不了你。

在此投入不成比例的努力。要激进。要有创造力。拒绝放弃。

Ways to construct one — try them in roughly this order（构建反馈回路的方法——大致按这个顺序尝试）

  1. 失败的测试——在能触达 bug 的任何接缝上：单元、集成、端到端。
  2. 针对正在运行的 dev server 的 curl / HTTP 脚本。
  3. 带 fixture 输入的 CLI 调用，把 stdout 与已知正确的快照（known-good snapshot）做 diff。
  4. 无头浏览器脚本（Playwright / Puppeteer）——驱动 UI，对 DOM/控制台/网络做断言。
  5. 重放捕获的 trace。 把真实的网络请求/载荷/事件日志存到磁盘；在隔离环境中沿代码路径重放它。
  6. 一次性测试台（throwaway harness）。 拉起系统的一个最小子集（一个服务、模拟的依赖），用单次函数调用去行使 bug 代码路径。
  7. 性质/模糊测试回路（property / fuzz loop）。 如果 bug 是"有时输出错误"，跑 1000 个随机输入，寻找失败模式。
  8. 二分测试台（bisection harness）。 如果 bug 出现在两个已知状态（提交、数据集、版本）之间，把"启动到状态 X、检查、重复"自动化，这样你就能 git bisect run 它。
  9. 差分回路（differential loop）。 把同一输入分别跑过旧版本 vs 新版本（或两种配置），并对 diff 输出。
  10. 人机协作 bash 脚本（HITL）。最后手段。如果必须由人类点击，用 scripts/hitl-loop.template.sh 驱动_他们_，让回路仍然是有结构的。捕获的输出反馈给你。

构建正确的反馈回路，bug 就 90% 修好了。

Tighten the loop（收紧回路）

把回路当作产品来对待。一旦你有了_一条_回路，就收紧它：

  • 能更快吗？（缓存设置、跳过无关的初始化、收窄测试范围。）
  • 信号能更锐利吗？（断言具体的症状，而不是"没崩溃"。）
  • 能更确定吗？（固定时间、播种随机数、隔离文件系统、冻结网络。）

一条 30 秒的偶发回路比没有回路好不了多少；一条 2 秒的确定性回路是紧的——那是调试的超能力。

Non-deterministic bugs（非确定性 bug）

目标不是干净的复现，而是更高的复现率。把触发器循环 100 次、并行化、加压、收窄时间窗口、注入 sleep。50% 概率复现的 bug 是可调试的；1% 不是——不断提高复现率直到它可调试。

When you genuinely cannot build a loop（当你确实构建不出回路时）

停下并明确说出来。列出你试过的东西。向用户索要：(a) 能复现它的环境的访问权，(b) 脱敏的捕获产物（HAR 文件、日志转储、核心转储、带时间戳的屏幕录制），或 (c) 添加临时生产插桩的许可。不要在没有回路的情况下继续提出假设。

Completion criterion — a tight loop that goes red（完成判据——一条会变红的紧回路）

当回路紧且能变红（red-capable）时，阶段 1 才算完成：你能说出一条命令——一个脚本路径、一次测试调用、一条 curl——你已经实际运行过至少一次（展示调用及其输出，脱敏后），并且它：

  • [ ] 能变红（Red-capable）——它驱动实际的 bug 代码路径，并断言用户的确切症状，所以它能在这个 bug 上变红、修复后变绿。不是"运行不报错"——它必须能_抓住这个具体的 bug_。
  • [ ] 确定性（Deterministic）——每次运行结论一致（对偶发 bug：固定的、高复现率，见上文）。
  • [ ] 快（Fast）——秒级，而不是分钟级。
  • [ ] agent 可运行（Agent-runnable）——你能无人值守地运行它；人只能通过 scripts/hitl-loop.template.sh 在回路中。

如果你发现自己在上述命令存在之前就开始读代码、构建理论，停下——直接跳到假设正是这个技能要阻止的确切失败。 没有能变红的命令，就没有阶段 2。

Phase 2 — Reproduce + minimise（阶段 2——复现 + 最小化）

运行回路。看着它变红——bug 出现了。

确认：

  • [ ] 回路产生的是用户描述的失败模式——而不是恰好旁边的另一个失败。错的 bug = 错的修复。
  • [ ] 失败在多次运行中可复现（或对非确定性 bug，能以足够高的频率复现以便调试）。
  • [ ] 你已捕获确切症状（错误消息、错误输出、慢的计时），以便后续阶段能验证修复确实解决了它。

Minimise（最小化）

一旦变红，把复现缩小到仍然会变红的最小场景。一次一个地削减输入、调用方、配置、数据和步骤，每次削减后重跑回路——只保留对失败承重的部分。

为什么要费这个劲：最小复现缩小了阶段 3 的假设空间（剩下可怀疑的动件更少），并成为阶段 5 中干净的回归测试。

当剩下的每个元素都是承重的时才算完成——移除任何一个都会让回路变绿。

在既已复现又已最小化之前不要继续。

Phase 3 — Hypothesise（阶段 3——提出假设）

在测试任何一个之前，生成3–5 个排序的假设。单假设生成会锚定在第一个貌似合理的想法上。

每个假设必须可证伪（falsifiable）：陈述它所做的预测。

格式："如果 是根因，那么 <改变 Y> 会让 bug 消失 / <改变 Z> 会让它更糟。"

如果你说不清预测，这个假设就是一种感觉（vibe）——丢弃或磨利它。

在测试之前把排序列表展示给用户。 他们往往拥有能瞬间重新排序的领域知识（"我们刚部署了一个针对 #3 的改动"），或知道他们已经排除掉的假设。这是廉价的检查点，能省大量时间。不要阻塞在它上面——如果用户不在场，就按你的排序继续。

Phase 4 — Instrument（阶段 4——插桩）

每个探针都必须对应阶段 3 中的一个具体预测。一次只改变一个变量。

工具偏好：

  1. 调试器 / REPL 检查——如果环境支持。一个断点胜过十条日志。
  2. 在能区分假设的边界处做针对性日志。
  3. 永远不要"记全部日志再 grep"。

给每条调试日志打上唯一前缀标签，例如 [DEBUG-a4f2]。最后的清理变成一次 grep。未打标签的日志存活；打标签的日志消亡。

性能分支。 对性能回归，日志通常是错的。改用：建立一个基线测量（计时测试台、performance.now()、profiler、查询计划），然后二分。先测量，后修复。

Phase 5 — Fix + regression test（阶段 5——修复 + 回归测试）

在修复之前写回归测试——但前提是存在正确的接缝。

正确的接缝是指测试在调用点实际发生的位置行使真实的 bug 模式。如果唯一可用的接缝太浅（bug 需要多个调用方时只有单调用方测试、无法复现触发 bug 的链条的单元测试），那里的回归测试会给出虚假的信心。

如果不存在正确的接缝，这本身就是发现。 记下它。代码库架构正在阻止这个 bug 被锁死。把它标记给下一阶段。

如果存在正确的接缝：

  1. 把最小化的复现变成那个接缝上的失败测试。
  2. 看着它失败。
  3. 应用修复。
  4. 看着它通过。
  5. 针对原始的（未最小化的）场景重跑阶段 1 的反馈回路。

Phase 6 — Cleanup（阶段 6——清理）

宣布完成前必须做到：

  • [ ] 原始复现不再复现（重跑阶段 1 回路）
  • [ ] 回归测试通过（或不存在接缝已记录在案）
  • [ ] 所有 [DEBUG-...] 插桩已移除（用 grep 搜前缀）
  • [ ] 一次性原型已删除（或移到明确标记的调试位置）
  • [ ] 最终证明正确的假设写在提交/PR 消息中——让下一个调试者学到

Research（研究）

它的工作：

tdd（测试驱动开发）

红绿重构回路的测试驱动开发。一次一个垂直切片地构建功能或修复 bug。

name: tdd
description: Test-driven development. Use when the user wants to build features or fix bugs test-first, mentions "red-green-refactor", or wants integration tests.

Test-Driven Development（测试驱动开发）

TDD 就是红 → 绿回路。这个技能是让那条回路产出值得保留的测试的参考：好测试是什么样的、测试放在哪里、反模式、以及回路的规则。每个小节在每个周期都适用——在回路期间及之前都要查阅它们，而不是之后。

在探索代码库时，阅读 CONTEXT.md（如果存在），让测试命名和接口词汇与项目的领域语言一致，并尊重你正在触碰区域的 ADR。

What a good test is（好测试是什么样的）

测试透过公共接口验证行为，而不是实现细节。代码可以彻底改变；测试不应该。一条好测试读起来像一份规范——"user can checkout with valid cart"（用户可以用有效购物车结账）精确地告诉你存在什么能力——而且能安然度过重构，因为它不在乎内部结构。

参见 tests.md 的示例和 mocking.md 的模拟指南。

Seams — where tests go（接缝——测试放在哪里）

接缝（seam）是你测试所在的公共边界：那个无需伸进内部就能观察行为的接口。测试住在接缝上，绝不对着内部。

只在预先约定的接缝上测试。 在写任何测试之前，写下被测的接缝并与用户确认。不在未经确认的接缝上写测试。你不可能测所有东西——事先约定接缝，正是让测试投入落在关键路径和复杂逻辑上、而不是每一个边界情况上的方法。

问："公共接口是什么，我们应该测哪些接缝？"

当那个接口的形态本身就是问题所在时——模块有多深、接缝该放哪里、接口该暴露什么——调用 Skill 工具并带上 "codebase-design"，获取那套词汇。它是 module、interface、depth、seam、adapter、leverage 和 locality 这些术语的共同来源，是一份参考文档，而不是要运行的一次会话。

Anti-patterns（反模式）

  • 实现耦合（implementation-coupled）——模拟内部协作者、测试私有方法，或透过旁路渠道验证（查询数据库而不是用接口）。特征：你重构时测试就挂了，但行为并没有变。
  • 同义反复（tautological）——断言用与代码相同的方式重算期望值（expect(add(a, b)).toBe(a + b)、以同样方式手工推导出的快照、断言一个常量等于它自己），所以它靠构造就通过，永远无法与代码产生分歧。期望值必须来自独立的事实来源——一个已知正确的字面量、一个手算示例、一份规范。
  • 水平切片（horizontal slicing）——先写全部测试，再写全部实现。批量测试验证的是_想象出来的_行为：你测试的是东西的_形状_而不是面向用户的行为，测试对真实变化不敏感，而且你在理解实现之前就承诺了测试结构。改为按垂直切片（vertical slices）工作——一个测试 → 一个实现 → 重复，每个测试都是一颗曳光弹（tracer bullet），回应上一个周期教给你的东西。

Rules of the loop（回路的规则）

  • 先红后绿。 先写失败的测试，然后只写足够让它通过的代码。不要预期未来的测试，也不要加投机性的功能。
  • 一次一片。 每个周期一个接缝、一个测试、一个最小实现。
  • 重构不是回路的一部分。 它属于评审阶段（参见 code-review 技能），不属于红 → 绿实现周期。

Good and Bad Tests（好测试与坏测试）

Good Tests（好测试）

集成风格（Integration-style）：透过真实接口测试，而不是模拟内部部件。

// GOOD: Tests observable behavior
test("user can checkout with valid cart", async () => {
  const cart = createCart();
  cart.add(product);
  const result = await checkout(cart, paymentMethod);
  expect(result.status).toBe("confirmed");
});

特征：

  • 测试用户/调用方在乎的行为
  • 只用公共 API
  • 能安然度过内部重构
  • 描述 WHAT（做什么），而不是 HOW（怎么做）
  • 每个测试一个逻辑断言

Bad Tests（坏测试）

实现细节测试（Implementation-detail tests）：耦合到内部结构。

// BAD: Tests implementation details
test("checkout calls paymentService.process", async () => {
  const mockPayment = jest.mock(paymentService);
  await checkout(cart, payment);
  expect(mockPayment.process).toHaveBeenCalledWith(cart.total);
});

危险信号（Red flags）：

  • 模拟内部协作者
  • 测试私有方法
  • 对调用次数/顺序做断言
  • 行为没变时重构导致测试挂掉
  • 测试名描述 HOW 而不是 WHAT
  • 透过外部手段验证而不是透过接口
// BAD: Bypasses interface to verify
test("createUser saves to database", async () => {
  await createUser({ name: "Alice" });
  const row = await db.query("SELECT * FROM users WHERE name = ?", ["Alice"]);
  expect(row).toBeDefined();
});

// GOOD: Verifies through interface
test("createUser makes user retrievable", async () => {
  const user = await createUser({ name: "Alice" });
  const retrieved = await getUser(user.id);
  expect(retrieved.name).toBe("Alice");
});

同义反复的测试（Tautological tests）：期望值复述了实现，所以测试靠构造就通过。

// BAD: Expected value is recomputed the way the code computes it
test("calculateTotal sums line items", () => {
  const items = [{ price: 10 }, { price: 5 }];
  const expected = items.reduce((sum, i) => sum + i.price, 0);
  expect(calculateTotal(items)).toBe(expected);
});

// GOOD: Expected value is an independent, known literal
test("calculateTotal sums line items", () => {
  expect(calculateTotal([{ price: 10 }, { price: 5 }])).toBe(15);
});

When to Mock（何时模拟）

只在系统边界（system boundaries）处模拟：

  • 外部 API（支付、邮件等）
  • 数据库（有时——优先用测试数据库）
  • 时间/随机性
  • 文件系统（有时）

不要模拟：

  • 你自己的类/模块
  • 内部协作者
  • 任何你掌控的东西

Designing for Mockability（为可模拟性而设计）

在系统边界，设计易于模拟的接口：

1. Use dependency injection（使用依赖注入）

把外部依赖传入，而不是在内部创建它们：

// Easy to mock
function processPayment(order, paymentClient) {
  return paymentClient.charge(order.total);
}

// Hard to mock
function processPayment(order) {
  const client = new StripeClient(process.env.STRIPE_KEY);
  return client.charge(order.total);
}

2. Prefer SDK-style interfaces over generic fetchers（优先用 SDK 风格的接口，而不是通用 fetcher）

为每个外部操作创建具体函数，而不是一个带条件逻辑的通用函数：

// GOOD: Each function is independently mockable
const api = {
  getUser: (id) => fetch(`/users/${id}`),
  getOrders: (userId) => fetch(`/users/${userId}/orders`),
  createOrder: (data) => fetch('/orders', { method: 'POST', body: data }),
};

// BAD: Mocking requires conditional logic inside the mock
const api = {
  fetch: (endpoint, options) => fetch(endpoint, options),
};

SDK 方式意味着：

  • 每个 mock 返回一个具体的形状
  • 测试设置里没有条件逻辑
  • 更容易看出一个测试行使了哪些端点
  • 每个端点有类型安全

ADR Format（ADR 格式）

ADR 存放在 docs/adr/，使用顺序编号：0001-slug.md、0002-slug.md 等。

推迟创建 docs/adr/ 目录——只有需要第一个 ADR 时才创建。

Template（模板）

# {Short title of the decision}

{1-3 sentences: what's the context, what did we decide, and why.}

就这些。一个 ADR 可以只有一段话。价值在于记录做过了一个决定以及为什么——而不在于填满小节。

Optional sections（可选小节）

只有在它们确实增加价值时才包含这些。大多数 ADR 用不上它们。

  • Status（状态）frontmatter（proposed | accepted | deprecated | superseded by ADR-NNNN）——当决策会被重新审视时有用
  • Considered Options（考虑过的选项）——只在被否决的备选方案值得记住时
  • Consequences（后果）——只在需要点名非显而易见的连锁影响时

Numbering（编号）

扫描 docs/adr/ 找到现有最高编号并加一。

When to offer an ADR（何时提议 ADR）

以下三条必须全部成立：

  1. 难以逆转——日后改变想法的代价是有意义的
  2. 脱离上下文时令人惊讶——未来读者看着代码会想"他们到底为什么这么做？"
  3. 真实权衡的结果——存在真正可选的方案，而你出于具体原因选了其中一个

如果决策容易逆转，跳过它——你反正会把它逆转掉。如果它不令人惊讶，没人会问为什么。如果没有真正的备选方案，除了"我们做了显而易见的事"之外没什么可记录的。

What qualifies（什么够格）

  • 架构形态（Architectural shape）。 "我们用的是 monorepo。" "写模型（write model）是事件溯源（event-sourced）的，读模型（read model）被投影进 Postgres。"
  • 上下文之间的集成模式（Integration patterns between contexts）。 "Ordering 和 Billing 通过领域事件通信，而不是同步 HTTP。"
  • 带来锁定（lock-in）的技术选择。 数据库、消息总线、鉴权提供方、部署目标。不是每个库——只是那些换掉要花一个季度的。
  • 边界与范围决策（Boundary and scope decisions）。 "客户数据归 Customer 上下文所有；其他上下文只按 ID 引用它。" 显式的"不"和"是"一样有价值。
  • 刻意偏离显而易见路径的决定（Deliberate deviations from the obvious path）。 "我们用手工 SQL 而不是 ORM，因为 X。" 任何一位理性读者会假设相反情况的决定。这些能阻止下一个工程师"修好"某个刻意的选择。
  • 代码里看不到的约束（Constraints not visible in the code）。 "因为合规要求我们不能用 AWS。" "因为伙伴 API 契约，响应时间必须低于 200ms。"
  • 被否决的备选方案——当否决本身非显而易见时（Rejected alternatives when the rejection is non-obvious）。 如果你考虑过 GraphQL 却因为微妙的原因选了 REST，记录下来——否则六个月后又会有人建议 GraphQL。

Rules（规则）

  • 自然聚类出现时用子标题分组。 如果所有术语都属于一个单一内聚的领域，平铺列表就够了。

Codebase Design（代码库设计）

设计深模块（deep module）：大量行为藏在小型接口后面，坐落在干净的接缝上，透过那个接口可测试。在任何正在设计或重构代码的地方使用这套语言和这些原则。目标是调用方的杠杆（leverage）、维护者的局部性（locality），以及所有人的可测试性。

Glossary（术语表）

精确使用这些术语——不要替换成 "component"、"service"、"API" 或 "boundary"。一致的语言正是全部意义所在。

Module（模块）——任何有接口和实现的东西。刻意与规模无关：一个函数、类、包，或跨层级（tier-spanning）的切片。避免用：unit、component、service。

Interface（接口）——调用方要正确使用模块所必须知道的一切：类型签名，还有不变式（invariants）、顺序约束、错误模式、所需配置和性能特征。避免用：API、signature（太窄——它们只指类型层面的表面）。

Implementation（实现）——模块内部的东西，它的代码本体。与Adapter（适配器）区分：一个东西可以是一个小适配器配大实现（一个 Postgres repo），也可以是大适配器配小实现（一个内存假件 in-memory fake）。当话题是接缝时用 "adapter"；否则用 "implementation"。

Depth（深度）——接口处的杠杆：一个调用方（或测试）每学习一单位接口就能行使的行为量。当一个模块有大量行为藏在小接口后面时它是深的，当接口几乎和实现一样复杂时它是浅的。

Seam（接缝） (Michael Feathers) ——一个无需就地编辑就能改变行为的地方；一个模块接口所居住的位置。接缝放哪里本身就是独立于"接缝后面放什么"的设计决策。避免用：boundary（与 DDD 的限界上下文 bounded context 过载）。

Adapter（适配器）——在接缝处满足某个接口的具体东西。描述角色（它填哪个槽），而不是实质（里面是什么）。

Leverage（杠杆）——调用方从深度中得到的东西：每学习一单位接口就获得更多能力。一份实现跨 N 个调用点和 M 个测试回本。

Locality（局部性）——维护者从深度中得到的东西：变更、bug、知识和验证集中在一个地方，而不是散落在调用方之间。修一次，处处修复。

Deep vs shallow（深 vs 浅）

深模块 = 小接口 + 大量实现：

┌─────────────────────┐
│   Small Interface   │  ← Few methods, simple params
├─────────────────────┤
│                     │
│  Deep Implementation│  ← Complex logic hidden
│                     │
└─────────────────────┘

浅模块 = 大接口 + 少量实现（避免）：

┌─────────────────────────────────┐
│       Large Interface           │  ← Many methods, complex params
├─────────────────────────────────┤
│  Thin Implementation            │  ← Just passes through
└─────────────────────────────────┘

设计接口时，问：

  • 我能减少方法的数量吗？
  • 我能简化参数吗？
  • 我能把更多复杂度藏进内部吗？

Principles（原则）

  • 深度是接口的属性，不是实现的属性。 一个深模块内部可以由小而可模拟、可替换的部件组成——它们只是不属于接口。一个模块可以有内部接缝（internal seams）（实现私有的，被它自己的测试使用），也可以有位于接口处的外部接缝（external seam）。
  • 删除测试（the deletion test）。 想象删除这个模块。如果复杂度消失了，它就是个透传（pass-through）。如果复杂度在 N 个调用方那里重新出现，它就在挣它的工资。
  • 接口就是测试面（test surface）。 调用方和测试跨同一条接缝。如果你想测试越过接口，模块的形状大概是错的。
  • 一个适配器意味着一个假设性的接缝。两个适配器意味着一个真实的接缝。 除非真有东西跨接缝变化，否则不要引入接缝。

Designing for testability（为可测试性而设计）

好接口让测试变得自然：

  1. Accept dependencies, don't create them（接收依赖，而不是创建依赖）。

```typescript // Testable function processOrder(order, paymentGateway) {}

// Hard to test function processOrder(order) { const gateway = new StripeGateway(); } ```

  1. Return results, don't produce side effects（返回结果，而不是制造副作用）。

```typescript // Testable function calculateDiscount(cart): Discount {}

// Hard to test function applyDiscount(cart): void { cart.total -= discount; } ```

  1. Small surface area（小的表面积）。 方法更少 = 需要的测试更少。参数更少 = 测试设置更简单。

Relationships（关系）

  • 一个模块（Module）有且仅有一个接口（Interface）（它呈现给调用方和测试的表面）。
  • 深度（Depth）是一个模块（Module）的属性，针对它的接口（Interface）来衡量。
  • 接缝（Seam）是一个模块（Module）的接口（Interface）所居住的地方。
  • 适配器（Adapter）坐在接缝（Seam）上并满足接口（Interface）。
  • 深度（Depth）为调用方产生杠杆（Leverage），为维护者产生局部性（Locality）。

Rejected framings（被拒绝的框架）

  • 深度作为实现行数与接口行数之比（Ousterhout）：奖励给实现注水。我们用深度即杠杆（depth-as-leverage）来代替。
  • 把 "Interface" 当作 TypeScript 的 interface 关键字或类的公共方法：太窄——这里的 interface 包含调用方必须知道的每一个事实。
  • "Boundary"：与 DDD 的限界上下文过载。说 seam 或 interface。

Going deeper（深入下去）

  • 在给定依赖的情况下加深一个簇（cluster）——见 DEEPENING.md：依赖分类、接缝纪律，以及"替换而不是分层（replace-don't-layer）"的测试。
  • 探索替代接口——见 DESIGN-IT-TWICE.md：并行拉起子 agent，用几种截然不同的方式设计接口，然后在深度、局部性和接缝位置上比较。

Deepening（加深）

如何在给定依赖的情况下安全地加深一个由浅模块组成的簇。假设 SKILL.md 中的词汇——module（模块）、interface（接口）、seam（接缝）、adapter（适配器）。

Dependency categories（依赖分类）

在评估一个加深候选时，对其依赖分类。类别决定加深后的模块如何跨接缝被测试。

1. In-process（进程内）

纯计算、内存状态、无 I/O。总是可加深——合并模块并直接透过新接口测试。不需要适配器。

2. Local-substitutable（本地可替换）

有本地测试替身（test stand-in）的依赖（Postgres 用 PGLite、内存文件系统）。如果替身存在就可加深。加深后的模块用跑在测试套件里的替身来测试。接缝是内部的；在模块的外部接口没有端口（port）。

3. Remote but owned (Ports & Adapters)（远程但自有，端口与适配器）

你跨网络边界的自有服务（微服务、内部 API）。在接缝处定义一个端口（port）（接口）。深模块拥有逻辑；传输层作为适配器（adapter）注入。测试用内存适配器。生产用 HTTP/gRPC/队列适配器。

推荐表述："在接缝处定义一个端口，为生产实现一个 HTTP 适配器、为测试实现一个内存适配器，这样即使跨网络部署，逻辑也待在一个深模块里。"

4. True external (Mock)（真正的外部，模拟）

你不控制的第三方服务（Stripe、Twilio 等）。加深后的模块把外部依赖作为注入的端口接收；测试提供一个模拟适配器。

Seam discipline（接缝纪律）

  • 一个适配器意味着一个假设性的接缝。两个适配器意味着一个真实的接缝。 除非至少两个适配器有正当理由（通常是生产 + 测试），否则不要引入端口。单适配器接缝只是间接层（indirection）。
  • 内部接缝 vs 外部接缝。 一个深模块可以有内部接缝（实现私有的、被它自己的测试使用的），也有位于接口处的外部接缝。不要仅仅因为测试用它们就把内部接缝透过接口暴露出去。

Testing strategy: replace, don't layer（测试策略：替换，而不是分层）

  • 一旦深模块接口处的测试存在，浅模块上的旧单元测试就变成废物——删掉它们。
  • 在加深后的模块的接口处写新测试。接口就是测试面。
  • 测试透过接口对可观察的结果做断言，而不是对内部状态。
  • 测试应该安然度过内部重构——它们描述行为，而不是实现。如果一个测试在实现变化时必须改变，它就在测试越过接口（testing past the interface）。

Design It Twice（设计两遍）

当用户想为选定的加深候选探索替代接口时，用这个并行子 agent 模式。基于"设计两遍"（Design It Twice，Ousterhout）——你的第一个想法不太可能最好。

使用 SKILL.md 中的词汇——module（模块）、interface（接口）、seam（接缝）、adapter（适配器）、leverage（杠杆）。

Process（流程）

1. Frame the problem space（框定问题空间）

在拉起子 agent 之前，为选定的候选写一份面向用户的问题空间说明：

  • 任何新接口都必须满足的约束
  • 它会依赖的东西，以及它们属于哪个类别（见 DEEPENING.md）
  • 一段粗略的、示意性的代码草图，让约束落地——不是提案，只是让约束具体化的一种方式

展示给用户，然后立即进入第 2 步。用户在子 agent 并行工作的时候阅读和思考。

2. Spawn sub-agents（拉起子 agent）

并行拉起 3 个以上子 agent。每个都必须为加深后的模块产出一个截然不同的接口。

给每个子 agent 一份单独的技术简报（technical brief）（文件路径、耦合细节、来自 DEEPENING.md 的依赖类别、接缝后面是什么）。这份简报独立于第 1 步中面向用户的问题空间说明。给每个 agent 一个不同的设计约束：

  • Agent 1："把接口最小化——目标是最多 1–3 个入口点。最大化每个入口点的杠杆。"
  • Agent 2："最大化灵活性——支持许多用例和扩展。"
  • Agent 3："为最常见的调用方优化——让默认情况微不足道。"
  • Agent 4（如适用）："围绕端口与适配器设计跨接缝依赖。"

在简报中包含 SKILL.md 词汇和 CONTEXT.md 词汇，这样每个子 agent 的命名与架构语言和项目领域语言保持一致。

每个子 agent 输出：

  1. 接口（类型、方法、参数——还有不变式、顺序、错误模式）
  2. 展示调用方如何使用的用法示例
  3. 实现藏在接缝后面的是什么
  4. 依赖策略和适配器（见 DEEPENING.md）
  5. 权衡（trade-offs）——哪里杠杆高，哪里杠杆薄

3. Present and compare（展示与比较）

逐个展示设计，让用户吸收每一个，然后用散文比较它们。按深度（depth）（接口处的杠杆）、局部性（locality）（变更集中的地方）和接缝位置（seam placement）对比。

比较之后，给出你自己的推荐：你认为哪个设计最强，为什么。如果不同设计的元素能很好地组合，提出一个混合方案。要有主见——用户要的是一个有力的判断，而不是一份菜单。

code-review（代码审查）

自某个固定点以来 diff 的双轴审查：Standards（标准）（是否符合仓库的编码标准，加上 Fowler 坏味道基线？）和 Spec（规格）（是否忠实实现了源 issue/规格？），以并行子 agent 运行。

name: code-review
description: Review the changes since a fixed point (commit, branch, tag, or merge-base) along two axes — Standards (does the code follow this repo's documented coding standards?) and Spec (does the code match what the originating issue/spec asked for?). Runs both reviews in parallel sub-agents and reports them side by side. Use when the user wants to review a branch, a PR, work-in-progress changes, or asks to "review since X".

Code Review（代码审查）

对 HEAD 与用户提供的固定点（fixed point）之间的 diff 做双轴审查：

  • 标准（Standards）——代码是否符合仓库文档化的编码标准？
  • 规格（Spec）——代码是否忠实实现了源 issue/规格？

两个轴都作为并行子 agent 运行，这样它们不会污染彼此的上下文，然后本技能汇总它们的发现。

issue 跟踪器应该已经提供给你。如果缺少 docs/agents/issue-tracker.md，告诉用户运行 /setup-matt-pocock-skills。

Process（流程）

1. Pin the fixed point（确定固定点）

无论用户说的固定点是什么——一个 commit SHA、分支名、tag、main、HEAD~5 等。如果他们没指定，就问。

把 diff 命令一次记下来：git diff <fixed-point>...HEAD（三个点，这样比较针对的是 merge-base）。同时用 git log <fixed-point>..HEAD --oneline 记下提交列表。

在走得更远之前，确认固定点能解析（git rev-parse <fixed-point>）且 diff 非空。坏的引用或空 diff 应该在这里失败——而不是在两个并行子 agent 内部。

2. Identify the spec source（定位规格来源）

按这个顺序寻找源规格：

  1. 提交消息中的 issue 引用（#123、Closes #45、GitLab !67 等）——通过 docs/agents/issue-tracker.md 中的工作流获取。
  2. 用户作为参数传入的路径。
  3. docs/、specs/ 或 .scratch/ 下与分支名或功能匹配的规格文件。
  4. 如果什么都没找到，问用户规格在哪里。如果他们说没有，规格子 agent 会跳过并报告"无可用规格（no spec available）"。

3. Identify the standards sources（定位标准来源）

仓库中任何记录代码应如何编写的文件，例如 CODING_STANDARDS.md 或 CONTRIBUTING.md。

在仓库文档化内容之上，标准轴总是携带下面的坏味道基线（smell baseline）——一组固定的 Fowler 坏味道（《重构 Refactoring》第 3 章），即使仓库什么都没记录也适用。两条规则约束它：

  • 仓库优先（The repo overrides）。 文档化的仓库标准总是获胜；在它认可基线会标记的东西时，抑制该坏味道。
  • 永远是判断（Always a judgement call）。 每个坏味道是一个带标签的启发式（"可能的 Feature Envy"），从来不是硬性违规——而且，和这里的任何标准一样，跳过任何工具已经在强制的东西。

每个坏味道读起来是它是什么 → 如何修复；把它对到 diff 上：

  • Mysterious Name（神秘命名）——名称无法揭示其作用或内容的函数、变量或类型。→ 重命名它；如果想不出诚实的名字，这个设计是浑浊的。
  • Duplicated Code（重复代码）——同一个逻辑形态出现在变更中的多个 hunk 或文件里。→ 抽取共享形态，让两处都调用它。
  • Feature Envy（依恋情结）——一个方法伸进另一对象的数据比伸进自己的还多。→ 把方法移到它嫉妒的那个数据上。
  • Data Clumps（数据泥团）——同一小组字段或参数不断一起旅行（一个想要出生的类型）。→ 把它们打包成一个类型，传那个。
  • Primitive Obsession（基本类型偏执）——用基本类型或字符串代替值得拥有自己类型的领域概念。→ 给这个概念一个自己的小类型。
  • Repeated Switches（重复的 switch）——针对同一类型的同一个 switch/if 级联在变更中反复出现。→ 用多态替代，或用两个地方共享的一张映射表。
  • Shotgun Surgery（霰弹式修改）——一个逻辑变更迫使 diff 中许多文件发生零散编辑。→ 把一起变化的东西收集进一个模块。
  • Divergent Change（发散式变化）——一个文件或模块因为几个不相关的原因被编辑。→ 拆分，让每个模块只为一个原因变化。
  • Speculative Generality（夸夸其谈的通用性）——为规格并不需要的需求添加的抽象、参数或钩子。→ 删除它；内联回去，直到真实需求出现。
  • Message Chains（消息链）——调用方不应依赖的长 a.b().c().d() 导航。→ 把这段行走藏到第一个对象上的一个方法后面。
  • Middle Man（中间人）——一个主要是转发的类或函数。→ 砍掉它，直接调用真正的目标。
  • Refused Bequest（被拒绝的遗赠）——忽略或重写大部分继承内容的子类或实现者。→ 放弃继承，用组合。

4. Spawn both sub-agents in parallel（并行拉起两个子 agent）

标准子 agent 提示（Standards sub-agent prompt）——包含：

  • 完整的 diff 命令和提交列表。
  • 你在第 3 步找到的标准来源文件列表，加上第 3 步的坏味道基线的全文——子 agent 没有其他途径拿到它。
  • 简报："报告——在相关的每个文件/hunk 处——(a) diff 违反文档化标准的每一处：引用标准（文件 + 规则）；以及 (b) 你注意到的任何基线坏味道：说出名字并引用该 hunk。区分硬性违规与判断——文档化标准的违反可能是硬性的，但基线坏味道永远是判断，而且文档化的仓库标准覆盖基线。跳过任何工具强制的东西。400 字以内。"

规格子 agent 提示（Spec sub-agent prompt）——包含：

  • diff 命令和提交列表。
  • 规格的路径或抓取到的内容。
  • 简报："报告：(a) 规格要求但缺失或只完成一部分的需求；(b) diff 中没被要求的行为（范围蔓延 scope creep）；(c) 看起来已实现但实现看起来有问题的地方。每条发现都引用规格原文。400 字以内。"

如果规格缺失，跳过规格子 agent，并在最终报告中注明。

5. Aggregate（汇总）

在 ## Standards 和 ## Spec 标题下呈现两份报告，原文照录或轻度清理。不要合并或重新排序发现——两个轴刻意分开（见《为什么是两个轴》）。

最后给一行总结：每个轴的发现总数，以及_每个轴内_最严重的问题（如果有）。不要跨轴选一个赢家——那正是分离所要阻止的重新排序。

Why two axes（为什么是两个轴）

一个变更可能过一个轴而挂另一个：

  • 遵守了每一条标准但实现错了东西 → 标准过、规格挂（Standards pass, Spec fail）。
  • 完全按 issue 的要求做但破坏了项目约定 → 规格过、标准挂（Spec pass, Standards fail）。

分开报告能阻止一个轴掩盖另一个。

resolving-merge-conflicts（解决合并冲突）

逐 hunk 处理进行中的 git 合并或变基冲突，按追溯到双方一手来源的意图来化解，然后完成操作——绝不 --abort。

name: resolving-merge-conflicts
description: "Use when you need to resolve an in-progress git merge/rebase conflict."

  1. 看清合并/变基的当前状态。检查 git 历史和冲突文件。

  2. 为每个冲突找到一手来源（primary sources）。深入理解每个改动为什么发生、原始意图是什么。读提交消息、查 PR、查原始 issue/ticket。

  3. 解决每个 hunk。 尽可能保留双方意图。两者不兼容时，选与合并声明目标一致的那个，并注明权衡（trade-off）。不要发明新行为。总是解决；绝不 --abort。

  4. 发现项目的自动化检查并运行它们——通常是类型检查，然后是测试，然后是格式化。修复合并弄坏的任何东西。

  5. 完成合并/变基。 暂存所有内容并提交。如果是变基，继续变基过程直到所有提交都被变基。

Wizard（向导脚本）

向导脚本（wizard）是一个 bash 脚本，一步步引导人类完成一个手动流程——这个流程手动做很繁琐，每次重新向 AI 解释也很繁琐。它打开每个 URL、精确说明要点什么和复制什么、捕获值、把它们写到该写的地方（.env、GitHub secrets）、在每个阶段确认，并显示还剩多少阶段。它可能配置第三方服务、运行一次性迁移，或把项目从一个状态移到另一个状态。

愉快的 UX 已经被 template.sh 解决——逐阶段进度、确认门控（confirmation gates）、跨平台打开 URL（包括 WSL）、隐藏的密钥输入、幂等的 .env upsert、gh secret/gh variable 写入，以及收尾总结。你的工作只是界定流程并编写它的各个阶段。 STAGES 标记之上的库在每个向导中都是相同的；这种一致性正是重点——永远不要手工编辑它。

向导默认是一次性的（ephemeral）——为一次运行而建，保存到 scratch 或 scripts/ 路径，任务完成即删除。只有当用户想要一个应该常驻仓库的可重复设置路径时才提交它。

Process（流程）

1. Scope the procedure（界定流程）

算出人类必须采取的每一个手动步骤，以及沿途捕获的每一个值。先读仓库——不要冷冰冰地问：

  • 对设置：.env、.env.example、.env.*、README、docker-compose*、框架配置，以及 .github/workflows/*（每个 secrets.* / vars.* 引用都是向导必须产出的值）。
  • 对迁移或转换：当前状态、目标状态，以及两者之间不可逆的动作。

然后向用户展示有序的阶段列表以及每个阶段产出的值，并确认——他们可能增、删或重排。

完成判据（Done when）： 每个阶段都按顺序命名，并且对每个捕获的值你知道 (a) 人类从哪里拿到它，(b) 它被写到哪里（.env、一个 GitHub secret、两者都是，或都不写——有些阶段是纯动作），以及 (c) 它是否是秘密（隐藏输入）还是公开的。

2. Map each stage's journey（映射每个阶段的人类旅程）

对每个阶段，写出人类会遵循的精确路径：打开哪个 URL、在那里做什么、值显示在哪里、它填充哪个变量——例如 "Dashboard → Developers → API keys → Reveal test key → copy"。在你实际上不知道当前 UI 或确切命令的地方，说出来并询问用户或查文档——永远不要发明可能不存在的步骤。

完成判据（Done when）： 每个阶段都能追溯到一个陌生人能照做的具体指令。

3. Author the wizard（编写向导）

把 template.sh 复制到目标路径。按依赖顺序，为每个步骤用一个 stage 替换示例阶段。使用库助手——stage、say/step、open_url、ask/ask_secret、write_env、set_secret/set_var、pause/confirm——并把 TOTAL_STAGES 设置为你写的阶段数。

守住模板设下的标准：在询问某个值之前先打开它的 URL、对任何秘密用 ask_secret、write_env 每个需要持久化的值、set_secret 只设置 CI 真正需要的值，并在任何不可逆动作前 confirm。每个 stage 会清屏，让只有当前步骤可见——把一个阶段保持为一项聚焦的任务，这样人类需要的东西不会滚出屏幕。不要碰标记之上的库。

4. Verify and hand off（验证与交接）

  • bash -n <script>；如果可用就运行 shellcheck。
  • chmod +x <script>。
  • 不要自己端到端地运行它——它会打开浏览器并阻塞等待人类输入。改为静态追踪：第 1 步的每个值都被捕获并落到第 1 步说的地方，并且每个 set_secret 名称都精确匹配 CI 中的一个 secrets.* 引用。
  • 告诉用户如何运行它。如果它是可重复的设置路径，提交它并从 README 链接它，这样下一个人运行脚本而不是问 AI。

grilling（拷问式追问）

一句话简介（来自 README）：反复采访用户关于某个计划、决策或想法，直到设计决策树的每个分支都被解决。

---
name: grilling
description: Grill the user relentlessly about a plan, decision, or idea. Use when the user wants to stress-test their thinking, or uses any 'grill' trigger phrases.
---

持续不断地采访用户，直到你们达成共识。把这绘制成一棵设计决策树：每个决策都会分支出依附于它的后续决策。

以轮次为单位推进这棵树。前沿（frontier）指所有前置条件已经确定的决策：也就是你现在就能问的问题，而不必猜测那些你还没听到过的答案。在一轮里问完整个前沿：为每个问题编号，并给出你的推荐答案。然后在进入下一轮之前，等用户回答完毕。

每个问题的格式如下：

❓ **Q1** - **<question title>**: <question body, might be multiple paragraphs, including multiple choices>

➡️ <your recommended answer>

每一轮，用户的回答都会重塑这棵树：已确定的决策会把前沿向外推进，并解锁那些依赖它们的、原本被阻塞的问题。重新计算前沿，然后进行下一轮。某个问题的答案如果依赖于本轮中仍未解决的另一问题，它属于_更晚的_一轮，而不是本轮。

查找事实（facts）是你的职责，绝不是用户的。当前沿问题需要来自环境（文件系统、工具等）的某个事实时，派遣一个子 agent 去找；凡是你能自己查到的东西，就不要问用户。不要为此阻塞：一项正在进行的探索是一个未决的前置条件，只有它下游的问题需要等子 agent 汇报；其余的先前沿现在就问。决策（decisions）属于用户：把每个决策摆到他们面前，然后等待。

当前沿为空时，本次会话结束：设计决策树的每个分支都已遍历过，没有留下任何被静默假设的东西。在用户确认你们已达成共识之前，不要据此行动。

理念（Philosophy）

要进行深度学习，用户需要三样东西：

  • 知识（Knowledge），来自高质量、高可信度的资源
  • 技能（Skills），通过你基于知识设计的、高度相关的交互式课程来习得
  • 智慧（Wisdom），来自与其他学习者和实践者的互动

在 RESOURCES.md 充实起来之前，你的重点应当是寻找能帮助用户获取知识的高质量资源。永远不要相信你的参数化知识（parametric knowledge）。

有些主题可能更需要技能而非知识。深入学习理论物理学可能更偏重知识；瑜伽则更偏重技能。

流畅度强度与存储强度（Fluency vs Storage Strength）

你应该注意区分两种类型的学习：

  • 流畅度强度（fluency strength）：当下即刻提取知识的能力
  • 存储强度（storage strength）：知识的长期留存能力

流畅度会给用户一种虚幻的掌握感，但存储强度才是真正的目标。试着通过合意困难（desirable difficulty）来设计课程，从而建立长期记忆：

  • 运用提取练习（从记忆中回想）
  • 间隔练习（把练习分散到一段时间内）
  • 交叉练习（在练习中混合不同但相关的主题——仅用于技能练习）

课程（Lessons）

课程是你产出的主要东西——知识与技能借此抵达用户的单元。每门课程是一个自包含的 HTML 文件，保存到 ./lessons/，命名为 0001-<dash-case-name>.html，编号每次递增。

一门课程应当精美——排版清晰、易读——因为用户之后会回来复习。想想图福特（Tufte）式的设计。

课程应当简短，能很快完成。学习者的工作记忆非常小，我们必须待在其中。但每门课程都应给用户一个实实在在的、可在此之上继续搭建的小胜利。它应当与任务直接挂钩，并且落在用户的最近发展区内。

如果可能，通过运行一条 CLI 命令为用户打开课程文件。

每门课程都应通过 HTML 锚点链接到其他课程和参考文档。

每门课程都应向用户推荐一个可以阅读或观看的一手来源。这应当是你为该主题找到的最高质量、最值得信赖的资源。

每门课程都应包含一个提醒，鼓励用户向 agent 提出追问。agent 就是他们的老师，可以帮助解决任何不清楚的地方。

资产（Assets）

课程由可复用的组件构建而成，存放在 ./assets/ 中：样式表、测验小部件、模拟器、图表辅助工具——任何第二门课程可能复用的东西。

复用是常态，不是例外。在撰写一门课程之前，先读一读 ./assets/，从已有的组件开始构建。当一门课程需要某个新的、可复用的东西时，把它写成 ./assets/ 里的一个组件并链接过去——绝不要内联那些未来课程会重复的代码。

共享样式表是每个工作区最先收获的组件：每门课程都链接它，这样所有课程看起来像一门一致的系列课程，而不是一堆一次性产物。随着工作区成长，组件库也应随之成长。

任务（The Mission）

每门课程都应紧扣任务——也就是用户想学习这个主题的原因。

如果用户对任务不清楚，或者 MISSION.md 还没有内容，你的首要工作应当是询问用户为什么想学这个。

不理解任务，就意味着知识获取无法落地到现实世界的目标上。课程会显得过于抽象。你也会无从判断用户下一步该做什么。

随着用户掌握更多技能和知识，任务可能会改变。这很正常——务必更新 MISSION.md，并添加一条学习记录来捕捉这个变化。在改变任务之前，先与用户确认。

最近发展区（Zone Of Proximal Development）

每门课程，用户都应始终感觉自己受到了"恰到好处"的挑战。

用户可能会指明一个他们想学的具体内容。如果没有，就通过以下方式判断他们的最近发展区：

  • 阅读他们的 learning-records
  • 根据他们的任务，确定教他们什么才合适
  • 教授最相关、且落在他们最近发展区内的内容

知识（Knowledge）

课程应围绕用户将要学习的技能来设计。课程中的知识应只是习得该技能所需的那部分。你先教知识，然后通过交互式反馈回路让用户练习技能。

知识应首先从可信资源中收集。用 RESOURCES.md 来跟踪它们。课程中应遍布引用——链接到外部资源，为任何论断提供支撑。这会提高课程的可信度。

在获取知识时，难度是敌人。它会吞噬你理解所需的工作记忆。

技能（Skills）

如果说知识重在获取，那么技能重在持久与灵活。让知识牢固下来。

在习得技能时，难度是工具。费力的提取（effortful retrieval）正是建立存储强度的途径。技能应通过交互式课程来教授。你手头有几种工具：

  • 交互式课程，使用测验和轻量的浏览器内任务
  • 引导用户按照一列现实世界步骤行动的课程（例如瑜伽体式）

这些都应基于一个反馈回路，让用户得到关于自己表现的反馈。这个反馈回路应尽可能紧凑，立即给出反馈——理想情况下是自动给出。

对于测验，每个答案的字数应完全相同（如有可能，字符数也相同）。不要通过格式给用户任何关于答案的线索。

获取智慧（Acquiring Wisdom）

智慧来自真正的现实世界互动——在学习环境之外检验你的技能。

当用户提出一个似乎需要智慧的问题时，你的默认姿态应当是先尝试回答——但最终把问题委托给一个社区（community）。

社区是一个（线上或线下的）地方，用户可以在真实世界中检验自己的技能。它可能是一个论坛、一个 subreddit、一个线下课堂（预算允许的话）或一个本地兴趣小组。

你应努力寻找用户可以加入的高声誉社区。如果用户表示他们不想加入社区，请尊重这个偏好。

参考文档（Reference Documents）

在创建课程的同时，你也应创建参考文档。课程可以引用这些文档——它们对跟踪跨课程有用的原始知识单元很有帮助。

课程以后很少会被重温——参考文档则会。它们应当是对课程的精炼浓缩，采用专为快速查阅设计的格式。

有些学习主题很适合做成参考材料：

  • 编程的语法和代码片段
  • 流程的算法和流程图
  • 瑜伽的体式和序列
  • 健身的训练动作和常规计划
  • 任何有自身命名体系的主题的术语表

尤其是术语表，是一种必不可少的参考。一旦创建了术语表，每门课程都必须遵循它。

NOTES.md

用户有时会表达他们希望被如何教授，或有些事情你应当记住。这里是记录这些偏好的地方，这样你在设计课程或与用户合作时，可以回头查阅它们。

MISSION.md 格式

MISSION.md 位于工作区根目录。它记录了用户学习这个主题的_原因_。每一个教学决策——接下来教什么、呈现哪些资源、设计哪些练习——都应能追溯到这份文档。

模板

# Mission: {Topic}

## Why
{1-3 sentences. The concrete real-world goal the user is chasing. What changes in their life or work when they have this skill? Avoid abstract framings like "to understand X" — push for the underlying outcome.}

## Success looks like
- {A specific, observable thing the user will be able to do}
- {Another specific thing}
- {…}

## Constraints
- {Time, budget, prior commitments, learning preferences, anything that bounds the approach}

## Out of scope
- {Adjacent topics the user explicitly does not want to chase right now — protects the zone of proximal development}

规则

  • 每个工作区只有一个任务。 如果用户想学两件互不相关的事，那就是两个工作区。
  • 具体胜过抽象。 "十月前跑完半程马拉松"胜过"把身体练得更好"。"给我的团队交付一个 Rust CLI"胜过"学习 Rust"。
  • 拒绝含糊。 如果用户说不出原因，在写下任何内容之前先采访他们。一个糟糕的任务比没有任务更糟。
  • 现实变化时及时修订。 任务会变。当用户的目标发生变化时，更新这个文件——不要留下一份过时的任务来左右未来的会话。
  • 保持简短。 如果 MISSION.md 超过一屏，它就不再是罗盘，而是变成了一份计划。

以下是 teach/GLOSSARY-FORMAT.md 的全文翻译。

GLOSSARY.md 格式

GLOSSARY.md 是这个教学工作区的规范语言。所有讲解、练习和学习记录都应遵循其术语体系。构建它本身就是学习的一部分：把一个概念压缩成紧凑的定义，正是用户理解它的证据。

结构

# {Topic} Glossary

{One or two sentence description of the topic this glossary covers.}

## Terms

**Hypertrophy**:
Muscle growth driven by mechanical tension and metabolic stress over repeated training sessions.
_Avoid_: Bulking, getting big

**Progressive overload**:
Systematically increasing the demand on a muscle over time — via load, volume, or intensity.
_Avoid_: Pushing harder, levelling up

**RPE (Rate of Perceived Exertion)**:
A 1–10 self-rating of how hard a set felt, where 10 is failure and 8 means two reps left in the tank.
_Avoid_: Effort score, intensity rating

规则

  • 只有在用户真正理解之后，才添加术语。 术语表是压缩知识的记录，不是用户靠阅读来学习的字典。如果用户刚刚接触某个概念，要等到他们能正确使用它时，再把它提升到此处。
  • 要有主见。 当同一个概念存在几个词时，挑出最好的一个，把其余的列为应避免的别名。语言就是这样被压缩的。
  • 定义保持紧凑。 一两句话。定义这个术语"是什么"，而不是它"做什么"或"怎么做"。
  • 在定义内部使用术语表自身的术语。 一旦某个术语进入术语表，就处处优先使用它——包括在其他定义内部。这正是让复杂术语日后更容易被理解的方式。
  • 当出现自然聚类时，用次级标题分组（例如 ## Anatomy、## Programming）。当术语本身自成一体时，扁平列表也可以。
  • 明确标注歧义。 如果某个术语在更广的领域里用法不严谨，注明你的裁决："在本工作区，'set' 始终指正式组（working set）——热身组单独记录。"
  • 随理解加深而修订。 用户在第一周写下的定义，到第六周可能已经错了。就地更新；不要留下过时的条目。

学习记录格式

学习记录存放在 ./learning-records/ 中，使用顺序编号：0001-slug.md、0002-slug.md 等。目录按需创建——只在写入第一条记录时才创建。

它们是教学领域的 ADR（架构决策记录）：记录那些不显而易见的教训、关键洞见以及明确陈述过的既有知识，从而指引未来的会话。它们被用来计算最近发展区。

模板

# {Short title of what was learned or established}

{1-3 sentences: what was learned (or what prior knowledge was established), and why it matters for future sessions.}

这就是全部格式。一条学习记录可以只是一个段落。它的价值在于记录"现在知道了_这件事_"，以及"_为什么_它会改变接下来要教什么"——而不是在于填满各个小节。

可选小节

只有当它们确实能增添价值时才包含这些。大多数记录用不到它们。

  • 状态（Status） 前置元数据（active | superseded by LR-NNNN）——当先前的理解被证明是错误的、并被取代时很有用。
  • 证据（Evidence）——用户是如何展示这一理解的（回答了一个问题、完成了一个练习、引用了既有经验）。当这个论断日后可能被复查时很有用。
  • 影响（Implications）——这为未来的会话解锁了什么、或排除了什么。在不显而易见时值得记录。

编号

扫描 ./learning-records/，找到现有最大的编号并加一。

何时写学习记录

以下任一情况成立时写一条：

  1. 用户展示了对某件不平凡之事的真正理解——不只是接触过，而是有证据表明他们能正确运用这个概念。这会为接下来要教的内容设定新的底线。
  2. 用户透露了既有知识——"我已经知道 X 了。"记录下来，这样未来的会话就不会重复教。同时记下声称的_深度_。
  3. 纠正了一个误解——用户先前相信了某个错误的东西，现在明白了原因。这些记录价值很高：它们能预示相关主题未来可能出现的绊脚石。
  4. 任务因学习而发生了转变——用户发现自己真正在意的其实和自己原先想的不一样。交叉链接到 [[MISSION.md]] 并更新它。

什么_不算_

  • 仅仅被讲到的材料。讲过不等于学到。等待证据。
  • 已在 [[GLOSSARY.md]] 中作为术语定义被简洁记录的任何内容。不要重复。
  • 逐会话的活动日志。学习记录不是日记——它们是决策级别的洞见。

取代（Supersession）

当一条较新的记录与较早的记录矛盾时（用户的理解加深或得到了纠正），把旧记录标记为 Status: superseded by LR-NNNN，而不是删除它。理解如何演化的历史本身就是有用的信号。

以下是 teach/RESOURCES-FORMAT.md 的全文翻译。

RESOURCES.md 格式

RESOURCES.md 是针对该主题精心整理的可信来源集合。讲解所需的知识应从这里取材，而不是来自参数化猜测。智慧则来自这里列出的社区。

结构

# {Topic} Resources

## Knowledge

- [Book: _The Science and Practice of Strength Training_ — Zatsiorsky & Kraemer](https://example.com)
  Foundational text on programming and adaptation. Use for: anything to do with periodisation, recovery, intensity zones.
- [Article: "How Much Should I Train?" — Greg Nuckols (Stronger By Science)](https://example.com)
  Evidence-based review of volume landmarks. Use for: weekly set targets per muscle group.

## Wisdom (Communities)

- [r/weightroom](https://reddit.com/r/weightroom)
  High-signal subreddit, moderated against bro-science. Use for: programme critique, plateau troubleshooting.
- Local: Tuesday strength class at {gym name}
  Use for: real-time coaching feedback on lifts.

规则

  • 只要高可信度。 优先选择一手来源、公认专家、同行评审的成果，以及管理严格的社区。如果某个资源是披着教育外衣的营销，就别收进去。
  • 为每个条目加注。 一个光秃秃的链接三个月后就没用了。加一行说明：它覆盖什么，以及何时该用它。
  • 按知识/智慧分组。 与 SKILL.md 中的理念相呼应。一个资源只出现在一个组里也没关系。
  • 明确暴露空白。 如果任务需要的某个领域没有好的资源，写一个 ## Gaps（空白）小节，列出缺失的东西。这会推动未来的搜索。
  • 无情地修剪。 被证明是错误、浅薄或偏离任务的资源应当被移除，而不是埋没。五个精悍的来源好过三十个平庸的。
  • 记录社区偏好。 如果用户选择不加入社区，在这里注明，这样未来的会话就不会一直推荐它们。

to-questionnaire（转成问卷）

一句话简介（来自 README）：把你无法独自回答的决策，变成一份 Markdown 问卷，交给唯一能回答的那个人——异步填写，或开会时一起填写。

---
name: to-questionnaire
description: Turn a decision you can't fully answer into a questionnaire for someone else to fill in.
disable-model-invocation: true
---

把用户无法独自回答的事情，变成一份问卷（questionnaire）——一份 Markdown 文档，用户把它交给一个人异步填写，或在一次会议中一起填写。接收者拥有用户所缺乏的知识；问卷负责把知识从他们那里提取出来。

拷问"发送"，而不是"主题"。 只采访用户关于_发送_的问题——这是他们总能回答的：发给谁，以及他们需要拿回什么。然后，文档里的问题瞄准的是接收者所知与用户所需之间的差距（gap）。

  1. 发给谁？ 在一次交流中问清接收者的角色、专业领域以及与用户的关系。这决定了问卷的语气，以及它需要承载多少背景信息。当你知道了接收者是谁、以及他们知道哪些用户不知道的东西时，这一步就完成了。

  2. 你需要拿回什么？ 在一次交流中问清用户无法独自解决、需要从这个人身上获得的那些具体决策或事实。当你得到一份具体的清单——用户离开时必须能够做到或决定什么——这一步就完成了。

  3. 撰写问卷。 按照下面的文档结构，起草瞄准第 1–2 步差距的问题。把它写入当前目录下的 to-questionnaire-<slug>.md（slug 取自主题），并报告路径。当文件存在、且用户在步骤 2 中提出的每一项都被一个问题覆盖到时，这一步就完成了。

文档结构

把文档定位成一份摸底问卷（discovery questionnaire）：用户缺少背景信息，接收者持有它。按"最重要优先"的顺序排列问题——异步意味着你可能只有一次机会——一旦问题超过几个，就按主题用 ## 标题分组。用下面的模板来写。

<问卷标题>

目的： 这份问卷为什么存在，以及它承载着哪个决策。

来自： <用户> —— 发给： <接收者> —— 你的回答将如何使用： <它们的去向>

背景（Context）

用一段话为不在用户脑子里的接收者指路。足以让回答者答得好，而不是一页纸。

如何回答（How to answer）

截止时间和大致工作量。部分回答和"我不知道"都是有用的——对任何不确定的地方要标注出来，而不是跳过。

<主题标题>

每个主题一个 ## 小节。在每个小节下，是该主题的问题，按最重要优先排列。每个问题只表达一个想法——绝不复合——下方紧跟着一个答案填空位，并且只在问题可能被误读、或可能招来敷衍回答的地方，加上一行_为什么这很重要_。

系统上线时预期要承受多大的负载？

为什么这很重要：它决定了我们是现在就为突发流量做准备，还是推迟再说。

还有其他要补充的吗？（Anything else?）

一个收尾的兜底问题：我们没问到、但你认为我们应该知道的事情？

wait-what（等等，什么？）

一句话简介（来自 README）：一条消息没被理解的那一刻立刻触发。agent 会用你缺失的上下文、用简单英语、并使用你 CONTEXT.md 的词汇重新解释它。

---
name: wait-what
description: Stop. That last message did not land — re-pitch it.
disable-model-invocation: true
---

等等——我没看懂你走到了哪里。请重新解释一下：给我一点背景，用 ASD-STE100 简化技术英语（Simplified Technical English）来说，并使用来自 CONTEXT.md 的通用语言（ubiquitous language）。

writing-for-agents（为 agent 写作）

一句话简介（来自 README）：为 agent 撰写文档：技能、AGENTS.md/CLAUDE.md，以及任何 agent 通过指针触达的文档。

---
name: writing-for-agents
description: Writing documents for agents. Use when creating or editing skills, or modifying AGENTS.md or CLAUDE.md.
---

为 agent 会消费的任何文档写作时的参考——一个技能、一份 AGENTS.md / CLAUDE.md、一份通过指针触达的文档。包装不同，写作方式不变：同样的杠杆让每一份都变得可预期——agent 每次运行都走同样的_流程_，而不是产出同样的输出。

当你写的是技能文档时，阅读 SKILL-MECHANICS.md，以了解前置元数据、调用方式选择和路由器技能。

上下文指针（Context Pointers）

上下文指针（context pointer）是 agent 上下文里持有的一种引用：它指名某份上下文之外的材料，并编码了触达它的条件。技能描述就是一个例子；AGENTS.md 中指明某份文档的一行也是同类对象。决定 agent 何时、以及以多高的可靠性触达材料的是指针的_措辞_，而不是它的目标。一个措辞软弱的指针后面挂着一个必需的目标，这是方差 bug（variance bug）：先打磨措辞，只有打磨失败时，才把材料内联进来。

指针做两件事——说明材料是什么，并列出应当触发触达它的分支（branch，指文档处理的某种不同场景，因此不同的运行会走不同的路径）。常驻加载的指针的每一个词都在每一轮耗费成本，所以它比正文更值得被严苛地修剪：

  • 把引导词前置——指针正是在这里完成它的触发工作。
  • 每个分支一个触发词。 只是给同一个分支换了个名字的同义词，等于把一个分支写了两遍；把它们合并，只保留真正不同的分支。
  • 删掉正文已经承载的标识性内容。

两种负载（The Two Loads）

你添加的每份文档和指针，都会花掉两种预算中的一种：

  • 上下文负载（context load）——常驻加载的材料对 agent 窗口的代价：一行 AGENTS.md、一个技能描述、任何每轮都待在上下文里的东西，无论触发与否都在消耗 token 和注意力。
  • 认知负载（cognitive load）——对人的代价：存在哪些文档，以及什么时候该去用哪一份。人是索引。这不是一个要最小化的成本——它是人的能动性（human agency）的代价；在人的判断重要的地方花它，在人不重要的地方省掉它。

只能通过指针触达的材料，以指针自身那一行为代价，逃脱了上下文负载；完全没有指针的材料，则完全靠认知负载来支撑。

信息层级（Information Hierarchy）

一份文档由两种内容类型构建——步骤（steps，agent 按顺序执行的动作）和参考（reference，按需查阅的定义、规则、事实）——它们可以自由混合：全是步骤（一份菜谱）、全是参考（某次评审的规则、本技能）、或者两者兼有。核心决策是每一块内容在信息层级上落在哪个位置。这是一个按 agent 对材料的需求急切程度排序的阶梯：

  1. 文件内步骤（in-file step）——第一级：agent 做什么，按顺序。
  2. 文件内参考（in-file reference）——按需查阅。它常常是合理的扁平同级集合（一次评审的所有规则同处一级）——这是很好的安排，不是坏味道。
  3. 已披露参考（disclosed reference）——推到单独的文件里，通过上下文指针触达，只在指针触发时加载。范围从同一文件夹下的同级文件，一直到可以存在于任何地方、任何文档都能指向的完全外部参考。

推得太少，顶部会膨胀；推得太多，你会藏起 agent 真正需要的材料。这个张力就是全部决策所在。

渐进式披露（progressive disclosure）就是向下移动——移出主文件、藏到指针后面——这样顶部保持易读。它主要不是一种 token 优化：它是保护层级的方式。分支是检验披露是否得当的最干净标准：把所有分支都需要的内容内联，把只有部分分支会触达的内容推到指针后面。当文档含有步骤时，本应被披露的文件内参考会埋没这些步骤，把注意到它们变成一次抛硬币——这是一个影响方差（variance）的杠杆，而不只是影响可读性。

同置（co-location）是文件内的配套动作：阶梯决定一块内容_下沉多深_，同置则决定它一旦就位，旁边该放什么。把一个概念的定义、规则和注意事项放在同一个标题下，而不是散落各处，这样读到一部分就会连带读到相邻部分。检验标准：文档读起来应当像专为 agent 写的文档——分组的材料读起来就是这样；散落的材料则不是。（这与重复不同：重复是在两个地方重复同一个意思；散落是把一个意思拆散到许多地方。）

蔓延（sprawl）是这里的失败模式：文档只是太长了，即使每一行都是有用且唯一的。注意力会在多余内容中变稀薄，而每多一行，就多一行需要保持相关性。解药是那个阶梯：把参考披露到指针后面，并按分支或序列拆分，让每条路径只携带它需要的东西。

步骤与完成判据（Steps and Completion Criteria）

每个步骤都以一个完成判据（completion criterion）收尾——告诉 agent 工作已完成的那个条件。两个属性使它成为一个杠杆：

  • 清晰度（clarity）——agent 能区分"完成"与"未完成"吗？一个含糊的界限（"已达成理解"）会招致过早完成（premature completion）：在真正完成之前就结束步骤，注意力滑向_显得已做完_。仍然可见的前方步骤——完成后的步骤（post-completion steps）——提供拉扯力；判据的清晰度则是阻力。按顺序防守：先打磨界限（局部且廉价）；只有当界限不可约地模糊_并且_你观察到赶工的迹象时，才通过拆分序列来隐藏后面的步骤——而且隐藏只在真正的上下文边界处有效（一次交接或一次子 agent 派遣；一次内联调用会把后续步骤留在上下文里，什么也清不掉）。
  • 要求度（demand）——它要求多少。"每个被修改的模型都要交代清楚"能逼出彻底的工作，而"产出变更清单"则不能。要求度驱动腿脚功夫（legwork）——agent 在工作内部进行的挖掘，它潜伏在措辞里，而不是被写成单独的步骤——而且它不局限于某个步骤："每一条规则都应用到位"约束的是一整块扁平参考，正如"每个步骤都做完"约束的是一整条序列——这正是全参考文档仍然带着一条穷尽性标尺的方式。

最强的判据既可核查、又穷尽所有情况。

何时拆分（When to Split）

把一份文档拆成两份会花掉两种负载之一，所以只有切割能挣回成本时才拆：

  • 按序列拆（by sequence）——拆分一串步骤，当"完成后的步骤"会诱使 agent 草草做完当前这一步时。让它们留在视野之外，会推动当前任务上更多的腿脚功夫。当心反向操作：合并序列会把每个步骤后面的步骤暴露给后续内容，招致过早完成。
  • 按调用方式拆（by invocation）——技能专属：参见 SKILL-MECHANICS.md。

引导词（Leading Words）

引导词（leading word）是一个紧凑的概念，它已经存在于模型的预训练中，agent 在运行文档时用它来思考（lesson（课程）、fog of war（战争迷雾）、tracer bullets（曳光弹））。它作为单个 token 反复出现、而不是一句话，通过调用模型已有的先验，用最少的 token 累积起一个分布式的定义，并锚定一整片行为区域。你也可以自己造词，只要定义清楚就行，但一个生造的词语调不起任何先验——你得用定义 token 去支付一个预训练词汇免费给出的东西；先去找现成的词。

它锚定两次。在正文里，锚定_执行_（execution）：每次这个词出现，agent 都会去取同样的行为；在扁平参考内部，它会把注意力集中到一类要找的东西上。在指针里，锚定_调用_（invocation）：当同一个词同时存在于你的提示词、你的文档和你的代码库里时，agent 会把这种共享语言与材料关联起来，从而更可靠地触达它。

寻找用引导词重构的机会。一个在三个地方写全的三元组、一个花一整句话来指向同一个想法的指针——每一处都是一段渴望压缩成单个 token 的文字：

  • "fast, deterministic, low-overhead"（快速、确定、低开销）→ tight（紧凑）（一条 tight 循环）。
  • "a loop you believe in"（一条你信得过的循环）→ red（变红）——一个模糊的门变成二元可观察的状态（遇到 bug，循环就变_红_，否则不变）。

你赢两次：token 更少，而且为 agent 提供了一枚更锋利的挂钩，用来挂住它的思考。假定每份文档里都带着引导词可以淘汰的重复表述——去找出它们。

否定（negation）是这个杠杆旁边的失败模式：靠禁令来引导，会把被禁止的行为拖进上下文，让它变得更_可及_，而不是更不可及。别去想大象，结果脑子里全是那头大象；否定是个软弱的修饰词，会被强烈激活的概念碾压过去，于是禁令有一半被读成"去做这件事"的指令。用正向（positive）措辞——直接陈述目标行为（"写单行注释"），这样被禁止的行为根本不会被说出来。禁令只有在作为一种无法用正向措辞表达的硬护栏时才有立足之地；即便如此，也要把它与正向目标配对，让注意力落在该做什么上。

修剪（Pruning）

  • 让每个含义保持单一事实来源（single source of truth）：一个权威的位置，这样改变行为就是一处编辑。重复（duplication）——同一个含义出现在多个地方——会付出维护和 token 的代价，并会把某个含义在阶梯上的显要程度抬高到它实际级别之上。（它恰好是引导词的反面：引导词刻意重复 token，而绝不重复含义。）
  • 环境也是一个事实来源——package.json 脚本、配置文件、目录布局、--help 输出——而一份复述它的文档是一份缓存（cache）：查找结果的副本，只有当查找本身昂贵时才值得它占据的负载。缓存那些 agent 靠"看"找不到的东西：未写下来的约定、某个选择背后的原因、没有任何配置会坦白的坑。把单文件、单命令的查找留给环境，在那里它们不会过时。
  • 逐行检查相关性（relevance）：它还与文档所做的事情有关吗？一行内容失去相关性，要么因为它从不涉及任务（纯粹是解释性文字，或一个本应被披露的分支），要么因为它描述的行为或世界发生变化而过时。更短的文档更容易保持相关。没有修剪纪律，默认的命运是沉积（sediment）：过时的层次一层层沉淀下来，因为添加让人感到安全、删除让人感到冒险，直到你不得不穿透这些层次，才能找到仍然有效的内容。
  • 逐句猎杀空操作（no-op）：一句模型默认就会遵守的指令，花了负载却什么也没说。检验标准——它相对默认行为是否改变了行为？——是模型相关的，不是读者相关的：两个人对某个 no-op 意见不一，其实是对"默认是什么"意见不一，而这要靠实际运行文档来解决，而不是靠争论。当一句话不合格时，整句删除，而不是从里面删几个词。这个检验也用来给引导词打分：一个弱到无法胜过默认的词（agent 已经大致彻底时，还说 be thorough（要彻底））就是 no-op，修法是换一个更强的词（relentless（毫不留情）），而不是换一种技巧。

技能机制（Skill Mechanics）

这是 writing-for-agents 中技能专属的分支：当文档是一个技能时，哪些东西会变——前置元数据、调用方式选择，以及路由器技能。关于写作的其他一切都以 SKILL.md 中的通用参考为准。

调用方式（Invocation）

两种选择，在两种负载之间取舍：

  • 模型调用（model-invoked）的技能保留 description，这样 agent 能自主触发它——其他技能也能触达它。你仍然可以输入它的名字：模型调用总是_包含_用户触达；description 只会增加 agent 的发现能力，绝不会移除人的触达能力。description 是技能的顶层上下文指针，被迫时刻保持加载——以永久性的上下文负载换取可发现性。一个内容全是参考的模型调用技能，也是共享参考的一个归宿：其他技能可以调用它，于是多个技能需要的参考就住在同一个地方。机制：省略 disable-model-invocation，并写一个面向模型的、携带触发分支的 description（SKILL.md 中的指针写作规则全部适用）。
  • 用户调用（user-invoked）的技能把 description 从 agent 的触达范围里剥离：只有输入它名字的人能调用它，任何其他技能都不行。上下文负载为零，但它消耗认知负载——你就是必须记住它存在的那个索引。机制：设置 disable-model-invocation: true；description 变成面向人的——一行摘要，触发词列表被剥离。

只有当 agent 必须自己触达这个技能、或另一个技能必须触达它时，才选模型调用。如果它只靠手动触发，就做成用户调用，不付上下文负载。

两个用户调用的技能都需要、却都无法容纳的共享参考——由于没有 description，两者谁也无法触发对方。把它推到技能系统之外的普通文件里：任何技能都能指向的外部参考。

按调用方式拆分（Splitting by Invocation）

这是拆分的调用方式切分（序列切分在 SKILL.md 里）：当你有一个应能独自触发它的独特引导词——一个你确实会在提示词中使用的触发词——或另一个技能必须触达它时，就拆出一个模型调用的技能。你要为新的常驻 description 支付上下文负载，所以这份独立的触达能力必须值得这个代价。

路由器技能（Router Skills）

当用户调用的技能多到你记不住时，那些堆积起来的认知负载可以用一个路由器技能（router skill）来治愈：一个用户调用的技能，指名其他技能以及各自何时该用，这样人就只需要记住一个技能，而不是许多个。它只能提示，绝不能触发它们：用户调用的技能没有 description，所以除人之外没有任何东西能触达它们。

设置一个 PreToolUse 钩子，在 Claude 执行危险 git 命令之前将其拦截并阻断。

会被拦截的命令

  • git push（包括 --force 在内的所有变体）
  • git reset --hard
  • git clean -f / git clean -fd
  • git branch -D
  • git checkout . / git restore .

被拦截时，Claude 会看到一条提示消息，告知它没有权限访问这些命令。

迁移到 Shoehorn（Migrate to Shoehorn）

为什么用 shoehorn？

shoehorn 让你在测试中传入部分数据（partial data），同时让 TypeScript 保持满意。它用类型安全的替代方案取代了 as 断言。

仅用于测试代码。 永远不要在生成代码（production code）中使用 shoehorn。

as 在测试中的问题：

  • 被训练成不要使用它
  • 必须手动指定目标类型
  • 有意传入错误数据时需要双重断言（as unknown as Type）

安装

npm i @total-typescript/shoehorn

迁移模式

属性众多但只需其中少量的大对象

之前：

type Request = {
  body: { id: string };
  headers: Record<string, string>;
  cookies: Record<string, string>;
  // ...20 more properties
};

it("gets user by id", () => {
  // Only care about body.id but must fake entire Request
  getUser({
    body: { id: "123" },
    headers: {},
    cookies: {},
    // ...fake all 20 properties
  });
});

之后：

import { fromPartial } from "@total-typescript/shoehorn";

it("gets user by id", () => {
  getUser(
    fromPartial({
      body: { id: "123" },
    }),
  );
});

as Type → fromPartial()

之前：

getUser({ body: { id: "123" } } as Request);

之后：

import { fromPartial } from "@total-typescript/shoehorn";

getUser(fromPartial({ body: { id: "123" } }));

as unknown as Type → fromAny()

之前：

getUser({ body: { id: 123 } } as unknown as Request); // wrong type on purpose

之后：

import { fromAny } from "@total-typescript/shoehorn";

getUser(fromAny({ body: { id: 123 } }));

何时使用哪个

函数 适用场景
fromPartial() 传入仍能通过类型检查的部分数据
fromAny() 有意传入错误数据（保留自动补全提示）
fromExact() 强制传入完整对象（之后可换成 fromPartial）

运行一场有状态的 /grilling 会话，其唯一产出是 workflow（工作流） 规格。采用拷问（grilling）的纪律——锲而不舍，一次一轮问题，每轮附带一个推荐答案——并始终瞄准下文所述的词汇表与目标。随着拷问逐步厘清问题，创建、编辑并删除相应的规格。

The loop lens（循环透镜）

一个循环（loop）是用户生活中反复出现的模式：他们的职业生涯、他们的一周、他们的早晨、某个反复进行的单一活动。把生活想象成循环套着循环，就能看清这些活动实际上有多么可预测——这正是它们值得被委派（delegating）的原因。用这面透镜去找出值得写成规格的循环，并主动提出那些用户自己尚未注意到的循环。

一个workflow（工作流）是某一个循环的规格，并将其落地实现。你在一个循环上运行 workflow——循环就是它的运行态实例。Workflow 存放于 workflows/*.md，是事实来源（source of truth）。

Vocabulary（词汇表）

一种共享语言，仅当一个 workflow 确实需要时才启用——绝不是一张检查清单。不强制任何结构：一个 workflow 并不需要 AI、不需要检查点、也不需要时间表，除非拷问表明它确实需要。

  • 触发器（Trigger） — 触发每次运行的东西：一个事件（event）（新邮件、新 issue）或一个时间表（schedule）（每天早晨）。事件触发通常更高效。
  • 检查点（Checkpoint） — 一个人工介入（human-in-the-loop）点，在此要求用户核实或拍板。有些 workflow 没有任何检查点，完全自主运行；有些则完全不使用 AI。
  • 尽量后置（Push right） — 把检查点尽可能往后推。在涉及人类介入之前做足最大量的工作，这样用户只被问一次、问得晚、且一切准备就绪。
  • 简报（Brief） — 检查点所呈现的东西：一份紧凑、可直接决策的摘要——产出了什么、为什么，以及一个指向产物本身的链接——绝不是原始输出。用户读的是简报，不是草稿。评审的速度至关重要。

Definition of done（完成定义）

一个 workflow 规格在实施者（implementer）agent 无需问出任何一个问题就能把它构建出来时，才算完成。拷问到那一刻为止；只要还有一个问题悬而未决，就什么都不算完成。

The workspace（工作区）

  • workflows/*.md — 每个 workflow 一份规格。
  • NOTES.md — 关于用户世界的原始笔记：他们使用的工具、他们处理的渠道，以及他们自己对这两者的叫法。当它为空或内容单薄时，在写出任何规格之前先就他们的世界进行访谈。当模糊的术语浮出水面时，把它们打磨成规范的术语，并记录在这里。

writing-beats（写作节拍）

把一篇文章塑造成一段节拍之旅，采用"选择你自己的冒险"风格。挑一个起始节拍，只写那个节拍，然后转向下一个，直到文章抵达自然的终点。

name: writing-beats
description: Writing, exploit — assemble raw material into a journey of beats, grounding each term before a beat leans on it.
disable-model-invocation: true

用户已经（或将要）传入一份原始素材的 markdown 文件。这是 exploit（开采） 阶段：探索已完成，素材堆是固定的——选定一条穿越它的路径，然后开采素材堆去填满每个节拍（beat）。

如果用户没有说明文章保存到哪里，问一次并记住该路径。

然后以"选择你自己的冒险"（choose-your-own-adventure）风格，按节拍一段一段地推进旅程：

  1. 确立前提（prerequisites）。 在写出任何节拍之前，先与用户敲定读者入场时已经知道什么——即从一开始就被奠基（grounded）的概念。其余一切概念，必须由某个节拍先奠定，之后的节拍才能使用它。参见 Grounding（概念奠基）。
  2. 写出 2–3 个候选的起始节拍（starting beats），取材于原始素材。每个都是进入文章的不同入口。每个起始节拍只能依赖已奠基的概念；标注出每个节拍各自奠定了哪些新概念。在写入文章文件之前，先把节拍展示给用户。由用户挑一个。预告选中该节拍会解锁哪些后续节拍——就像让用户提前看到一小段前路。
  3. 一旦用户选定起始节拍，只把那个节拍写入文章文件。一个节拍可以是一个句子，也可以是若干段落——取决于那个节拍天然的样子。就此打住。
  4. 从磁盘上重新读取文章文件。然后给出 2–3 个候选的后续节拍（next beats）——从文章当前所处位置，旅程可以转向的不同方向。每个候选都必须能由当前已奠基的集合到达；标注出每个节拍各自奠基了什么。
  5. 循环执行第 3–5 步，直到文章抵达自然的终点。

Grounding（概念奠基）

每个概念（concept）在被某个节拍依赖之前，都必须先被奠基（grounded）：读者要么入场时已经知道它，要么在更早的节拍里遇到过它。一个节拍伸手去够一个未奠基的概念，就会失去读者——这是整段旅程唯一不能做的一步。单位是概念本身，而不是它的说法：即使毫无术语痕迹，一个节拍也可能依赖读者并不具备的想法。当一个概念有名字——即术语（term）——奠基意味着把想法和术语一起落地。

一个概念通过两种方式之一获得奠基：

  • 前提（Prerequisite） — 在第一个节拍之前奠基。由读者自带。在一开始就固定下来。
  • 引入（Introduced） — 由某个节拍建立，从此它对之后的所有节拍都视为已奠基。

所以每个节拍承担两件事：它依赖（requires）那些已经奠基的概念，同时奠基（grounds）新的概念。持续维护一份"迄今已奠基"的清单，每落下一个节拍就更新一次。

这正是塑造"选择你自己的冒险"的东西。一个候选节拍只有在它所依赖的一切都已奠基时才能被到达；挑选一个奠基了概念 X 的节拍，就会解锁所有一直在等 X 的节拍。当你给出后续节拍时，它们必须全部能从当前已奠基的集合到达——并且说明每个节拍奠基了什么，好让用户看到它打开了哪些路径。

最大的杠杆在于：你究竟把什么设为前提、把什么放进文章内部去奠基。前置要求提得太多，就会把不具备这些前提的读者挡在门外；在文章内部奠基得太多，开头的节拍就会被定义淹没。在确立前提时与用户敲定这一点，并每当某个诱人的节拍恰好需要某个尚无任何节拍奠基过的概念时，回头重新审视——修法要么是在它之前补一个奠基节拍，要么是把该概念提升为前提。

What is a beat（什么是节拍）

一个节拍是旅程中的一步。它只做一件事——铺开场景、落下一个观点、提出一个问题、插一句旁白、扭转一个角度。然后它停下，把读者留在某个可以让下一个节拍转向的位置。

一个节拍的大小取决于它需要什么：

  • 一个句子，如果这一步仅此而已（"然后整整三周什么都没发生。"）。
  • 一个短段落，如果这一步需要铺垫。
  • 多个段落，如果这个节拍是一个自足的片段、论证或例子。

如果一个"节拍"需要五个段落和三个小标题，那它就不是一个节拍——它是两个节拍粘在了一起。拆开它。

Pulling from the pile（从素材堆中取材）

从原始素材堆中取材来填充每个节拍。你可以改写、拆分、重组或引用。素材堆就是一座采石场。

Ending the journey（结束旅程）

文章在旅程完成时结束——而不是在素材堆耗尽时结束。大多数素材堆都会剩下没被用进去的零散片段。这没关系；这正是"拥有比所需更多的原始素材"的意义所在。

Writing rhythm（写作节奏）

  • 一次只追加一个节拍。绝不超前写作。
  • 每次写入前都从磁盘重新读取文章文件。绝对保留用户的编辑。
  • 如果用户大幅修改了之前的某个节拍，就让它改变接下来发生的事。
  • 如果用户说"重写那个节拍"或"回去换一个不同的节拍 3"，照做——就地编辑，其余部分别动。

What is a fragment（什么是片段）

片段（fragment）是任何有可能活进最终文章的文字片段。它必须_能被作者自己读懂_——作者能看出它是什么意思——但它不必界定自己的术语，也不必让一个冷读者能看懂。标准是"这是一段好文字吗？"，而不是"这是一个自洽的论证吗？"

片段刻意地是异质性的。能算作片段的例子包括：

  • 一个你想在某个地方用上、但还不知道用在哪儿的一针见血的句子。
  • 一个带一行论证的论断。
  • 一个速写（vignette）：一件发生过的事、一段代码片段、一个场景、一个类比。
  • 一个半成品想法："关于 X 如何让人感觉像 Y 的东西，以后再说。"
  • 一句引言、一段对话、一句偷听到的话。
  • 一串靠感觉聚拢在一起的相关观察。
  • 一句抱怨、一段自白、一个笑点。
  • 一个领衔词（leading word）——一个能让整篇文章挂靠在上面的精炼隐喻或新造词（一个能命名整个想法的术语，就像 tracer bullets（曳光弹） 或 fog of war（战争迷雾） 命名了整整一种模式那样）。

其中，领衔词是最值得落地的片段。它是承重墙：在 explore 阶段命名对了，它就会在后来塑造结构、过渡和标题——在整个 exploit（开采）阶段持续带来红利。当对话反复围绕某个反复出现的想法打转时，推动为它造一个词。

小说家的日记是范式：经年累月、毫无结构的观察笔记，日后被开采出来当作原始素材。片段就是这样的观察笔记。

File format（文件格式）

# Working title

A first fragment lives here.

It can be multiple paragraphs. It can include lists, code, quotes — whatever
shape the fragment naturally takes.

---

A second fragment.

---

> A quoted line that the user wants to keep around.

A reaction to it.

---

- A cluster of related observations
- That hang together by feel
- And want to be near each other

片段之间用水平分隔线（\n---\n）隔开。正文内不设标题。不带标签。除了加入顺序之外不排序。

Writing rhythm（写作节奏）

安静地追加。不要为每个片段请求许可。顺带提一句你加了什么（"加上那个"），但不要用保存对话框打断对话。

每次写入前：从磁盘重新读取文件。用户可能在两轮之间编辑、重排或删除了片段——保留他们的改动。绝不覆盖文件；只追加（或者，如果用户要求，就地对某个特定片段做编辑）。

用户可以随时说"删掉最后一个"、"把那句改得更犀利"、"把那两个合并"。把这类指令当作一等公民处理。

writing-shape（写作塑形）

把一份原始素材的 markdown 文件逐段塑形成一篇文章，在每一步都就格式选择展开论证。

name: writing-shape
description: Writing, exploit — shape raw material into an article, paragraph by paragraph.
disable-model-invocation: true

用户已经（或将要）传入一份原始素材的 markdown 文件。把它当作输入素材堆——无论是一份整齐的片段清单、一墙无结构的散文，还是一份转录稿，格式都不重要。在做任何其他事情之前，先从头到尾读一遍。

然后运行一场塑形（shaping）会话，产出一份独立的文章文档。这是 exploit（开采） 阶段：探索已完成，素材堆是固定的——选定一个结构，然后开采素材堆去填充它。不要编辑原始素材文件——对这个技能来说它是只读的。

如果用户没有说明文章保存到哪里，问一次并记住该路径。

The loop（工作循环）

  1. 通读素材堆。 完整读取输入文件。对里面有什么形成感知。
  2. 确立前提。 与用户敲定读者入场时已经知道什么——即从一开始就被奠基（grounded）的概念。其余一切概念，必须由某个块（block）先奠基，之后的块才能依赖它。参见 Grounding（概念奠基）。
  3. 起草 2–3 个候选开头。 每个开头应当暗示文章不同的论点或角度。全部展示出来。迫使用户挑选一个，或拼出一个混合体。被选中的开头定义了文章其余部分必须做什么。
  4. 一段一段地生长。 开头落定后，问"鉴于这个开头，读者下一步需要听到什么？"从素材堆中取材来回答。下一个块只能依赖已奠基的概念，并在落地时奠基新的概念。就下一个块采取的形式展开论证——一段文字、一个列表、一张表格、一个提示框、一句引言、一段代码块。每个格式选择都应当是深思熟虑、站得住脚的。
  5. 边写边追加到文章文件。 不要批量处理。每个达成一致的段落或块都立刻写入，好让用户看到文章逐步成形。
  6. 循环执行第 4 步，直到文章完成。 由用户决定何时完成。

Grounding（概念奠基）

每个概念（concept）在被某个块依赖之前，都必须先被奠基（grounded）：读者要么入场时已经知道它，要么在更早的块里遇到过它。一个块伸手去够一个未奠基的概念，就会失去读者。单位是概念本身，而不是它的说法——即使毫无术语痕迹，一个块也可能依赖读者并不具备的想法。当一个概念有名字——即术语（term）——奠基意味着把想法和术语一起落地。

一个概念通过两种方式之一获得奠基：

  • 前提（Prerequisite） — 在开头之前奠基。由读者自带。在一开始就固定下来。
  • 引入（Introduced） — 由某个块建立，从此它对文章其余部分都视为已奠基。

持续维护一份"已奠基"的清单。当你问"读者下一步需要听到什么？"时，下一步动作所缺的某个未奠基概念本身就是答案：先奠基它——在这里，或在更早的块里——否则你就无法迈出这一步。这就是把 Pulling from the pile（从素材堆中取材） 里的"点名缺口"再抬高一个层级：在那里，素材堆缺的是材料；在这里，文章缺的是地基。

杠杆在于：你究竟把什么设为前提、把什么放进文章内部去奠基。前置要求提得太多，就会把读者挡在门外；在文章内部奠基得太多，开头就会被定义淹没。在确立前提时与用户敲定这一点。

Conversational feel（对话感）

这是一场反转的拷问（grilling）会话。在构思（ideation）阶段，问题曾是"你实际上注意到了什么？"在这里则变成"这篇文章实际上在论证什么，读者需要按什么顺序听到它？"要顶回去。绝不让软弱的过渡蒙混过关。如果一个段落配不上它的位置，就砍掉它。

要反复使用的一些具体招数：

  • "这个段落为读者做了什么，是前一段没做到的？"
  • "如果我把这段砍掉，什么会坏掉？"
  • "这是散文，还是应该改成列表？为什么是散文？"
  • "这个句子在干两件事——拆开它，或者选一件。"
  • "开头许诺了 X。我们漂移到了 Y。要么重新穿线，要么改开头。"

Pulling from the pile（从素材堆中取材）

把原始素材当作采石场，而不是剧本。取来一个片段，改造成贴合周边段落的样子，再放进去。一个片段可以被拆开分进多个段落、与另一个合并，或者改写。素材堆的职责是被开采；文章的职责是读起来像同一个人的声音。

如果素材堆缺少文章需要的东西，明确地点出缺口："这里需要一个例子，但素材堆里没有——现在给我一个，否则我们砍掉这一节。"

Format arguments to actually have（值得真正展开的格式论证）

在选择如何渲染一个块时，与用户当面权衡这些取舍，而不是默默决定：

  • 散文 vs. 列表。 散文承载论证；列表承载并列项。如果各项并非真正并列，散文更好。如果它们确实并列，列表扫读起来更快。
  • 行内 vs. 提示框。 提示、警告和题外话放进提示框（> [!TIP]、> [!NOTE]）——但仅当它们以行内形式呈现会真的冲淡主线论证时才如此。否则就留在行内。
  • 表格 vs. 重复结构。 如果同一种形状用相同字段重复了 3 次以上，就用表格。否则用带加粗起头的散文。
  • 引用 vs. 转述。 当原文措辞本身就是重点时，引用。当只有想法要紧时，转述。
  • 代码块 vs. 行内代码。 多行、可运行或示意性的 → 代码块。单个 token 或标识符 → 行内。

Writing rhythm（写作节奏）

每敲定一个块就追加到文章文件。每次写入前都从磁盘重新读取文件——用户可能在两轮之间做过编辑。绝不盲目覆盖。如果用户想重写某个段落，就地对那个特定段落做编辑；其余部分别动。

Out of scope（不在职责范围内）

  • 开采素材堆里没有的新片段（按"从素材堆中取材"一节处理缺口）。
  • 编辑原始素材文件。
  • 发布、为特定平台排版，或添加用户没要求的 frontmatter。

claude-handoff（Claude 交接）

把当前会话移交给一个全新的后台 agent，让它立即接手工作，用 claude --bg 以交接摘要作为种子提示。由用户调用。

name: claude-handoff
description: Hand the current conversation off to a fresh background agent that picks up the work immediately.
argument-hint: "What will the next session be used for?"
disable-model-invocation: true

写一份当前会话的交接摘要（handoff summary），让一个全新的 agent 能继续这项工作。与其把它保存下来，不如启动一个以该摘要作为其提示词（prompt）的后台 agent：claude --bg --name "<descriptive name>" "<handoff summary>"。它在当前工作目录中启动并立即返回；用户通过 claude agents 管理它。

始终传入带描述性名称的 -n/--name（例如 --name "Fix login bug"）——它设置在任务列表、会话选择器和终端标题中显示的显示名称。

在摘要中包含一个"suggested skills（建议使用的技能）"小节，指明下一个 agent 应当调用 Skill 工具获取哪些技能。

不要重复其他产物（specs、plans、ADRs、issues、commits、diffs）中已捕获的内容。改为通过路径或 URL 引用它们。

隐去任何敏感信息，例如 API 密钥、密码或可识别个人身份的信息——因为该摘要会成为 agent 的提示词。

如果用户传入了参数，把它们当作对下一个会话将聚焦于什么的描述，并据此定制摘要。

disable-model-invocation: true

Setup TS Deep Modules（搭建 TS 深模块）

让本仓库中的每个包（package）都成为一个深模块（deep module）：大量行为收拢在一个小接口后面。一个包的公共表面就是它的入口点（entry points）——即包根目录下的那些文件——而它在子文件夹里的所有东西都是隐藏的。本技能会安装 dependency-cruiser 以及让入口点成为唯一入口的规则，然后验证这些规则确实会咬人（确实能拦截违规）。

关于词汇（deep module 深模块、interface 接口、seam 接缝、depth 深度），用 "codebase-design" 调用 Skill 工具——全程使用它的语言。

The shape this enforces（本技能强制出的结构）

src/packages/
  <name>/
    index.ts        ← an entry point (public). Import this from outside.
    client.ts       ← another entry point. Packages may expose SEVERAL.
    lib/            ← implementation: hidden from outside, free to import each other.
    tests/          ← co-located tests + fixtures (a subfolder, so private).

公共表面是包的根文件（root files）——而不是某一个被指定的 index.ts。按惯例，实现放在 lib/、测试放在 tests/，让每个包都有同样的双文件夹结构。不过规则本身是通用的：任何子文件夹里的任何东西都是私有的，所以你永远不必为新增文件夹去扩展配置。

四条规则，均为 error 级别：

  1. 入口点边界（Entry-point boundary） — 包之外（应用代码或另一个包）的代码只能导入该包的入口点（其根文件），绝不能导入其子文件夹中的任何东西。
  2. 包内自由（Intra-package freedom） — 包自身的文件之间可以自由地互相导入。
  3. 经由入口点做测试（Tests through the entry points） — <pkg>/tests/ 下的文件可以导入任意包的入口点以及它们自己的 tests/ fixtures，但绝不能导入任何包的子文件夹内部（连自己的也不行）。跨包的集成测试没问题；深层导入（deep imports）不行。
  4. 无循环（No cycles） — 不允许出现依赖循环。

入口点，而不是 barrel 桶文件。 由于公共表面是每一个根文件，一个包可以暴露若干个小的入口点（index.ts、client.ts、server.ts），而不是把一切都塞进一个巨大的 index.ts。不鼓励那种把整个子树重新导出的 barrel 文件——保持入口点小而精，把实现藏进子文件夹。

分层（哪个包可以依赖哪个包）是另一个关注点，已在配置中留作注释桩（commented stub），由本仓库自行填写。

Steps（步骤）

1. Detect the environment（检测环境）

  • 包管理器（Package manager） — pnpm-lock.yaml → pnpm，yarn.lock → yarn，bun.lockb → bun，否则是 npm。下面每条命令都用它（pnpm/yarn/npm run/bunx）。
  • 包根目录（Packages root） — 如果存在 src/ 就用 src/packages，否则用 packages。如果仓库已经有不同的明显惯例，与用户确认这一选择。
  • 已有配置（Existing config） — 检查是否存在 .dependency-cruiser.* 文件。如果存在，不要覆盖它：把四条规则和选项合并进去，并告诉用户你加了什么。

完成条件（Done when）： package manager、packages root 和已有配置的状态均已明确。

2. Install dependency-cruiser（安装 dependency-cruiser）

用检测到的包管理器把 dependency-cruiser 安装为 devDependency。

完成条件（Done when）： dependency-cruiser 出现在 devDependencies 中。

3. Write the config（编写配置）

把 dependency-cruiser.config.cjs 复制到仓库根目录，命名为 .dependency-cruiser.cjs。把 PACKAGES_ROOT 设为第 1 步检测到的根目录。规则基于路径深度且与扩展名无关，所以其余部分无需任何改动。

完成条件（Done when）： .dependency-cruiser.cjs 已存在且 PACKAGES_ROOT 正确，四条禁止规则都在其中。

4. Wire it into the checks（把它接入检查流程）

  • 添加一个 lint:boundaries 脚本：depcruise <packages-root>（或 depcruise src）。
  • 把它并入仓库的总检查命令——即那条已经会跑 typecheck 的命令（例如 check / ci / validate 脚本）。不要改动 tsconfig，也不要添加路径别名。
  • 如果没有总脚本，就添加 lint:boundaries 并告诉用户把它纳入 CI。

完成条件（Done when）： lint:boundaries 存在，并且与 typecheck 在同一个命令中运行。

5. Scaffold the example package（搭建示例包）

创建一个已提交的 <packages-root>/example/，作为"复制我"模板：

  • index.ts — 一个入口点。导出一个委托给内部文件的函数（这样这个包看起来才是深的，而不是一个透传层）。
  • lib/impl.ts — 位于子文件夹中的内部文件，由 index.ts 导入，外部不可达。
  • tests/example.test.ts — 只导入 ../index（一个入口点），并针对公开函数做断言。

告诉用户这是一个可供复制或删除的入门模板。

完成条件（Done when）： 示例包存在，通过根入口点暴露其行为，并把 impl 藏在子文件夹中。

6. Prove the rules bite（证明规则确实咬人）

这是整个技能的完成判据——一条在违规时不报错的配置一文不值。

  1. 运行 lint:boundaries。它必须在干净的示例上通过。
  2. 临时在 tests/example.test.ts 里加一个深层导入（例如 import { thing } from "../lib/impl"）。再次运行 lint:boundaries——它必须带着 tests-through-entrypoints 失败。
  3. 撤销那个深层导入。再运行一次——它必须通过。

完成条件（Done when）： 你观察到了一次通过、一次对深层导入的失败、再一次通过。如果第 2 步没有失败，说明规则没有正确接线——在收尾前先修好。

7. Document the convention（记录这一约定）

在包文件夹内（<packages-root>/README.md）写一个 README.md——就放在它所管辖的包旁边——内容涵盖：src/packages/<name>/ 的布局（入口点在根目录，lib/ 放实现，tests/ 放测试）、"只能通过包的入口点（其根文件）导入"、以及如何运行 lint:boundaries。明确不鼓励 barrel 文件——宁可暴露几个小的入口点，也不要通过一个 index 重新导出整个子树。把它压缩成"复制我"片段加上四条规则，每条各一段。

然后从仓库的 agent 指令文件——有 CLAUDE.md 就用它，否则用 AGENTS.md（如果两者都不存在就创建 AGENTS.md）——加一个上下文指针（context pointer）指向它。一行就够，例如 Packages are deep modules — see [src/packages/README.md](./src/packages/README.md) before adding or importing one. 这才能让 agent 主动发现边界规则，而不是一头撞上去。

完成条件（Done when）： <packages-root>/README.md 存在并明确不鼓励 barrel，且仓库的 CLAUDE.md/AGENTS.md 链接到它。

Notes（备注）

  • 配置里的 $1 反向引用（dependency-cruiser 的分组匹配）正是让一个包能触达自己的内部、而外部人不能的关键——不要把它们摊平成分拆开来的逐包规则。
  • 公开 vs. 私有的裁决依据是深度（depth）：包的根文件是入口点；子文件夹里的任何东西都是私有的。惯用的子文件夹是 lib/（实现）和 tests/，但规则并没有把它们写死——任何子文件夹都是私有的，所以新增文件夹永远不需要改配置。新增一个入口点就是新增一个根文件——不需要 barrel。
  • 包是扁平（flat）的：根下只有一层直接子级。包的内部可以随你嵌套多深；但一个包不能包含另一个包。
  • 使用 .cjs（而不是 .js），这样即使在 "type": "module" 的仓库里，配置的 module.exports 也能工作。
