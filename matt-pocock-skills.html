📖 概述

🎯 核心理念

为真实工程项目设计的 Agent 技能，强调软件工程基础、清晰沟通和可维护的代码架构。不是"vibe coding"，而是基于数十年工程经验的最佳实践。

✨ 设计特点

技能是小型、易适配、可组合的。与任何模型配合使用，不绑定特定 AI 工具。用户可以保持完全控制权。

🚀 快速开始

运行 npx skills@latest add mattpocock/skills 选择技能并安装，然后运行 /setup-matt-pocock-skills 配置项目。

🎯 解决的四大核心问题

问题 #1: Agent 没有按我想要的方式工作

原因: 用户和 Agent 之间的对齐缺失

✅ 解决方案: grill-me / grill-with-docs - 通过严格访谈对齐认知

问题 #2: Agent 太啰嗦

原因: Agent 不理解项目术语

✅ 解决方案: 创建共享语言文档 (CONTEXT.md)，使用 caveman 模式压缩通信

问题 #3: 代码不工作

原因: Agent 生成代码后缺少反馈循环

✅ 解决方案: diagnose (调试循环) + tdd (测试驱动开发)

问题 #4: 代码变成泥球

原因: 没有关注代码设计

✅ 解决方案: improve-codebase-architecture + zoom-out + to-prd

🔧 工程技能详解

这些技能用于日常开发工作，需要在每个仓库中先运行 setup-matt-pocock-skills 配置。

🚀 初始配置

S

setup-matt-pocock-skills

必需前置 配置向导

功能: 为仓库配置 Agent 技能的基础设施，生成配置文件。

三步引导式配置:

  • 问题跟踪器 (Issue Tracker): 选择 GitHub / GitLab / 本地 Markdown / 其他
  • 分类标签词汇表: 配置 triage 状态机的标签映射
  • 领域文档布局: 单上下文 (CONTEXT.md) 或多上下文 (CONTEXT-MAP.md)

输出文件:

  • CLAUDE.md 或 AGENTS.md (写入 Agent skills 配置块)
  • docs/agents/issue-tracker.md (问题跟踪器配置)
  • docs/agents/triage-labels.md (标签映射)
  • docs/agents/domain.md (领域文档布局)

🎯 对齐与规划

G

grill-with-docs

核心技能 领域建模

功能: 通过严格访谈挑战你的计划，对照现有领域模型锐化术语，并内联更新文档 (CONTEXT.md, ADRs)。

核心流程:

  • 对每个计划方面进行 relentless 访谈，直到达成共同理解
  • 沿着设计树的每个分支走查，逐一解决决策依赖关系
  • 为每个问题提供推荐答案
  • 一次问一个问题，等待反馈后再继续

文档更新规则:

  • 术语解决时立即更新 CONTEXT.md
  • 仅在满足三个条件时创建 ADR (架构决策记录)
  • 条件: 难以逆转 + 没有上下文会令人惊讶 + 存在真实权衡
P

to-prd

PRD生成 自动化

功能: 将当前对话上下文转换为 PRD (产品需求文档) 并发布到问题跟踪器。不需要访谈 - 直接综合已有信息。

PRD 模板结构:

  • 问题陈述 - 从用户角度描述问题
  • 解决方案 - 从用户角度描述解决方案
  • 用户故事 - 很长的编号列表 (As an <actor>, I want...)
  • 实现决策 - 模块、接口、架构决策、模式变更、API 契约
  • 测试决策 - 测试策略、哪些模块将被测试
  • 范围外 - 此 PRD 不涵盖的内容

重要约束: 不要包含特定文件路径或代码片段 (容易过时)。例外: 原型生成的代码片段如果比散文更精确，可以内联。

I

to-issues

任务分解 垂直切片

功能: 使用 tracer-bullet 垂直切片将计划/规格/PRD 分解为可独立获取的 GitHub Issues。

垂直切片 vs 水平切片:

  • ❌ 水平切片 (错误): 先写所有测试，再写所有实现 - 测试的是"形态"而非用户行为
  • ✅ 垂直切片 (正确): 每个切片贯穿所有层 (架构、API、UI、测试)，是完整但薄的端到端路径

切片类型:

  • HITL (Human In The Loop): 需要人机交互 (架构决策、设计审查)
  • AFK (Away From Keyboard): 可以在无需人机交互的情况下实现和合并

优先选择 AFK 而非 HITL

🧪 质量与测试

T

tdd

核心技能 测试驱动

功能: 测试驱动开发，遵循红-绿-重构循环。一次一个垂直切片地构建功能或修复 bug。

核心理念: 测试应该通过公共接口验证行为，而非实现细节。代码可以完全改变，但测试不应改变。

好的测试特征:

  • 采用集成式风格: 通过公共 API 测试真实代码路径
  • 描述系统做什么，而非怎么做
  • 读起来像规范说明
  • 在重构后仍然有效

工作流程:

  • 规划: 确认接口变更、测试哪些行为、识别深度模块机会
  • 追踪子弹: 写一个测试确认一件事 (RED → GREEN)
  • 增量循环: 对每个剩余行为 (RED → GREEN)
  • 重构: 所有测试通过后，提取重复代码、深化模块

重要规则: 永远不要在 RED 状态下重构！

D

diagnose

核心技能 调试

功能: 针对疑难 bug 和性能回归的规范化诊断流程: 复现 → 最小化 → 假设 → 插桩 → 修复 → 回归测试。

核心原则: 反馈循环是王道

  • 没有可靠的可重运行机制，不要开始调试
  • 目标: 建立一个快速、确定性、可由 agent 运行的通过/失败信号

构建反馈循环的方法 (按优先级):

  • 1. 失败的测试 (单元测试、集成测试、端到端测试)
  • 2. Curl / HTTP 脚本 (针对运行中的开发服务器)
  • 3. CLI 调用 (使用固件输入，比较输出快照)
  • 4. 无头浏览器脚本 (Playwright / Puppeteer)
  • 5. 重放捕获的跟踪
  • 6. 一次性工具套件
  • 7. 属性/模糊循环
  • 8. 二分法工具套件 (git bisect run)
  • 9. 差异循环 (旧版本 vs 新版本)
  • 10. HITL bash 脚本 (最后手段)

诊断阶段:

  • Phase 1: 建立反馈循环 (投入不成比例的努力)
  • Phase 2: 复现 (确认 bug 可重现)
  • Phase 3: 假设 (生成 3-5 个可证伪的假设)
  • Phase 4: 插桩 (一次只改变一个变量)
  • Phase 5: 修复 + 回归测试
  • Phase 6: 清理 + 事后分析

🏛️ 架构与设计

A

improve-codebase-architecture

架构改进 重构

功能: 在代码库中寻找深化机会 - 将浅层模块转变为深层模块，提高可测试性和 AI 可导航性。

核心术语 (必须使用精确术语):

  • 深度 (Depth): 接口背后的大量行为。Deep = 高杠杆
  • 接缝 (Seam): 接口所在的位置；可以在不就地编辑的情况下改变行为的地方
  • 一个适配器 = 假设接缝。两个适配器 = 真实接缝

删除测试 (Deletion Test):

  • 想象删除模块。如果复杂性消失，它是传递模块
  • 如果复杂性出现在 N 个调用者中，它在发挥作用

工作流程:

  • 步骤 1: 探索 - 注意遇到摩擦的地方 (理解需要跳转多个模块、模块浅层、无局部性等)
  • 步骤 2: 呈现候选方案 - 使用 CONTEXT.md 词汇表和精确术语
  • 步骤 3: 追问循环 - 与用户一起遍历设计树

副作用 (内联发生): 更新 CONTEXT.md、创建 ADR、锐化模糊术语

Z

zoom-out

全局视角 代码理解

功能: 告诉 Agent 放大视野，提供更广泛的上下文或更高层次的视角。当你不熟悉某段代码或需要理解它如何融入更大图景时使用。

指令: "I don't know this area of code well. Go up a layer of abstraction. Give me a map of all the relevant modules and callers, using the project's domain glossary vocabulary."

使用场景:

  • 不熟悉某段代码区域时
  • 需要理解代码如何融入更大系统时是
  • 需要高层次视角时
R

prototype

原型 设计验证

功能: 构建可丢弃的原型来冲刷设计。用于验证设计决策、测试用户体验流程。

原型类型:

  • 可运行终端应用: 用于状态/业务逻辑验证
  • 多个 radically 不同的 UI 变体: 从一个路由切换，用于 UI/UX 设计验证

关键原则: 原型是可丢弃的 - 目标是快速验证设计，而不是构建生产代码。

📋 工作流管理

T

triage

Issue管理 状态机

功能: 通过分类角色驱动的状态机对 issue 进行分类。

两个类别角色:

  • bug - 某些功能损坏
  • enhancement - 新功能或改进

五个状态角色:

  • needs-triage - 维护者需要评估
  • needs-info - 等待报告者提供更多信息
  • ready-for-agent - 完全指定，准备好给 AFK agent
  • ready-for-human - 需要人类实施
  • wontfix - 不会采取行动

分类流程:

  • 1. 收集上下文 (阅读 issue、探索代码库、检查 .out-of-scope/)
  • 2. 推荐类别和状态 (向维护者展示推理)
  • 3. 复现 (仅限 bugs - 尝试复现并报告)
  • 4. 询问 (如果需要充实，运行 /grill-with-docs 会话)
  • 5. 应用结果 (应用角色、发布代理简介或分类笔记)

重要规则: 每个分类的 issue 必须以此免责声明开头: *This was generated by AI during triage.*

⚡ 效率技能详解

这些技能用于通用工作流，提高沟通和生产力。

C

caveman

压缩通信 Token优化

功能: 超压缩通信模式，通过删除填充词、冠词和客套话来减少约 75% 的 token 使用，同时保持完整的技术准确性。

删除内容:

  • 冠词 (a/an/the)
  • 填充词 (just/really/basically/actually/simply)
  • 客套话 (sure/certainly/of course/happy to)

表达模式: [thing] [action] [reason]. [next step].

示例:

  • 问题: "Why React component re-render?"
  • 回答: "Inline obj prop -> new ref -> re-render. useMemo."

自动澄清例外 (暂时退出 caveman 模式):

  • 安全警告
  • 不可逆操作确认
  • 多步骤序列
  • 用户要求澄清或重复问题
G

grill-me

压力测试 计划验证

功能: 对用户关于计划或设计的各个方面进行 relentless 访谈，直到达成共同理解。用于非代码场景。

与 grill-with-docs 的区别:

  • grill-me: 基础版，用于非代码场景
  • grill-with-docs: 高级版，带有文档更新 (CONTEXT.md, ADRs)

核心机制:

  • relentless 访谈 - 对计划的每个方面进行持续深入的询问
  • 决策树遍历 - 沿着设计决策树的每个分支走查
  • 依赖关系解决 - 逐一解决决策之间的依赖关系
W

write-a-skill

技能创建 扩展

功能: 创建新技能，具有适当的结构、渐进式披露和捆绑资源。

使用场景:

  • 想要创建自己的 Agent 技能时
  • 想要扩展现有技能系统时需要
  • 想要为特定工作流创建可重用技能时

📚 关键概念词汇表

🔍 垂直切片 (Vertical Slice)

贯穿所有层 (架构、API、UI、测试) 的端到端薄切片。每个切片是完整但独立的，可以独立演示或验证。

🔍 水平切片 (Horizontal Slice)

❌ 反模式: 先写所有测试，再写所有实现。测试的是"形态"而非用户行为。

🔍 深度模块 (Deep Module)

小接口、深实现。接口背后封装大量功能，调用者只需了解少量接口即可使用大量行为。

🔍 浅层模块 (Shallow Module)

接口几乎与实现一样复杂。调用者需要了解几乎所有实现细节才能使用。

🔍 接缝 (Seam)

接口所在的位置。可以在不就地编辑的情况下改变行为的地方。一个适配器 = 假设接缝，两个适配器 = 真实接缝。

🔍 追踪子弹 (Tracer Bullet)

编写一个测试来确认系统的一件事 (RED → GREEN)。证明路径端到端可行，然后在此基础上增量构建。

🔍 CONTEXT.md

共享领域语言文档。定义项目中的术语、概念及其关系，确保 Agent 和人类使用相同的词汇。

🔍 ADR (Architecture Decision Record)

架构决策记录。仅在满足三个条件时创建: 难以逆转、没有上下文会令人惊讶、存在真实权衡。

🔍 HITL vs AFK

HITL (Human In The Loop): 需要人机交互。
AFK (Away From Keyboard): 可以在无需人机交互的情况下实现。

💡 最佳实践与建议

📌 建议 #1: 始终先运行 setup-matt-pocock-skills

在开始使用任何工程技能之前，确保已配置问题跟踪器、分类标签和领域文档布局。这将为后续所有技能提供正确的上下文。

📌 建议 #2: 使用 grill-with-docs 建立共享语言

在项目开始时，通过与 Agent 的严格访谈建立 CONTEXT.md。这将显著减少后续沟通中的术语混淆，提高 Agent 输出的准确性。

📌 建议 #3: 优先使用垂直切片而非水平切片
