原文：[How to Kill the Code Review](https://www.latent.space/p/reviews-dead) by Ankit Jain (Aviator Founder)

人类代码审查已死。2026 年，是 AI 代码审查的终结年。

我们一直欺骗自己

每个工程团队都有一个不能说的秘密：

  • PR 堆积数天无人 review
  • 审查者快速浏览 500 行 diff，然后橡皮图章式通过
  • "这是质量门禁" —— 但事实上，没有逐行 review 就发版的情况已经持续了十年

Code review 甚至在 2012-2014 年才真正普及，之前没有足够多的人记得罢了。

AI 让问题更糟

来自 Faros AI 的数据显示：

  • 高 AI 采纳团队：任务完成 +21%，PR 合并 +98%
  • 但 PR 审查时间增加 91%

两个指数级增长：

  • 变更的数量 增长
  • 变更的规模 增长
"我们无法消费这么多代码。"

而且，开发者普遍认为：review AI 生成的代码比 review 同事写的代码更累。团队产出更多代码，然后花更多时间审查。

AI Review 只是延缓死亡

AI code review 工具只是买时间。如果 AI 写代码，AI 审代码，为什么还需要一个漂亮的 review UI？

Post-PR review 的逻辑是"需要 fresh eyes"，但当 agent 写代码时，"fresh eyes" 只是另一个有同样盲点的 agent。

"We know from experience agents are not always reliable, and it's very human to think, I caught the AI doing something dumb once; therefore, I must always check it."

这个想法在人工验证可行的时代是对的。但在当前规模下，已经不可能了。而且只会越来越糟。

真正的解决方案：从 Review Code 到 Review Intent

答案是：把人类检查点往上游移动。

Spec 成为新的 Source of Truth

如果"不审查代码"听起来可怕，想想 checkpoint 之前也移动过：

  • 从瀑布流签收 → 持续集成
  • 现在再一次移动
Spec-driven development 正在成为与 AI 协作的主要方式。
  • 人应该 review spec、计划、约束、验收标准
  • 而不是 500 行 diff
  • 代码成为 spec 的产物
  • 人 review 的不是代码本身，而是步骤，是 verification rules，是合约
"Human-in-the-loop approval moves from 'Did you write this correctly?' to 'Are we solving the right problem with the right constraints?'"

最有价值的人类判断，应该在第一行代码生成之前行使，而不是之后。

五层信任体系：Swiss-Cheese Model

代码必须不由人写，代码必须不由人 review。但 LLM 不擅长遵循命令，它们会偏离，它们对自己的验证也不可靠。

解决方案：叠加 imperfect filters，直到洞不再对齐。

Layer 1: 多选对比

让三个 agent 用不同方式尝试，选最好的结果。optionality 的成本是软件工程历史上最低的。

Selection 可以不手动：用输出通过最多验证步骤的排名、用 diff 最小的、用不引入新依赖的。

Layer 2: 确定性 Guardrails

应该有确定性方式验证工作：测试、类型检查、contract verification —— 没有观点，只有事实。

验证步骤应该在代码写之前定义，而不是之后为了确认已存在的东西而发明。

"If the agent writes both the code and the tests, you've just moved the problem."

Verification criteria 需要来自 spec，而不是 implementation。

Layer 3: 人类定义验收标准

这是 BDD (Behavior-Driven Development) 复兴的时刻。

BDD 一直是好主意：用自然语言写规格，描述预期行为，然后自动化这些规格为测试。但以前写规格像是额外工作——因为还要写代码。

有了 agent，公式变了。spec 不是额外工作；它是主要产物。
  • Agent 实现
  • BDD 框架验证
  • 只有失败时才需要读实现
"Humans do what humans are good at: defining what 'correct' means, encoding business logic and edge cases, thinking about what could go wrong."

Layer 4: 权限系统架构化

这个 agent 能碰什么？什么需要升级？

  • 大多数 agent 框架权限是全有或全无
  • 粒度很重要：修 utils/dates.py 的 bug，不需要访问整个代码库
  • 敏感模式（auth logic、database schema、新依赖）应该自动标记人工 review

Layer 5: 对抗性验证

一个 agent 干活，另一个验证。它们不信任彼此——这就是重点。

第三个 agent 专门尝试打破第一个 agent 构建的东西：找边缘情况和失败模式。Red team, blue team——但自动化，每次变更都跑。

结论

旧模式：
review slowly, miss bugs anyway, debug in production
新模式：
ship fast, observe everything, revert faster
"Ultimately, if agents can handle the code just fine, what does it matter if we can read it or not?"
我们读不过机器。我们需要比机器想得更多——在上游，在决策真正重要的地方。
